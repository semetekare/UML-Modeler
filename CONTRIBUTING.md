# Как участвовать

UML Modeler — офлайн-редактор UML: vanilla ES-модули, SVG, ноль зависимостей,
ноль сборщика, ноль бэкенда. Правка — это файл в `app/src`, `app/notation`,
`app/course` или в документации; «сборка» — копия сайта в `app/dist`.

Полный контекст проекта и правила работы — [README.md](README.md) (§11–12),
инварианты слоёв — [docs/architecture/overview.md](docs/architecture/overview.md) (§1–6).

## Первый запуск

```sh
cd app
node tools/verify.mjs     # 18 наборов + сверка копий + реестр покрытия + эталон
./serve.sh                # http://localhost:8123 (порт ищется от 8123 вверх)
```

Открывать приложение нужно через сервер: ES-модули не грузятся с `file://`
(об этом прямо сказано в шапке [app/serve.sh](app/serve.sh)). Человек открывает
сборку `app/dist/index.html`, разработчик — `app/index.html`, оба через
`./serve.sh` из папки `app`.

Быстрая проверка без браузера: `node tools/verify.mjs --copies-only` — только
две копии, реестр покрытия, поисковый индекс и эталон.

Требуется Node и Python 3 (второй — для статического сервера). Ничего
устанавливать не нужно: `app/package.json` существует только ради проверщика
(`npm run build` = `node build.mjs`), зависимостей в нём нет.

## Правило №1: без зелёного `verify` не сдают

`cd app && node tools/verify.mjs` — один код возврата на всё. Он запускает
наборы по очереди (они поднимают headless-браузер и дерутся за порт), сверяет
`src` ↔ `dist` по md5, проверяет, что реестр покрытия не отстал от источника,
что поисковый индекс справочника содержит столько же правил, сколько в наборе,
и что эталон `tests/fixtures/old-v3.json` остался побайтово тем же
(4 611 Б, md5 `3d600cf08dc26b3329489331de80f3f6`). Устройство прогона —
[app/tools/verify.mjs](app/tools/verify.mjs).

Три вещи, которые `verify` ловит и которые руками не видны:

- набор, лежащий в `tests/` и не попавший в `SUITES`, — печатается как
  ЗАМЕЧАНИЕ: такой набор никто не запускает;
- разошедшиеся копии — «тесты зелёные, а человек видит старое»;
- устаревший `coverage.json` или поисковый индекс — числа в интерфейсе и в
  документации разъезжаются молча.

## Направление сборки одно: `src` → `build.mjs` → `dist`

```sh
cd app && node build.mjs    # dist/ + src/mechanics.generated.js (поставка: без прозы OMG)
cd app && node build.mjs --with-spec  # то же, но с полным текстом стандарта — только локально
```

- Правится **`app/src`**. `app/dist` руками не правится и обратно в `src` не
  копируется.
- `dist/` — копия **сайта**, а не копия `src/`: в ней `dist/src/`,
  `dist/notation/`, `dist/index.html` и остальные позиции списка `SITE`.
  Поэтому сравнивать `app/src` с `app/dist` напрямую нельзя — получите сотни
  ложных расхождений; сверку делает `verify.mjs` по-файлово.
- `app/src/mechanics.generated.js` генерируется из `app/mechanics.json`. Руками
  не правится: правка числа в листе без пересборки оставляет код со старым.

Почему правило жёсткое: 2026-11-07 копирование `dist/src` поверх `app/src`
уничтожило работу четырёх агентов (дерево, меню, печать, вложения);
`index.html` остался и ссылался на удалённые файлы — 404 в консоли и красный
`smoke`. Если `dist` новее `src`, это повод спросить, а не «синхронизировать»:
сборку делает один человек после слияния (иначе `dist` снимется с
полуправленого `src`). Правило родилось из аварии 2026-11-07, когда `dist/src`
скопировали поверх `src` и потеряли работу четырёх агентов.

## Как добавить правило проверки

Слоёв три, и они различаются данными, а не кодом: стандарт UML 2.5.1, практика
моделирования и правила проекта. Слой выставляет движок
(`basis: 'uml' | 'practice' | 'project'` в `app/src/rules/engine.js`), а в JSON
стандарта есть `source` с пунктом, у практики — `rationale` и нет `source`
(движок бросает, если у совета появился `source`).

1. Записать правило: `app/notation/rules/uml-2.5.1.json` (стандарт) или
   `app/notation/rules/practice.json` (совет). Поля стандарта: `id`, `source`
   (`clause`, `constraint`, `name`, дословный `text`, `ocl`, `page`, `file`),
   `level`, `appliesTo` (вид элемента и область), `check`, `message`, `hint`.
   В `hint` — граница «когда правило молчит»: без неё на корпусе появятся
   ложные срабатывания.
2. Написать функцию в `app/src/rules/<тема>.js` и добавить её в
   `CHECKS` в [app/src/rules/registry.js](app/src/rules/registry.js). Ключ
   реестра обязан совпасть с `check` правила: правило без функции — ошибка
   загрузки набора, а не тихий пропуск (кроме правил, записанных невыразимыми
   в `app/src/rules/coverage.js`).
3. Положить фикстуры: `app/tests/data/rules/<id>.json` и `<id>.ok.json`.
4. Добавить нарушение в `app/material/demo-errors.json` и строку в
   `app/material/DEMO-ERRORS.md`. Контракт `node tests/demo.mjs`: каждое
   правило с функцией обязано дать находку, случайных находок быть не должно.
5. Пересобрать каталог проверяемости:
   ```sh
   node material/rules-coverage/build.mjs              # coverage.json, report.md, docs/RULES-SOURCE.md
   cd app && node tools/build-coverage-ui.mjs          # копия для вкладки «Стандарт»
   ```
   `build.mjs --check` возвращает 1, если файлы устарели; он зависит от
   sha256 `app/notation/rules/uml-2.5.1.json`, поэтому после правки правил
   пересборка обязательна. Очередь невыполненных правил —
   `material/rules-coverage/TO-IMPLEMENT.md`.
6. Если правило добавляет новые данные справочнику:
   ```sh
   python3 material/reference-content/build_search_index.py && cd app && node tools/build-reference.mjs
   ```
   `verify` сверяет число правил в `app/reference/search.json` с числом правил в
   наборе.
7. Прогнать `node tests/rules.mjs` и `node tests/demo.mjs`, затем весь
   `node tools/verify.mjs`; сборку — после слияния.
8. Числа о правилах в документации не вбивать руками: их печатает прогон.
   После изменения набора проверить [app/README.md](app/README.md),
   [app/RULES-COVERAGE.md](app/RULES-COVERAGE.md),
   [docs/RULES-TESTS.md](docs/RULES-TESTS.md),
   [docs/user-guide/editing.md](docs/user-guide/editing.md),
   [docs/README.md](docs/README.md).

Чек-лист с теми же шагами и обоснованием — `docs/research/VALIDATOR-PLAN.md`,
Приложение B. Правила проекта хранятся в самом файле модели (`projectRules[]`),
пишутся по белому списку полей и операторов без `eval`.

## Как добавить фигуру

Нотация — данные, а не код: `app/notation/uml.json` (сейчас 51 фигура,
27 связей, 14 типов диаграмм).

1. Запись в `shapes`: `label`, `hint`, `icon` и `treeIcon`, `style`,
   `defaultSize`, при необходимости `compartments`.
2. `style` — имя из таблицы `RENDERERS` в `app/src/ui/render.js`. Незнакомого
   `style` быть не может: если фигуре нужен новый способ рисования, добавьте
   новый `style` в `RENDERERS` — и его переиспользуют все фигуры с этим стилем.
   Ветвление рендерера по `id` фигуры — ошибка.
3. Добавить фигуру в палитру своего типа: `types.<тип>.palette.shapes` и,
   если нужна клавиша, `types.<тип>.keys`.
4. Иконки рисуются в VectorCraft: `app/tools/make-icons.py` и редактируемый
   исходник `app/tools/icons.vectorcraft`. Копировать графику Visual Paradigm
   нельзя.
5. Прогнать `node tests/shape-types.mjs`, `node tests/types.mjs`,
   `node tests/smoke.mjs`, затем `verify`.

## Как добавить тип диаграммы

1. Запись в `types` файла `app/notation/uml.json`: `label`, `ru`, `kind`, `vp`,
   `what`, `palette` (фигуры и связи), `keys`.
2. Порядок в `typeOrder` — тип появится в списке листов. Второй пакет не
   создаётся и `notation/index.json` не трогается: у всех типов общая
   метамодель, поэтому они живут в одном файле.
3. Пересобрать каталог проверяемости (`material/rules-coverage/build.mjs`):
   вид → метакласс считается из нотации, новый вид меняет знаменатель покрытия.
4. Прогнать `node tests/types.mjs`, `node tests/layout.mjs`, `node tests/smoke.mjs`.

## Дисциплина доказательств

- **Свои проверки подозревай первыми.** Прежде чем объявлять чужую ошибку,
  сломай проверку намеренно: если тест остался зелёным — виноват тест.
  Намеренная поломка — штатный способ убедиться, что проверка проверяет.
- **Всякое число — с командой проверки.** «Стало лучше» без прогона не
  принимается; в отчёте должна быть команда, которой число повторяется.
- **Замер и решение не путать.** В `app/mechanics.json` у значения в `source`
  написано, откуда оно: адрес в коде, запись `.vpp`, файл и строка — или
  `decision` / `choice`, если число наше. Своё число помечается честно и не
  выдаётся за измеренное в оригинале.
- **Числа в документации расходятся молча.** Не всякое встреченное «23»
  относится к правилам (бывает «таблица из 23 BasicStroke» — про линии).
  Меняли правила — сверьте разделы о правилах в пяти документах из шага 8.

## Зоны

Параллельные агенты и люди не правят одни и те же файлы: перед началом
работы сверяются `mtime` и список зон. `node build.mjs` делает один человек
после слияния. Стенд приёмки, архивные снимки и планы прошлых проходов в
репозиторий не входят — они живут в приватной части, поэтому зоны здесь:
`app/`, `tests/`, `docs/`, `material/`.

## Стиль кода

- ES-модули, без зависимостей, без сборщика и транспиляции. Импорт — только
  вверх по слоям из [docs/architecture/overview.md](docs/architecture/overview.md) §1:
  `model/` не знает про DOM, `io/` не знает про `state/`.
- Комментарий объясняет **почему**, а не что: в этом коде «почему» — это
  история грабель, без неё следующий агент ломает работающее.
- Числа берутся из `mechanics.json` (см. §5 архитектуры), а не хардкодятся в
  CSS и JS.
- Офлайн — инвариант: никаких внешних загрузок. Все `fetch` идут на свои файлы
  рядом с приложением, шрифты локальные (`app/ui-kit/fonts/`, лицензии едут
  вместе с ними).
- Фигура не хранит смысл: имя, стереотип и члены живут в элементе модели (§3).
- Схема файла меняется только вместе с функцией миграции: старые
  `uml-model/2` и `uml-class-diagram/1` обязаны открываться.
- `ui-kit/` и `sync-kit/` — вендорные копии; своё оформление — в
  `app/src/brand/brand.css` переопределением переменных.

## Что не принимается

- зависимость, пакет, сборщик, транспиляция;
- сетевой вызов: внешний шрифт, CDN, телеметрия, «просто проверка версии»;
- изменение чисел в документации без пересборки источника этих чисел;
- правка `app/dist` руками;
- правка `ui-kit/`, `sync-kit/` и удаление `ui-kit/fonts/licenses/`.

## Как проверяется правка

Git в проекте нет, поэтому «PR» — это переданный набор файлов и отчёт о
прогоне. Принимающий проверяет:

1. полный `cd app && node tools/verify.mjs` — зелёный, включая раздел «две
   копии»;
2. отдельный прогон затронутого набора: `node tests/<набор>.mjs` (список
   наборов — `SUITES` в `app/tools/verify.mjs`);
3. если менялись правила — `node material/rules-coverage/build.mjs --check`;
4. числа в [app/README.md](app/README.md),
   [app/RULES-COVERAGE.md](app/RULES-COVERAGE.md),
   [docs/RULES-TESTS.md](docs/RULES-TESTS.md),
   [docs/user-guide/editing.md](docs/user-guide/editing.md) и
   [docs/README.md](docs/README.md) совпадают с выводом прогона;
5. итоговый diff прочитан целиком: сборку `dist` делает один человек после
   слияния.
