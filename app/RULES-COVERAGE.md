# Проверки UML 2.5.1: что проверяется, чем и что не выражается

> **Что это.** Наборы правил, движок, который их проверяет, и панель «Проверки»,
> которая показывает результат. Слоёв три, и они разные по природе: констрейнт
> стандарта со ссылкой на пункт, совет практики с обоснованием и правило проекта
> — договорённость команды из файла модели. Числа о правилах здесь намеренно не
> пишутся: их считает [`material/rules-coverage/build.mjs`](../material/rules-coverage/build.mjs)
> и печатает в [`docs/RULES-COVERAGE.md`](../docs/RULES-COVERAGE.md) (указатель,
> собирается из `coverage.json`) и в
> [`report.md`](../material/rules-coverage/report.md). Расхождение поймает
> `node material/rules-coverage/build.mjs --check`.
>
> **Чего это не делает.** Проверки — совет, а не запрет: они не отклоняют файл
> при сохранении, не мешают открыть старую модель, не блокируют импорт и не
> меняют модель ни на байт. Модель с нарушениями сохраняется и открывается как
> обычная.

---

## 1. Как это устроено

Три слоя различаются происхождением правила, а не строгостью. У правила
стандарта есть пункт UML, на который оно ссылается; у совета практики ссылаться
не на что — есть только объяснение, почему такую модель труднее читать; у
правила проекта нет ни пункта, ни обоснования: это договорённость, и живёт она
в файле модели, а не в поставке приложения.

| Роль | Файл | Что делает |
|---|---|---|
| данные: стандарт | `notation/rules/uml-2.5.1.json` | правило = `id`, `source` (пункт, констрейнт, дословный текст, OCL, страница), `level`, `appliesTo`, `check`, `message`, `hint` |
| данные: практика | `notation/rules/practice.json` | те же поля без `source`; вместо него обязательный `rationale` |
| данные: проект | `projectRules[]` в файле модели | правило, которое завёл человек; схема `uml-project-rules/1`, поставкой не поставляется |
| реестр | `src/rules/registry.js` | `check → функция`. Ключ обязан совпасть с `check` правила; `PRACTICE_CHECKS` говорит, какие проверки принадлежат практике |
| проверки стандарта | `src/rules/<тема>.js` | по одной маленькой функции на `check`; файл — это метакласс или тема (`multiplicity`, `names`, `classification`, `pseudostates`, `activity`, `fragments`, `instances`, `port`, `transitions`, `deployment`, `component`, `ownership`, `interaction`…) |
| проверки практики | `src/rules/practice.js` | советы о сиротах, дублях, безымянных и ссылках; проверки о подписях последовательности лежат рядом, в `sequence.js` — у них та же природа, но свой предмет |
| ссылки модели | `src/rules/refs.js` | индекс по `id` на один прогон правила: `classifierId`, `behaviorRef`, `represents`, `refersTo`, `ownerId`, номер листа |
| графовые помощники | `src/rules/graph.js`, `cycle-path.js` | входящие/исходящие рёбра по родам; цикл вместе с путём |
| вид → метакласс | `src/rules/meta.js` | `oclIsKindOf` там, где констрейнт спрашивает метакласс, а у нас вид нотации |
| движок | `src/rules/engine.js` | собирает слои, проверяет целостность при загрузке, гоняет правила, изолирует сбой одного правила |
| DSL и компиляция | `src/rules/dsl.js`, `project.js` | белый список полей и операторов, проверка правила, предикат без `eval` |
| загрузка | `src/rules/index.js` | читает оба JSON при старте страницы, как нотацию |
| невыразимое | `src/rules/coverage.js` | правила стандарта, у которых нет функции, с названным недостающим полем |
| панель | `src/ui/checks.js` | разделы по слоям, счётчик в статусбаре, переход к объекту, список «не проверяется» |

Поля `basis` в файлах правил нет — слой приписывает движок по тому, из какого
набора пришло правило: иначе набор мог бы назваться чужим слоем.

Поимённого списка файлов здесь нет намеренно: новый метакласс — новый файл, и
перечисление устарело бы на первом же правиле. Устойчива роль; кто её играет
сегодня, видно по `import` в `registry.js`.

Единственная разница между копией набора в приложении и
`docs/rules-uml-2.5.1.json` — поле `source.notice: "app/reference/NOTICE.md"` у
каждого правила; в `docs/` этого поля нет, а сами правила совпадают (это
проверяет `tests/rules.mjs`).

Замечание, которое возвращает проверка:

```
{ ruleId, level, basis, message, detail, hint,
  clause, constraint, page, rationale, targets: [id…], diagramId }
```

`message` — формулировка нарушения из набора (одна на правило), `detail` — что
именно нашлось в этой модели, `targets` — id элементов и связей модели (не фигур:
вид на объект ищет панель). У двух правил о циклах (`generalization-cycle`,
`usecase-include-cycle`) `targets` — это весь путь обхода: `[A, B, C]`, у петли
`[A]`; первый id — тот, с которого начинается показ, а `detail` называет цепочку
словами.

Запись-сбой (`status: 'failed'`, `failure()` в `src/rules/finding.js`) — та же
форма плюс `status` и пустые `targets`: правило не смогло прочитать модель, и
винить некого. У обычного замечания поля `status` нет вовсе — отсутствие и есть
«это нарушение модели».

`diagramId` — лист, к которому замечание относится, или `null`. Ставит его
единственное правило — `shape-isolated-on-diagram`: фигура одинока на
конкретном листе, и переходить надо туда, а не на первый попавшийся. У слоя
стандарта это поле всегда `null`: констрейнты говорят о модели, а не о листах,
и `gotoFinding` выбирает лист сам — текущий, если объект на нём есть, иначе
первый, где он показан.

`basis` говорит, откуда правило: `uml`, `practice` или `project`. Отсюда и
разная обвязка: у замечания стандарта заполнены `clause`, `constraint` и `page`,
а `rationale` пуст; у замечания практики наоборот — три поля ссылки равны
`null`, `rationale` заполнен; у правила проекта пусто и то, и другое. Панель по
`basis` раскладывает замечания по разделам, поэтому совет никогда не покажет
пустое «п.», а нарушение стандарта — пустое объяснение.

### Ошибка загрузки, а не тихий пропуск

`createRuleset` отказывается собирать набор, если:

- у правила стандарта нет `source.clause`, `source.constraint` или
  `source.text` — правило без пункта стандарта в набор не попадает;
- у правила практики есть поле `source` — практика не имеет права притворяться
  стандартом;
- у правила практики пуст `rationale` — совет обязан объяснить, почему модель
  читать труднее;
- `level` не `error` и не `warning`;
- `check` правила нет в реестре и правило не записано невыразимым;
- правило записано невыразимым, но функция для него всё-таки есть;
- в наборе два правила с одним `id`;
- в реестре есть проверка, которой не пользуется ни одно правило (опечатка в
  `check`);
- правило проекта не проходит проверку DSL — неизвестное поле, оператор или
  связка.

Отказ виден: панель «Проверки» и статусбар говорят «проверки: —» с причиной,
модельер при этом работает дальше. Наборы читаются вместе: битый любой — это
отказ загрузки, а не «половина правил». Битое правило проекта внутри уже
открытой модели ведёт себя иначе — оно одно становится записью-сбоем, потому
что уносить весь прогон из-за опечатки в файле модели нельзя.

## 2. Какие констрейнты проверяются

Полный список с пунктами, статусами и причинами — в
[`report.md`](../material/rules-coverage/report.md) и
[`coverage.json`](../material/rules-coverage/coverage.json): там у каждого из
констрейнтов стоит `status` (`executable`, `todo`, `gap`, `tautology`,
`no-ocl`, `out-of-scope`). Дублировать таблицу здесь смысла нет — она уже
разъехалась один раз, когда правила писали быстрее, чем документ.

Три места, где толкование стандарта неочевидно и записано в комментариях к
проверкам, — их стоит прочитать, прежде чем править правило:

- `composite-upper-bound-le-1` верит прозе (конец с ромбом), а не OCL рядом с
  ней (противоположный конец), иначе обычная композиция «1 ◆—— 0..*» считалась
  бы ошибкой;
- `namespace-members-distinguishable` ищет дубли внутри одной полки члена
  (`attributes`, `operations`): вложенности пространств имён в схеме нет, а
  сигнатура операции лежит в `name`, поэтому перегрузки различимы сами;
- `usecase-no-association-to-usecase` при отсутствии поля `subject` считает
  нарушением любую ассоциацию между вариантами использования — это же советует
  `hint`, и при появлении `subject` проверка станет точнее без переписывания.

Кратность у члена модели не проверяется, и это не пропуск. У члена в
`uml-model/3` поля кратности нет вовсе (`member()` = `{vis, name, type,
default}`), а проверки смотрят только на концы связей. Поэтому у
`mult-upper-ge-lower` и `mult-lower-non-negative` из `appliesTo` убрано поле
`member: ["attribute", "operation-parameter"]`: правило не имеет права называть
поле, которого в модели не существует. У `mult-lower-is-integer` и
`mult-upper-is-unlimited-natural` поля `member` не было изначала — проверка
литерала относится к кратности на любом носителе, и это намеренно.

## 3. Чего модель не выражает

Это не отключённые правила и не «не успели»: проверить их нечем. Список ниже —
ключи `NOT_EXPRESSIBLE` в `src/rules/coverage.js`, и разойтись с набором он не
может: движок бросает, если ключ не соответствует правилу или если у
«невыразимого» появилась функция. Тот же список показан в самой панели
«Проверки» — свёрнутым блоком внизу, чтобы он был виден в продукте, а не только
в документе.

| Правило | Чего не хватает модели |
|---|---|
| `association-specialization-ends` | концы обобщения, которые могут указывать на **связь**, а не только на элемент: загрузчик выбрасывает обобщение с id связи на конце, поэтому ассоциацию-потомка в модели не выразить |
| `association-end-typed` | необязательный конец ассоциации: конец типизирован самим фактом связи, нетипизированного не бывает |
| `stereotype-binary-association` | список концов (`memberEnd`) вместо пары `from`/`to`: при двух концах `memberEnd->size() = 2` выполняется всегда |
| `usecase-binary-association` | то же самое: небинарную ассоциацию схема не знает |
| `transition-same-container` | `regions` у состояния и признак `local` у перехода: сравнить «ту же машину» нечем |
| `package-element-visibility` | видимость **элемента** (у члена она есть, у элемента нет) |

Причины у них разные, и путать их нельзя. Три — **тавтологии схемы**
(`association-end-typed`, `stereotype-binary-association`,
`usecase-binary-association`): при `from`/`to` нарушить их нечем, и это не долг,
а свойство формата. Два упираются в **отсутствующее поле** и станут правилами,
когда поле появится. Одно **невозможно по конструкции**
(`association-specialization-ends`): ситуация не записывается в файл, а не
«пока не написана».

У `association-aggregation-binary-only` проверяется только OCL-половина
(`memberEnd->exists(aggregation = none)`): проза «Only binary Associations can be
aggregations» требует небинарной ассоциации, которой схема не знает. Это
единственное правило, покрытое частично, и в прототипе оно такое же.

## 4. Слой практики

Стандарт UML не запрещает элементу не участвовать ни в одной связи, поэтому
такое нарушение не может быть правилом стандарта: у него нет пункта, на который
можно сослаться. Движок же отказывается грузить правило без `source.clause`.
Отсюда второй набор: советы практики моделирования. У них нет поля `source`
вовсе, вместо него `rationale` — почему такую модель труднее читать. Все советы
уровня `warning`: совет не может быть ошибкой.

| Правило | Что ловит |
|---|---|
| `element-isolated` | элемент не участвует ни в одной связи модели |
| `element-not-on-any-diagram` | элемент есть в модели, но ни на одной диаграмме нет его фигуры |
| `element-unnamed` | у элемента пустое имя |
| `relationship-duplicate` | две связи одного структурного вида между одной и той же парой, у которых совпадают роли, кратности, имя, навигация и агрегация концов |
| `relationship-not-on-any-diagram` | связь есть в модели, но её вида нет ни на одной диаграмме |
| `shape-isolated-on-diagram` | фигура на листе не соединена ни с одной, хотя её элемент в модели связан |
| `name-not-clash` | имя стереотипа уже занято другим стереотипом на том же метаклассе |
| `object-classifier-kind` | `classifierId` объекта ведёт на пакет, заметку или актёра, а не на классификатор |
| `action-behavior-is-activity` | ссылка «вызывает» у действия ведёт не на деятельность |
| `swimlane-represents-kind` | дорожка «представляет» пакет или заметку, а не участника |
| `interaction-use-refers-kind` | ссылка на взаимодействие ведёт не на лист взаимодействия или на себя |
| `lifeline-represents-classifier` | линия жизни представляет не классификатор |
| `message-signature-operation` | сигнатура сообщения называет операцию, которой у классификатора получателя нет |

Правило практики с полем `source` — ошибка загрузки набора, как и правило без
`rationale`. Это не формальность: поле `source` у практики означало бы, что
совет выдаёт себя за констрейнт стандарта, а панель нарисовала бы у него кнопку
«п.», ведущую в пустоту.

### Границы, откалиброванные по корпусу

Наивное «элемент без связей» даёт на 48 учебных моделях с раскладкой
(`material/corpus-layout`) **137** срабатываний, и почти все ложные: заметки,
пакеты, дорожки и прочие виды стоят на листе сами по себе по своей природе.
Правило с таким выходом бесполезно — человек перестаёт его читать. Отсюда две
границы в `src/rules/practice.js`:

- **`STANDALONE`** — виды, которые стоят на листе сами по себе по природе:
  `note`, `text`, `package`, `model`, `profile`, `systemBoundary`, `swimlane`,
  `fragment`, `interactionUse`, `activation`, `port`, `activityParameter`,
  `timingLane`. Они исключаются из `element-isolated`, `element-unnamed` и
  `shape-isolated-on-diagram`.
- **`STRUCTURAL`** — виды связей, у которых повтор между той же парой считается
  дублем: `association`, `aggregation`, `composition`, `generalization`,
  `realization`, `dependency`. Сообщения, потоки и переходы исключены: вызов и
  ответ между той же парой линий жизни законны, и на полном наборе видов все
  ложные срабатывания корпуса приходились на `message`.

После границ замер по тем же 48 моделям: `element-isolated` — **96**,
`element-unnamed` — **2**, остальные четыре правила — по нулю. Слой стандарта на
этом корпусе даёт 0. Разница 137 → 96 и есть цена границы: 41 срабатывание из
137 были не находками, а видами, которым связи не положены.

Число это — свойство **корпуса**, а не правил, и твёрдым порогом в тестах не
стоит: корпус живёт в `material/` и его правят отдельно от приложения. Дописали
связь в модель — сирот стало меньше; завели две одинаковые — стал виден
настоящий дубль. Тест поэтому проверяет не число, а то, что обязано быть верным
при любом корпусе: слой стандарта молчит, каждое замечание практики размечено и
адресовано существующему объекту, а урожай не превращается в «сработало на
каждом элементе».

### Граница `hasAnyView`

Правила о диаграммах (`element-not-on-any-diagram`,
`relationship-not-on-any-diagram`) молчат, если в модели нет ни одной фигуры.
Причина в том, что файл `uml-model/3` вправе хранить модель без видов: так лежит
`app/tests/data/corpus` — 48 моделей, 0 фигур, 0 видов связей. Без этой границы
правила сказали бы «не показан» про каждый элемент и каждую связь — по
замечанию на каждый, сотни строк шума, — и это ничего не говорило бы о модели,
у которой листы просто не заполнены.

### Корпус неполон, и это дефект корпуса

У 17 из 48 моделей корпуса нет ни одной связи, у 20 есть хотя бы один
изолированный элемент. 5.1.6 — 13 элементов и 0 связей, 4.2.1 — 5 классов и 0
связей, 3.1.1 — 5 актёров и 0 ассоциаций. Отсюда почти весь урожай
`element-isolated`. Правило здесь работает правильно: модель без связей
действительно читается плохо. Но число 96 говорит о корпусе не меньше, чем о
правиле, и убирать границы ради красивой цифры нельзя — ни в ту, ни в другую
сторону.

## 5. Третий слой: правила проекта

Правило проекта отвечает не «верна ли модель по UML» и не «удобно ли её
читать», а «как договорилась команда»: «домен не зависит от интерфейса», «у
публичного класса есть документация». Поэтому у его замечания нет ни пункта, ни
`rationale`, а есть только текст правила; счётчик в статусбаре отдельный —
`· проект N`, и в «предупреждения UML» эти замечания не подмешиваются, иначе
стандарт выглядел бы строже, чем он есть.

- **Где живут.** `projectRules[]` в файле модели, схема `uml-project-rules/1`.
  Модель без правил сохраняется байт в байт: пустой массив не пишется.
- **Как устроены.** Условие из белого списка полей (`kind`, `name`,
  `stereotype`, `owner.name`, `owner.kind`, `visibility`,
  `documentation.empty`, `incoming`, `outgoing`; у связи — концы и кратности) и
  операторов (`eq`, `ne`, `in`, `notIn`, `glob`, `exists`, `empty`, `notEmpty`,
  `gt`, `lt`, `ge`, `le`), связанных `all`/`any`/`not`. Никакого `eval` и
  никаких регулярных выражений: `glob` сравнивается двумя указателями, поэтому
  ReDoS неоткуда взяться.
- **Почему проверка при загрузке, а не при прогоне.** Неизвестное поле или
  оператор — это ошибка с **именем правила**, а не «правило ничего не нашло»:
  иначе человек искал бы дефект в модели там, где опечатка в правиле.
  `validateRule` зовёт и редактор (показать ошибку до сохранения), и движок
  (отказаться собирать). Битое правило, пришедшее из файла уже открытой модели,
  не роняет прогон: оно становится одной записью-сбоем, остальные замечания
  остаются.
- **Откуда берутся данные для условия.** Владелец, степени вершины и концы
  связи считаются в `project.js` на каждый прогон: `commit` правит модель на
  месте, и кеш по ссылке на модель судил бы вчерашнее состояние.

Как читать замечания всех трёх слоёв, что значит «не проверено N» и как добавить
своё правило — [`docs/uml/validation.md`](../docs/uml/validation.md).

## 6. Чем это подтверждено

| Проверка | Где | Что доказывает |
|---|---|---|
| проверки движка | `node tests/rules.mjs` | у каждого правила стандарта есть пункт; реестр покрывает оба набора поставки (правилу проекта `check` не нужен — его компилирует `project.js`); правило без функции — ошибка загрузки; на каждое правило пара фикстур (нарушение ловится, контрольная чиста, чужие правила молчат); упавшее правило даёт одну запись-сбой и не уносит остальные замечания, сбой не попадает в счётчик нарушений; цикл обобщения и цикл включений несут весь путь (`targets.length === 3`), петля — один элемент; границы `STANDALONE`/`STRUCTURAL` совпадают с `appliesTo`; корпус из 48 моделей даёт 0 замечаний стандарта; прогон детерминирован |
| сценарии интерфейса | `node tests/types.mjs` | панель открывается и показывает замечание стандарта со ссылкой на пункт; раздел практики с чипом «практика» и без кнопки пункта; диалог практики говорит «это не требование стандарта»; счётчик статусбара совпадает с числом замечаний, включая хвосты «· советов N» и «· проект N»; клик по замечанию выделяет объект; фильтр «только ошибки» режет оба слоя; пустое состояние; сбой проверки идёт отдельным разделом, без кнопки пункта и без перехода к объекту, а «все чисто» при нём не пишется; модель с нарушением сохраняется и открывается; правила обоих наборов приходят с источниками; 48 моделей корпуса |
| правила проекта | `node tests/project-rules.mjs` | DSL отвергает неизвестное поле и оператор с именем правила; правило компилируется в предикат; пять правил дают столько же замечаний, сколько независимый пересчёт; правило переживает круг «сохранить → открыть»; модель без правил не меняется ни на байт |
| сценарии модели | `node tests/smoke.mjs` | сохранение байт в байт, старый файл `uml-model/3` не меняется, миграция `uml-class-diagram/1` |
| демо всех правил | `node tests/demo.mjs` | каждое правило с функцией даёт находку на демо-модели и ни одно замечание не ссылается в пустоту |
| прототип | `node tests/rules/check.mjs` (в корне проекта) | замороженный срез слоя стандарта: те же проверки и фикстуры, что были на момент заморозки |

Число проверок в каждом наборе печатает сам прогон — здесь оно не повторяется,
чтобы не разъезжаться с кодом. Фикстуры и корпус для тестов приложения
скопированы в `tests/data/` (источник — `tests/rules/` и `tests/corpus/`
проекта; копия нужна, чтобы тесты работали от корня `app/`, который отдаёт
сервер). У слоя практики теперь есть пары фикстур наравне со стандартом: корпус
доказывал только отсутствие ложных срабатываний, а срабатывание не доказывал.

## 7. Решения там, где план молчит

1. **Ключ реестра — `check`, а фикстуры названы по `id` правила.** Это разные
   имена (`composite-end-upper-bound` против `composite-upper-bound-le-1`).
   Реестр держится за `check` (так требует задание), тесты сопоставляют их через
   набор правил, а не по имени файла.
2. **Ссылка на пункт стандарта открывает окно с цитатой**, а не уходит в
   интернет: приложение офлайн, а пункт стандарта — это дословный текст
   констрейнта, его OCL и страница. В `title` та же цитата — видно без клика.
3. **Замечание несёт `detail` сверх обязательных полей.** `message` — перевод
   констрейнта на человеческий язык (одинаков для правила), `detail` — что
   именно нашлось («конец «from»: кратность «5..2»…»). Без второго панель
   показывала бы десять одинаковых строк.
4. **Список «не проверяется» стоит в панели**, свёрнутый, с пунктом и
   недостающим полем. Держать его только в документе — значит показывать
   человеку «0 из 0» без объяснения, почему у набора есть правила без функции.
5. **Слой практики — отдельный раздел панели, а не строки в общем списке.**
   Общий список выдавал бы совет за нарушение: у замечания практики нет пункта,
   нет уровня «ошибка», и подпись у него своя — «совет». Раздел появляется
   только тогда, когда в нём что-то есть.
6. **Счётчики слоёв не складываются.** `checkCounts()` возвращает `{errors,
   warnings, advice, project, failed, total, ready, error}`; `total` — сумма
   `errors` и `warnings`, то есть только стандарт. `advice` и `project` в неё не
   входят: иначе «предупреждений» стало бы больше без единого нового нарушения
   стандарта. Отсюда три вида строки в статусбаре: `проверки: 2 · 1`,
   `проверки: 0 · 0 · советов 1` и `проверки: 0 · 0 · проект 3`, а при сбое —
   хвост `· не проверено N`.
7. **Прогон кешируется по ревизии модели.** Панель и статусбар считают один и
   тот же результат, поэтому цифры не расходятся, а перерисовка панели не
   запускает проверки заново. Правка модели — новый прогон.
8. **Автопрогон — при открытии вкладки и при каждой правке модели**, кнопка
   «Проверить» нужна для «покажи ещё раз» (и для человека, который не доверяет
   тишине).
9. **Проверки ничего не отменяют.** Движок читает модель и возвращает список;
   ни `deserialize`, ни `serialize`, ни импорт его не вызывают. Модель с
   нарушением сохраняется побайтово так же, как чистая, — это проверено тестом.
10. **Правила проекта не попадают в `rules` движка.** Они меняются вместе с
    моделью, а `rules` — снимок загрузки; поэтому они собираются в `run` и
    кешируются по ссылке на массив правил, а не по модели.
