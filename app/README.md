# UML Modeler

Веб-редактор UML 2.5 в духе Visual Paradigm: **все 14 типов диаграмм**, профиль
из 304 стереотипов, модель «элемент + вид» и вложенные диаграммы. Без сборщика,
без npm, без зависимостей — чистые ES-модули, SVG-канва и светлая тема ui-kit.
Работает офлайн.

    ./serve.sh                          → http://localhost:8123 (занят — следующий свободный)
    ./serve.sh 8300                     → другой порт
    ./serve.sh --screenshot файл.png    → снимок окна 1440×900 и выход

`--screenshot` поднимает сервер, снимает страницу headless-браузером
(Playwright headless-shell → Chromium из кеша Playwright → Chromium Craft
Anything → системный Chrome → Firefox) и проверяет, что PNG не пустой. Та же
реализация у `Build/uml-modeler --screenshot`; `serve.sh` только передаёт ей
управление. Для проверки одного типа: `Build/uml-modeler --screenshot s.png
--query "model=all&diagram=sequence"`.

## Что умеет

- **Пустой старт.** При первом открытии — не готовый пример, а экран «Начало
  работы»: одна крупная кнопка «Создать диаграмму…», рядом «Открыть файл…»,
  два примера и курс. Пустая модель при этом настоящая (ноль диаграмм), панели
  и инструменты живут как обычно. Автосохранение черновика возвращается молча,
  `?model=sample` и `?model=all` открывают пример сразу — этим живут
  браузерные наборы и снимки (`src/ui/welcome.js`, `src/welcome.css`).
- **14 типов UML 2.5** — структурные: Class, Component, Composite Structure,
  Deployment, Object, Package, Profile; поведенческие: Activity, State Machine,
  Use Case, Sequence (в VP — `InteractionDiagram`; `FramedInteraction` — это
  рамка-фрагмент внутри Sequence), Communication, Timing, Interaction
  Overview. Тип выбирается при создании диаграммы («+» у списка диаграмм);
  палитра, клавиши и инспектор меняются вместе с типом.
- **Профиль стереотипов** из `profile/stereotypes.json` — **304 стереотипа**
  (428 записей профиля Visual Paradigm → 407 определений после слияния дублей →
  304 после канонизации имён; 15 с рисунком, 9 псевдонимов). Файл собирает
  `tools/build-profile.mjs` из `material/profile-canonical/`; `material/stereotypes.xml`
  — вход этой сборки, а не то, что приложение открывает при запуске. Стереотип
  назначается **элементу и связи**; tagged values (текст, перечисление, длинный
  текст) редактируются в инспекторе, свои значения добавляются кнопкой.
- **Модель «элемент + вид»**: элемент живёт в модели, диаграмма — вид на него.
  Один элемент на нескольких диаграммах; связь живёт в модели, на диаграмме —
  её вид. `Delete` снимает вид, `Shift+Delete` удаляет из модели.
- **Вложенные диаграммы**: диаграмма принадлежит элементу модели, видна под ним
  в дереве и открывается оттуда. Создать вложенную — «+ Вложенная диаграмма» в
  инспекторе; **перенести уже созданную** — селект «Владелец» в том же
  инспекторе (пособие, упр. 4.3.3 требует именно переноса из корня). Отказ один:
  элемент, показанный на самой диаграмме, владельцем стать не может — лист
  оказался бы внутри себя (`setDiagramOwner` в `src/model/model.js`).
- **Дерево модели** — не список имён: под элементом его связи (вид, имя, второй
  конец), вложенные элементы, его диаграммы и «Где используется» (список
  листов). Ветки сворачиваются (стрелки, `aria-expanded`, состояние помнится в
  `localStorage`), есть «свернуть всё / развернуть всё» и сортировка «по порядку
  в файле / по имени / по виду». Поиск ищет по имени, виду, стереотипу,
  документации и именам связей и подсвечивает совпадение (`src/tree.css`).
- **Контекстное меню** — правый клик по фигуре, связи или пустому месту листа.
  Пункты зовут те же команды, что меню и клавиши: «Переименовать», «Свойства»,
  «Стереотип…», «Дублировать», «Снять с диаграммы», «Удалить из модели» (с
  пояснением, что исчезнет со всех диаграмм), а на пустом — «Вставить»,
  «Вписать в окно», «Сетка». Клавиатура: ↑↓, Home/End, Enter, Esc
  (`src/ui/context-menu.js`, `src/context-menu.css`).
- **Имя сразу после постановки.** Поставили фигуру — редактор имени открылся
  сам, текст выделен: Enter принимает, Esc оставляет имя по умолчанию. Раньше
  на каждую фигуру приходилось жать F2.
- **«Держать» — липкий инструмент.** Кнопка-кнопка в конце полосы: включённая,
  она оставляет инструмент после постановки (десять вариантов использования —
  десять кликов вместо десяти нажатий клавиши). По умолчанию **выключена**:
  иначе клик по пустому листу начал бы новую фигуру вместо снятия выделения.
- **Печать / PDF** — первым пунктом меню «Экспорт»: печатается только лист,
  A4, с подписью модели и диаграммы. Панели, полоса и статусбар на печати
  скрыты (`src/ui/print.js`, `src/print.css`).
- **Вложения файлов** — у элемента модели: «Приложить файл…», список с именем и
  размером, скачивание и удаление, предел 2 МБ на файл. Файл живёт **внутри**
  модели (`element.attachments`, base64) и уезжает вместе с `.uml.json`: сервера
  нет, положить файл рядом некуда. Пустой список в файл не пишется, поэтому
  старые модели пересохраняются байт в байт.
- **Хитбоксы.** У актёра, линии жизни, начального/конечного узла и ромба решения
  под рисунком лежит невидимая подложка во всю рамку: попасть мышью можно по
  всей фигуре, а не только по кружку головы (было 9,1 % рамки актёра — стало
  100 %). В экспорт SVG подложка не попадает.
- **Две связи между одной парой — две линии.** Если у двух фигур две законные
  связи (ассоциация и зависимость, две ассоциации с разными ролями), концы
  каждой отходят от кромки на своё место: обе линии, обе подписи и обе
  кратности видны. Сдвиг — свойство рисунка, в файл он не пишется
  (`src/model/parallel-links.js`, шаг — `mechanics.json`).
- Фигуры двигаются и ресайзятся, связи перерисовываются за концами, концы и
  подписи перетаскиваются, двойной клик правит имя/строку члена/строку
  entry-do-exit/подпись связи.
- Отмена/повтор (100 шагов), автосохранение черновика, Ctrl+K — палитра команд,
  сохранение/открытие `*.uml.json`, экспорт SVG.
- **Экспорт всего проекта** — один `.json` со всеми диаграммами (метка
  `kind: 'project'`) плюс по SVG на диаграмму; такой файл открывается целиком,
  а не первой диаграммой.
- **Оборванный файл не теряется**: если JSON обрезан (закрытая вкладка, полный
  диск, оборванная передача), модель восстанавливается до последнего целого
  значения, а не выбрасывается исключением.

## Типы и их палитры

| Тип (VP) | Фигуры | Связи |
|---|---|---|
| Class | класс, интерфейс, перечисление, тип данных, пакет, объект, примечание | ассоциация, агрегация, композиция, обобщение, реализация, зависимость |
| Component | компонент, интерфейс, порт, артефакт, класс, пакет, примечание | сборка, зависимость, реализация, обобщение, ассоциация |
| Composite Structure | класс, компонент, часть, порт, кооперация, использование кооперации | коннектор, делегирование, сборка, зависимость |
| Deployment | узел, устройство, среда выполнения, артефакт, спецификация развёртывания, компонент | развёртывание, путь связи, ассоциация, зависимость, манифестация |
| Object | объект, класс, пакет, примечание | связь объектов, ассоциация, зависимость |
| Package | пакет, модель, класс, интерфейс, примечание | зависимость, импорт, слияние, обобщение, использование |
| Profile | профиль, стереотип, метакласс, класс, пакет | расширение, обобщение, зависимость, ассоциация |
| Activity | деятельность, действие, начальное/конечное, решение, слияние, разделение, объединение, объект данных, параметр, дорожка | поток управления, поток объектов |
| State Machine | состояние, начальное, конечное, выбор, соединение, история (мелкая/глубокая), точка входа/выхода, завершение | переход |
| Use Case | актёр, вариант использования, граница системы, пакет | ассоциация, включение, расширение, обобщение, зависимость |
| Sequence | линия жизни, актёр-линия жизни, активация, фрагмент, ссылка на взаимодействие | сообщение, ответ, создание, уничтожение |
| Communication | объект, актёр, линия жизни | связь объектов, сообщение |
| Timing | шкала времени | сообщение |
| Interaction Overview | взаимодействие, ссылка на взаимодействие, начальное/конечное, решение, слияние, разделение, объединение | поток управления |

Список — данные, а не код: `notation/uml.json` описывает фигуры (`style`,
размер, компартменты), связи (наконечники, пунктир, кратности) и палитру
каждого типа. Один метамодельный набор на все типы — как в самом Visual
Paradigm, где `MODEL_ELEMENT` общий, а тип диаграммы лишь выбирает вид.

## Где что лежит в интерфейсе

- **Полоса над листом** — инструменты выбранного типа: «Выбор», фигуры, связи.
  Высота 56 px с подписями, 32 px только со значками — решает замер: если
  подписи всех инструментов типа не влезают в ширину полосы (у Class 14
  инструментов и нужно ~1076 px), полоса сама переходит на значки, чтобы ни
  один инструмент не уезжал за край. Подписи остаются в `title`, `aria-label`
  и Ctrl+K.
- **Слева** — дерево модели по схеме владельца: **корень — диаграммы**, внутри
  листа плоский список его содержимого — элементы (в порядке постановки) и
  связи (в порядке связей), без групп «Элементы»/«Связи». Элемент, владеющий
  диаграммой, показывает её дочерним узлом (и та раскрывается так же).
  «Где используется» в дереве нет — этот список живёт в инспекторе
  («Показан на: N листах») и в подсказке строки. Ветка «Модель — нигде не
  показаны: N» появляется только когда есть сироты. Клик по диаграмме
  открывает её; двойной клик по элементу ставит его на текущий лист; строку
  можно перетащить на лист. В шапке панели — свернуть/развернуть всё,
  сортировка (файл / имя / вид) и поиск по имени, виду, стереотипу,
  документации и связям.
- **Справа** — «Свойства» (имя, стереотип, документация, таблицы членов,
  строки entry/do/exit, оператор фрагмента, состояния шкалы времени, заливка
  сплошная или градиентом из 16 направлений — как в оригинале,
  tagged values, вложенные диаграммы, размер), «Профиль» (все 304 с поиском;
  клик назначает стереотип выделенному) и «Проверки» (три слоя: констрейнты
  UML 2.5.1 со ссылкой на пункт, советы практики моделирования без пункта и
  правила проекта из файла модели; переход к объекту по клику).
- **Шапка** — Файл (новая модель, открыть, сохранить, импорт PlantUML),
  Правка (отмена/повтор, копирование/вырезание/вставка/дубликат, выравнивание
  и распределение, две команды удаления), Вид (сетка 10 px), Примеры
  (классы, ошибки проверок, все 14 типов), Экспорт (весь проект, печать всех
  диаграмм в PDF, SVG, PNG ×1 и ×2, JSON, печать этой диаграммы в PDF),
  список диаграмм и «+», панели, «?», Акцент (6 пресетов; от него зависит и
  цвет всех панелей, и выделение на листе).
- **Имя диаграммы** правится в инспекторе, блок «Диаграмма»: поле «Имя»
  (Enter или уход фокуса), рядом тип и «Владелец». После правки имя сразу
  меняется в списке диаграмм и в дереве; пустое имя не принимается.

Выделение — список: рамка-лассо на пустом месте листа и Shift-клик набирают
группу, группа перетаскивается, сдвигается стрелками и удаляется целиком, а
при двух и более фигурах в инспекторе появляются восемь пиктограмм
выравнивания. `Ctrl+C`/`Ctrl+X`/`Ctrl+V`/`Ctrl+D` работают на модели: вставка
на том же листе создаёт новые элементы, на другом — вид существующего, `Ctrl+D`
всегда дублирует элемент со сдвигом на шаг сетки. Строку дерева можно
перетащить на лист — это тоже вид, и если он уже есть, он подсвечивается.

## Модель и вид

`uml-model/3` разделяет три вещи, как `.vpp`:

| Что | Где живёт | Что хранит |
|---|---|---|
| элемент | `elements[]` | имя, тип, стереотип, документация, члены, tagged values |
| связь | `relationships[]` | тип, имя, стереотип, концы-элементы, кратности, роли, tagged values |
| вид | `diagrams[].shapes[]`, `diagrams[].links[]` | геометрию и ссылки на элемент/связь |

Следствия:

- переименование элемента — одна правка, видно на всех диаграммах;
- `Delete` на фигуре снимает вид, элемент и его связи остаются;
- `Shift+Delete` на фигуре удаляет элемент, все его виды, все связи с ним и
  диаграммы, которые ему принадлежат;
- `Delete` на связи снимает вид связи, сама связь остаётся в модели;
- `Shift+Delete` на связи удаляет связь из модели на всех диаграммах;
- одну связь можно показать на второй диаграмме (поставить оба элемента и
  провести связь заново — или открыть файл: вид ссылается на `relId`).

## Сообщения в Sequence

Порядок сообщения — его высота: номера считаются по `y`, а не хранятся.
Перетащите линию сообщения вверх-вниз — номера пересчитаются. Модель может
задать порядок явно (`seq: 10, 20, 30`): если он есть хотя бы у одного
сообщения диаграммы, он главный для всех, а сообщения без него получают
порядок по геометрии и идут после. Свободный конец (`from`/`to` = `null`) —
это найденное или потерянное сообщение: линия обрывается кружком, а не
пропадает из модели. Расстояние между
линиями жизни 80 px и между сообщениями 30 px — из записи
`_interactionDiagramLayoutOptions` самого проекта Visual Paradigm
(`myProject.vpp`), см. `MECHANICS.md` §12b. Ответ рисуется пунктиром, создание
и уничтожение — «create»/«destroy» с крестом.

## Файл модели `*.uml.json`

Канонический JSON: два одинаковых состояния дают побайтово одинаковый файл.

```json
{
  "schema": "uml-model/3",
  "id": "m1abcd",
  "name": "Пример — Интернет-магазин",
  "elements": [
    { "id": "e1", "kind": "class", "name": "Заказ",
      "attributes": [ { "vis": "private", "name": "номер", "type": "int" } ],
      "taggedValues": [ { "name": "table", "value": "orders" } ] }
  ],
  "relationships": [
    { "id": "r1", "kind": "association", "name": "оформляет",
      "from": "e2", "to": "e1", "fromMultiplicity": "1", "toMultiplicity": "0..*" }
  ],
  "diagrams": [
    { "id": "d1", "name": "Классы заказа", "kind": "class",
      "shapes": [ { "id": "s1", "elementId": "e1", "x": 600, "y": 60, "w": 190, "h": 170 } ],
      "links":  [ { "id": "l1", "relId": "r1",
                    "from": { "shapeId": "s2", "side": "right" },
                    "to":   { "shapeId": "s1", "side": "left" } } ] }
  ],
  "currentDiagramId": "d1"
}
```

Правила: ключи в одном порядке; умолчания опускаются (public, `t=0.5`,
прямой маршрут, пустые списки); координаты целые; id стабильны. Член —
четыре поля `{vis, name, type, default}`. Текстовые компартменты (`entry`,
`do`, `exit`, `extensionPoints`) — массив строк. У фрагмента — `operator`, у
шкалы времени — `timeline: [{state, from, to}]`.

**Семантика UML 2.5.1** (необязательные поля; файл без них открывается и
пересохраняется теми же байтами):

| Поле | Где | Что значит | На листе |
|---|---|---|---|
| `abstract` | элемент | абстрактный классификатор (§9.2.4) | имя курсивом |
| `isStatic` | член | статический член (§9.4.4) | имя подчёркнуто |
| `isDerived` | член | производный (§9.5.3) | `/` перед именем |
| `isID` | член | идентифицирующий атрибут | `{id}` после строки |
| `navigable` | связь: `none/from/to/both` | навигация ассоциации (§11.5.4) | открытая стрелка у конца |
| `fromAggregation`/`toAggregation` | связь: `none/shared/composite` | агрегация на конце (§11.5.3) | полый/залитый ромб |
| `fromRole`/`toRole` | связь | имя полюса | подпись у конца |
| `setId` + `generalizationSets[]` | связь + модель | набор обобщений (§9.7) | `{complete, disjoint}` |
| `trigger` / `guard` / `effect` | связь `transition` | событие, сторожевое условие, действие перехода (§14.5.10) | подпись `событие [условие] / действие` |
| `attachments[]` | элемент: `{id, name, mime, size, data}` | вложенный файл, base64 без префикса `data:` | секция «Вложения» в инспекторе |
| `waypoints` | вид связи: `[[x,y], …]` | изломы линии, поставленные человеком | ломаная через эти точки |
| `rounded` | вид связи: `off/small/large` | скругление углов (радиус 6/16) | дуги на изломах |
| `ownerId` | элемент | владелец: пакет, компонент, узел, класс (§12.2, §11.4.6) | вложенность в дереве модели |

Счётчик пробелов корпуса — `node tests/gaps.mjs`: каждая проба сама гоняет
поле через файл, поэтому «закрыто» здесь означает «пережило круг», а не
«записано в плане».

Умолчания: `abstract: false`, флаги членов `false`, `navigable: none`,
агрегация — как у вида связи (`aggregation` → `shared`, `composition` →
`composite`, иначе `none`). Поэтому нетронутые поля в файл не пишутся.

**Линия связи — любая форма.** У вида связи есть `waypoints`: точки перегиба
в мировых координатах, которые человек ставит сам. Двойной клик по линии
добавляет точку, перетаскивание двигает, Alt+клик или Delete убирает; пока
точек нет, работает автоматический маршрут (`routePoints`). Поле пишется
только когда непусто, поэтому файл без изломов пересохраняется побайтово.
Скругление углов — `rounded: small` или `large`, и это одно и то же число:
оригинал срезает угол на 7 px по обеим ногам и кладёт между срезами одну
кубику (`v/cct/es#a(D)+0x00b1`, MECHANICS §27d), второго размера у него нет.
Файл draw.io со своим `arcSize` сохраняет свою дугу `A`. Срез не длиннее
половины короткой ноги — иначе линия сложилась бы сама на себя. Путь строит
одна функция `pathD` (`src/model/geometry.js`) — и для листа, и для экспорта
SVG, поэтому картинка в файле не расходится с экраном. Стиль «Curve» — не
цепочка `Q`: маршрут идёт по натуральному кубическому сплайну через изломы и
рисуется 161 отсчётом, как `v/cct/ba#l()` (MECHANICS §27c). Подпись связи
садится на середину всей ломаной по длине пути, наконечники — по направлению
последнего нарисованного участка (у кривой — по касательной сплайна).

**Скачки на пересечениях.** У связи есть `lineJumps` — те же пять кодов, что
печатает диалог свойств оригинала: 0 «нет», 1 «дуга», 2 «разрыв», 3
«квадрат», 4 «как на диаграмме» (в файл не пишется — это и есть значение
реестра). Пятое значение разрешается в `lineJumps` самой диаграммы
(оригинал хранит его в строке `DIAGRAM`), затем в настройку `DefaultLineJumps`
= 0. Размер — `lineJumpsSize` 0…2, младший (0) по умолчанию. Геометрия взята
из значков панели `LineJumps*.png`: дуга 6×3 px, разрыв по 2.5 px от центра,
ступенька 6×4; шаг роста на код размера (2 px) — единственное число, которого
в оригинале нет, и оно помечено `decision` в `MECHANICS.md` §26. Скачок
принадлежит связи: линия без кода остаётся сплошной, даже если её пересекают.

**Миграция.** `uml-model/2` (связи лежали в диаграмме) и `uml-class-diagram/1`
(древнейший формат: одна диаграмма, члены строкой — его больше не пишут, но он
по-прежнему читается) открываются без потери данных: каждая старая связь
становится связью модели плюс видом; фигуры получают элементы; строки `id: int`
разбираются на поля. Сохранение всегда пишет `uml-model/3`.

Файл читается «с ремонтом»: неизвестный тип заменяется известным, битая связь
пропускается, отсутствующий id получает новый; поправки показываются
сообщением.

### Оборванный файл: правило восстановления

Обрыв (вкладку закрыли во время записи, кончилось место, оборвалась передача)
раньше давал исключение «Не корректный JSON» — модель терялась целиком. Теперь
файл восстанавливается, и правило одно, без подбора:

1. Один проход по тексту запоминает точки, где значение **закончилось**: после
   `}` и `]`, после закрывающей кавычки строки, после числа или слова
   (`true`/`false`/`null`). В каждой точке известно, какие `{`/`[` тогда были
   открыты. Скобки внутри строк не считаются: экранированная кавычка строку не
   закрывает.
2. Разбор упал — берём эти точки **с конца**: префикс до точки плюс
   недостающие закрывающие скобки в обратном порядке. Первый префикс, который
   разбирается, и есть восстановление: хвост отрезан, скобки закрыты.
3. Не вышло — внятная ошибка с позицией, строкой и столбцом, без стека.

Почему с конца и почему это «до последнего целого объекта»: обрыв почти всегда
в хвосте файла, а последняя целая точка — это конец последнего полностью
записанного значения. Обрыв внутри строки отрезает незаконченную пару
«ключ: значение» целиком — закрывающей кавычки в такой точке ещё нет, значит
точкой она не считается.

Каждое восстановление — строка в `repairs` («Файл обрезан на позиции N:
восстановлено X элементов, Y диаграмм»), а в интерфейсе — тост с числом
исправлений и кнопкой «Подробности»: список того, что именно починили. Ремонт
никогда не молчит.

Предел — **32 МБ** (`MAX_REPAIR_BYTES` в `src/io/json-repair.js`): восстановление
это второй проход по тексту и до 32 попыток разбора, на сотнях мегабайт это
минуты работы браузера ради файла, который человек всё равно не откроет. Файл
больше предела получает ответ «слишком большой» и не чинится. Предел —
решение этого приложения, а не число из Visual Paradigm.

Полный корректный файл читается ровно как раньше: `repairs` пуст, а
`tests/fixtures/old-v3.json` пересохраняется побайтово.

### Файл всего проекта

`Экспорт → Экспорт всего проекта…` пишет **один** `.json` — та же модель
`uml-model/3`, но с явной меткой `kind: 'project'`, чтобы при открытии было
видно, что это проект, а не одна диаграмма:

    { "schema": "uml-model/3", "kind": "project", "id", "name", "created",
      "revised", "stereotypes": [{ "id", "name" }], "elements": [...],
      "relationships": [...], "generalizationSets", "diagrams": [...],
      "currentDiagramId" }

В `stereotypes` идут **только использованные** записи профиля (id из
`stereotypeId` элементов и связей), а не все 304: профиль — поставляемые данные
и лежит рядом с программой, файл должен называть то, без чего его элементы
потеряют вид, а не носить стокилобайтную копию. Список выводится из модели,
поэтому при повторном экспорте он тот же.

Рядом скачивается по SVG на диаграмму, `<NN>-<slug>.svg` (`01-классы.svg`).
Это серия скачиваний, а не архив: зависимостей для ZIP нет и не будет. Браузер
может спросить разрешение на несколько файлов подряд — тост говорит об этом и
предлагает «Только JSON»: один файл, в котором лежит вся модель.

`Файл → Открыть` принимает такой файл и грузит **все** диаграммы (тост
сообщает, сколько). Круг «экспорт → открыть → экспорт» совпадает побайтово:
`revised` при экспорте не обновляется, потому что экспорт — чтение модели, а не
правка. Обычное `JSON (как на диске)` по-прежнему сохраняет одну текущую
диаграмму без метки проекта.

## Откуда числа

`mechanics.json` — лист чисел, `MECHANICS.md` — источник каждого: адрес класса
и смещение в байткоде (Java-путь: `Visual_Paradigm_CE_17.3/lib/vpplatform.jar`,
`lib01.jar`, `openapi.jar`) или запись, которую программа пишет сама (`*.vpp` —
SQLite, у фигуры читаемый DSL в `DIAGRAM_ELEMENT.DEFINITION`). `build.mjs`
превращает лист в `src/mechanics.generated.js`; код читает числа оттуда.

Значения без ключа в оригинале помечены `estimated` (высота головы линии
жизни 40 px, актёрской — 70 px, плюс два цвета значков видимости) — это
решения, а не измерения. Что именно искали и почему не нашли — `MECHANICS.md`
§22: ни один из четырёх чисел не встречается ни в одном jar, ни в одной
записи `*.vpp`.

Сетка — не одна константа: у программы два поля (`HorizontalGridSize` 10 и
`VerticalGridSize` 10), две галочки (`ShowGrid` выключена, `AlignToGrid`
включена упакованными настройками первого запуска) и переключатель
`ClassVisibilityStyle` (1 — значки, 0 — символы `+ - # ~`). Все четыре теперь
читаются из листа (`MECHANICS.md` §1b): `canvas.js` берёт `SNAP_X`/`SNAP_Y` и
`snapTo()`, `store.js` — начальное `showGrid`, `render.js` — вид значка
видимости, `geometry.js` — стиль связи. Значения совпадают с прежними
константами, поэтому картинка не изменилась, но менять их теперь можно в
`mechanics.json`, а не в коде.

Стрелки и пунктир — не решения: их числа прочитаны в байткоде
(`MECHANICS.md` §13). Голова — отдельный класс-художник на каждое имя
(`v/cco/b#e()` перечисляет 45 имён), длина и ширина задаются в конструкторе
(`HollowArrow1` 8×11, `Arrow1` 8×4, `SolidArrow1` 7×4, `HollowDiamond` 8×16),
а пунктир — таблица из 23 `BasicStroke` в `v/dal/au#<clinit>` (`Style2` = `8 5`).

## Проверки модели: стандарт, практика и правила проекта

Третья вкладка справа — «Проверки». Слоёв четыре, и они разные по природе, а не
по строгости. Числа о правилах здесь не повторяются: их печатает
`node tools/verify.mjs`, а разбор по пунктам — в
[`RULES-COVERAGE.md`](RULES-COVERAGE.md) и
[`../material/rules-coverage/report.md`](../material/rules-coverage/report.md).

- **По спецификации UML 2.5.1** — правила из
  `notation/rules/uml-2.5.1.json`; у каждого есть пункт, имя констрейнта и
  дословный текст. Часть правил записана невыразимыми с названным полем модели
  (`src/rules/coverage.js`).
  `element-isolated` не считает одинокой фигуру, развёрнутую на узле: в этой
  нотации вложенность геометрическая (пособие 5.1.6), поэтому правило смотрит
  на лист — прямоугольник в прямоугольник — и на `ownerId`, если владелец
  узел. Дорожка и пакет контейнером не считаются: это деление листа, а не
  отношение, и освобождать всё, что в них лежит, значило бы ослепить правило
  на диаграммах деятельности.
- **Практика моделирования** — советы из `notation/rules/practice.json`
  (`element-isolated`, `element-not-on-any-diagram`, `element-unnamed`,
  `relationship-duplicate`, `relationship-not-on-any-diagram`,
  `shape-isolated-on-diagram`, `name-not-clash`, `object-classifier-kind`,
  `action-behavior-is-activity`, `swimlane-represents-kind`,
  `interaction-use-refers-kind`, `lifeline-represents-classifier`,
  `message-signature-operation`). Все уровня «предупреждение», пункта UML у них
  нет вовсе — вместо него `rationale`: почему такую модель труднее читать.
  Раздел появляется, только когда в нём что-то есть.
- **Правила проекта** — соглашения команды, которые лежат в файле модели
  (`projectRules[]`), а не в поставке: «домен не зависит от интерфейса», «у
  публичного класса есть документация». У них нет ни пункта, ни `rationale`;
  условие пишется по белому списку полей и операторов без `eval`. Счётчик у
  слоя свой (`· проект N`), чтобы договорённость не выглядела нарушением
  стандарта. Разбор — [`RULES-COVERAGE.md`](RULES-COVERAGE.md) §5.
- **Геометрия листа** — четвёртый слой и единственный, который судит не модель,
  а картинку: налезают ли рамки друг на друга, влезает ли имя в свою фигуру, не
  станет ли текст нечитаемым при вписывании листа в окно. Модель при этом может
  быть безупречной по UML: связь верная, а на рисунке подпись поверх линии.
  Вложенность наложением не считается — компонент внутри своего класса по
  `ownerId` это норма (UML 2.5.1 §9.2), а не дефект раскладки. Счётчик слоя
  свой (`· раскладка N`) и в ошибки стандарта не входит, поэтому цифры `2 · 1` в
  статусбаре не сдвигаются от смены раскладки. Проверки взяты из archify 3.0.1
  (MIT) и лежат в `src/vendor/archify/`; мост — `geometry-adapter.mjs`.

Проверки — в `src/rules/` (по одной маленькой функции на `check`, реестр в
`registry.js`), панель — в `src/ui/checks.js`. Прогон идёт при открытии вкладки и
после каждой правки модели, кнопка «Проверить» повторяет его вручную.

- Строка замечания стандарта: уровень (ошибка / предупреждение), сообщение, что
  именно нашлось, подсказка и кнопка `п. 7.8.8.8`. Кнопка открывает дословный
  текст констрейнта, его OCL и страницу — приложение офлайн, поэтому цитата
  показывается в окне, а не уводит в интернет.
- Строка замечания практики: подпись «совет» и чип «практика» вместо пункта. Чип
  открывает `rationale` и строку «Это не требование стандарта UML, а совет по
  практике моделирования». Ссылки на пункт у такого замечания нет — и это
  принципиально: стандарт такого не требует.
- Строка правила проекта: чип «проект» и текст самого правила — сослаться
  можно только на файл модели.
- Строка геометрии листа: метка «вид» и чип «раскладка» вместо пункта. Чип
  открывает объяснение, что это свойство рисунка, а не нарушение UML; сама
  строка ведёт к виноватой фигуре так же, как остальные.
- Клик по строке выделяет виноватый объект: если его вид на другом листе,
  лист переключается.
- «Только ошибки» скрывает предупреждения и убирает слой практики целиком: у
  советов нет уровня «ошибка». Пустой результат — это результат: «Нарушений не
  найдено» и строка «Модель проверена по N из M правил UML 2.5.1 и по K
  правилам практики моделирования» (числа подставляет панель по загруженному
  набору).
- Внизу — свёрнутый список «Не проверяется: N правил — модель не выражает» с
  недостающим полем модели у каждого. Разбор — `RULES-COVERAGE.md` §3.
- В статусбаре — `проверки: 2 · 1` (ошибок · предупреждений), а когда есть
  советы — `проверки: 0 · 0 · советов 1`. Цифры слоя стандарта от появления
  советов не меняются; клик открывает вкладку.
- **Сбой проверки** — отдельный раздел «Проверки, которые не выполнились»:
  правило, бросившее исключение, отключается до конца прогона, остальные
  отрабатывают, а сбой назван один раз. У такой строки нет ни кнопки пункта, ни
  перехода к объекту (винить некого), в счётчик нарушений она не входит, но и не
  прячется: статусбар получает хвост `· не проверено 1`, бейдж считает сбои, а
  «все чисто» при упавшем правиле не пишется.

Проверки ничего не блокируют: движок только читает модель, поэтому файл с
нарушениями сохраняется и открывается как обычный. Правило без функции в
реестре, правило практики с полем `source` и правило практики без `rationale` —
ошибка загрузки набора, а не тихий пропуск; она видна в панели и статусбаре
(`проверки: —`), а модельер продолжает работать.

Границы слоя практики откалиброваны по корпусу: наивное «элемент без связей»
даёт на 48 учебных моделях 137 срабатываний, после исключения видов, которым
связи не положены (`STANDALONE`), остаётся 96. Подробности — `RULES-COVERAGE.md`.

## Курс: пособие внутри инструмента

Учебник «Упражнения по UML-моделированию системы регистрации на курсы» (ВМК
МГУ, Малышко В. В., Visual Paradigm 16.3) целиком внутри редактора. 3 главы,
20 упражнений. Открывается кнопкой «Курс» в шапке (глиф `ui-course` —
строки списка) и живёт **отдельным режимом** над листом
(`#course-mode` внутри `#work`), а не вкладкой панели. Это разные категории:
курс — «что мне делать дальше», инспектор — «что у выделенного»; в одной
вкладке курс отнимал у человека свойства ровно тогда, когда тот рисовал по
уроку. Вход в курс не сужает лист (при 1440×900 он так и остаётся 856 px) и
не скрывает инспектор; выход — «✕ Закрыть» в шапке режима, Esc и «К листу»,
а масштаб и выделение после выхода те же. Разбор решения —
[`docs/research/UX-COURSE-LIBRARY.md`](../docs/research/UX-COURSE-LIBRARY.md).

**Нумерация — с 1.** В бумажном пособии главы начинаются с 3 (1–2 вводные), и
курс, честно повторявший номера, выглядел оборванным. В интерфейсе главы идут
1, 2, 3, упражнения — 1.1, 1.2, 2.1 …, а номер пособия остаётся в данных
(поле `number`) и показан мелким «глава 3 пособия» / «в пособии 3.1». Id и
имена файлов не меняются: `ex-3.1` остаётся `ex-3.1`.

Текст в курсе — **адаптированный**: авторский текст предметной области
сохранён дословно, а действия описаны нашими средствами — палитрой, деревом
модели, панелью «Свойства» и командой `Ctrl+K`, а не меню Visual Paradigm.
Где операции у нас нет, стоит пометка `> ⚠ У нас нет: <операция>. <что делать
вместо>`: она называет пробел, а не притворяется, что действие выполнимо.
Адаптацию собирает `material/tutorial-adaptation/build.mjs` из
`docs/uml-tutorial.md` (исходник не правится), а таблица соответствия операций
и разбор пробелов лежат в [`docs/research/TUTORIAL-ADAPTATION.md`](../docs/research/TUTORIAL-ADAPTATION.md).
Тест `types.mjs` следит, чтобы меню Visual Paradigm в курсе не появлялось вне
таких пометок.

Данные готовит `tools/build-course.mjs` (Node, только stdlib):

    node tools/build-course.mjs           # собрать course/
    node tools/build-course.mjs --check   # сверить с пособием, ничего не писать

- `course/index.json` — главы → упражнения: номер, заголовок, тип диаграммы,
  путь к тексту, рисунки (номер, подпись, наша модель, снимок пособия) и поле
  `missing`, если модели корпуса нет.
- `course/text/<id>.md` — текст упражнения. Строка `[Рис. 3.1.2](…)` и подпись
  под ней стали меткой `[[fig:3102|Рис. 3.1.2]]`, а упоминания в прозе («на
  рисунке 3.1.2», «см. рис. 4.1.3») — такими же метками: по ним урок
  прокручивает к нужному рисунку.
- `course/figures/<номер>.uml.json` — побайтовая копия модели корпуса
  (`material/corpus-layout/`), чтобы приложение оставалось самодостаточным.

Повторный прогон даёт побайтово те же файлы (порядок — из пособия и манифеста,
JSON с фиксированным отступом, лишние файлы прошлого прогона удаляются); это
проверяет `tests/types.mjs`.

Что видно в интерфейсе:

- Режим «Курс»: шапка режима («🎓 Курс · глава N «…» · урок N.M · M / 20» и
  кнопка «✕ Закрыть»), слева — плотный список в 24 px строку (главы, под ними
  упражнения с галочкой «пройдено», номером и названием), справа — урок.
  Заголовок главы открывает её вступление и список упражнений.
- Урок — заголовок, тип, счётчик рисунков, номер пособия мелким, галочка, текст
  в 14/20, рисунки над текстом (урок длиной в две-три тысячи пикселей, и
  рисунок в его конце был бы за горизонтом; область рисунков ограничена 46vh и
  прокручивается сама, чтобы текст оставался на экране).
- **Две картинки рядом.** Если у рисунка есть и модель корпуса, и снимок
  пособия, они стоят бок о бок: слева наш рендер с «Открыть как модель»,
  справа снимок Visual Paradigm (`reference/vp163/<номер>.png`) с «Оригинал в
  пособии». Сравнивать надо бок о бок, а не по очереди. Когда места на две не
  хватает (узкое окно), остаётся **переключатель «Наши модели / Из пособия»** в
  шапке режима — на весь курс; выбор помнится в `localStorage`
  (`uml-course.figures`, ключ отдельный от модели) и в файл не уезжает.
- **Наша картинка** — `exportSvgString` из `src/ui/render.js` по модели
  корпуса, то есть ровно то, что человек увидит, открыв модель. Снимок Visual
  Paradigm — отдельная ссылка «Оригинал в пособии» (`reference/vp163/…png`).
  Стили экспорта при вставке получают префикс блока: `<style>` внутри
  вставленного `<svg>` иначе действовал бы на весь документ.
- **«Открыть как модель»** открывает копию эталона: документ без имени файла
  (`fileName = null`), «Сохранить» спросит имя, правки не трогают корпус. Если
  в текущей модели есть несохранённые изменения, приложение спрашивает так же,
  как при открытии файла. Кнопка стоит **у каждого рисунка** (и у каждого — своя
  ссылка «Оригинал в пособии»); в подвале урока осталась одна «К листу» —
  дублирующие кнопки владелец попросил убрать. Курс при этом закрывается: лист
  лежит под слоем режима, и открытая копия иначе осталась бы невидимой; место
  в курсе помнится, возврат — одно нажатие «Курс».
- **Прогресс** — галочка «пройдено» в localStorage (`uml-course.done`, общая
  для всех моделей) и в поле `courseDone` модели: отметки уезжают вместе с
  файлом. Поле пишется только когда непусто, поэтому старые файлы
  пересохраняются побайтово. Выбранное упражнение тоже запоминается
  (`uml-course.selected`) — возврат в режим «Курс» открывает тот же урок.

Чего нет и почему: у упражнения 3.3 («Описания вариантов использования») в
пособии нет ни одного рисунка — только текст, поэтому в `index.json` у него
`missing`, кнопок у рисунков нет вовсе, а в подвале урока остаётся одна
«К листу». Модели
рисунков, помеченных в манифесте как невоспроизводимые, остаются в уроке
(картинка рисуется), но об этом честно говорит поле `reproducible`.

Кнопка «Библиотека» в шапке (глиф раскрытой книги; и команда `Ctrl+K` →

## Сборка: две копии, `node build.mjs`

Приложение собирается **само из себя**: это ES-модули и вендоренный `ui-kit`,
бандлить нечего, npm не нужен. Но копий на диске две, и они играют разные роли.

| Копия | Кто её открывает | Чем отличается |
|---|---|---|
| `src/` — исходники, рядом лежат `index.html`, `profile/`, `notation/`, `course/`, `reference/` | `serve.sh` из папки `app/`, браузер человека, `tests/*.mjs` | рабочая копия; правки делают здесь |
| `dist/` — та же папка целиком, скопированная `build.mjs` | проверщик (ищет готовый сайт в `dist/`, `build/` или `out/`) и `dist/serve.sh` | снимок; правки сюда не пишут |

    node build.mjs        # = npm run build; пересобирает dist/ и mechanics.generated.js

Что делает `build.mjs`:

1. **`mechanics.json` → `src/mechanics.generated.js`.** Лист чисел — источник,
   код читает числа только оттуда (`SHEET_KEYS` связывает имя строки с именем
   константы; строка без ключа — ошибка сборки). Меняете число в листе —
   пересоберите, иначе код продолжит работать со старым.
2. **Копия сайта в `dist/`** — `SITE`: `index.html`, `src`, `ui-kit`, `material`,
   `notation`, `profile`, `course`, `reference`, `serve.sh`, `Build`, `README.md`,
   `CREDITS.md`, `MECHANICS.md`, `mechanics.json`. `package.json` и сам
   `build.mjs` не копируются: это обвязка сборки, а не сайт.
3. **Самопроверка, без которой сборка падает с кодом 1:** `dist/index.html`
   ссылается на `src/main.js`; в `dist/material/stereotypes.xml` 428 записей
   (вход профиля); в `dist/profile/stereotypes.json` 304 стереотипа (то, что
   читает приложение); в курсе 20 упражнений и у каждого есть текст;
   `dist/Build/uml-modeler` на месте (иначе не заработает
   `serve.sh --screenshot`).

После правок в `src/` сверка обязательна — иначе человек увидит старую копию:

    node build.mjs && diff -r src dist/src && md5sum src/**/*.js | md5sum   # и то же для dist/src

Любая правка только в `docs/`, `README.md` или `mechanics.json` тоже требует
сборки, если `mechanics.json` менялся: `mechanics.generated.js` лежит в `src/`
и едет в `dist/` вместе с ним.

## Иконки

Набор рисуется в VectorCraft и лежит в `src/brand/icons/`: 51 фигура на сетке
24 плюс её пара на 16 для дерева, 27 связей и 16 служебных значков интерфейса
(`ui-*`). Каждый вид нотации называет свой файл полями `icon` и `treeIcon` в
`notation/uml.json` — раньше 36 файлов обслуживали 78 видов, и девять разных
фигур выглядели как «класс».

Перерисовать набор целиком:

    python3 tools/make-icons.py --out /tmp/icons   # посмотреть, потом скопировать
    python3 tools/make-icons.py --master           # SVG в src/brand/icons + исходник

`--master` кладёт `tools/icons.vectorcraft` — один документ VectorCraft, где
каждая иконка лежит на своей монтажной области. Его открывают, чтобы подвинуть
узел или поправить обводку руками; SVG при этом перерисовываются скриптом, а не
правятся по одному.

Скрипт создаёт по документу на иконку, ставит обводку 1.5 (1.25 на 16) с
круглыми концами и пунктиром без круглых концов, экспортирует SVG и заменяет
`#000000` на `currentColor` — поэтому значок принимает цвет кнопки.

## Заглушки и отличия от оригинала

- Печать не сделана.
- Экспорт PNG есть (в своём размере и ×2), но растр получается через
  canvas из того же SVG: шрифт в нём — Arial по имени, не встроенный,
  поэтому на машине без Arial текст заменится похожим.
- Формы фигур приближены к UML и записям `.vpp`, но не пиксель-в-пиксель:
  например, голова линии жизни — решение, а не измерение.
- Иконки инструментов — свой глиф у каждого вида (24/16 px), см. «Иконки» ниже.
- Timing-диаграмма хранит состояния в процентах окна наблюдения; оригинал
  хранит строки состояний по каждой линии — форма беднее, но редактируемая.
