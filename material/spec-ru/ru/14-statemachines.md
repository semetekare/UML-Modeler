# 14 Машины состояний

> **UML 2.5.1** (formal/2017-12-05) · Раздел 14 · печатные стр. 305–372 · PDF стр. 347–414

## 14.1 Краткое описание

Пакет «Машины состояний» определяет набор понятий для моделирования дискретных событийно-управляемых поведений с помощью формализма конечных автоматов. Помимо выражения поведения частей системы (например, поведения экземпляров классификатора), машины состояний могут также использоваться для выражения допустимых последовательностей взаимодействия — так называемых протоколов — для частей системы. Эти два вида машин состояний называются соответственно поведенческими машинами состояний и протокольными машинами состояний. Конкретная форма конечных автоматов, используемая в UML, основана на объектно-ориентированном варианте формализма схем состояний Дэвида Харела. (Однако читателям, знакомым с этим формализмом, следует учитывать, что существует небольшое число семантических отличий, отличающих версию UML от оригинала.)

## 14.2 Поведенческие машины состояний

### 14.2.1 Краткое описание

Поведенческие машины состояний могут использоваться для задания любого из следующего:

- classifierBehavior активного класса;

- ownedBehavior классификатора с поведением, не являющегося classifierBehavior этого классификатора;

- отдельного поведения, то есть такого, которое не имеет соответствующего классификатора с поведением;

- метода, соответствующего поведенческой характеристике (то есть операции или приёму).

### 14.2.3 Семантика

#### 14.2.3.1 Машина состояний

Поведенческая машина состояний состоит из одного или нескольких регионов, каждый из которых содержит граф (возможно, иерархический) из набора вершин, соединённых дугами, представляющими переходы. Выполнение машины состояний запускается подходящими вхождениями событий. Конкретное выполнение машины состояний представляется набором допустимых прохождений путей по графам одного или нескольких регионов, запускаемых диспетчеризацией вхождения события, соответствующего активным триггерам в этих графах. Правила сопоставления триггеров описаны ниже. В ходе такого прохождения экземпляр машины состояний может выполнить потенциально сложную последовательность поведений, связанных с конкретными элементами проходимых графов (эффекты переходов, поведения при входе и выходе состояния и т. д.).

Если машина состояний имеет контекст вида «классификатор с поведением», то этот классификатор определяет, какие триггеры сигналов и событий вызова применимы к этой машине состояний и какие характеристики доступны поведениям, принадлежащим машине состояний. Триггеры сигналов и триггеры событий вызова для машины состояний определяются соответственно по приёмам и операциям этого классификатора. Эти характеристики могут использоваться для определения триггеров событий-сообщений машины состояний. Если машина состояний не имеет контекста «классификатор с поведением» (то есть является отдельным поведением), то её триггеры не обязаны быть привязаны к каким-либо приёмам или операциям некоторого классификатора. Например, такая машина состояний могла бы быть определена как

шаблон, триггеры которого заданы как параметры шаблона. Затем такая машина состояний может повторно использоваться с разными контекстными классификаторами путём связывания подходящих триггеров событий вызова или сигналов с этими параметрами шаблона.

В ситуациях, когда машина состояний задаёт метод поведенческой характеристики (операции или приёма), параметры машины состояний должны соответствовать параметрам этой поведенческой характеристики (см. подпункт 13.2.3). Именно так выполнение машины состояний получает доступ к параметрам поведенческой характеристики. В остальных случаях способ, которым выполняющийся экземпляр машины состояний получает доступ к диспетчеризованному вхождению события и связанным с ним данным, не определён (см. пункт 13).

По определению, вызовы выполнений машины состояний приводят к запускаемым эффектам (см. подпункт 13.3.3) и, следовательно, с таким выполнением связан пул событий. Пул событий выполнения машины состояний принадлежит либо объекту её контекстного классификатора, либо, если машина состояний задаёт метод поведенческой характеристики, экземпляру классификатора, которому принадлежит эта поведенческая характеристика.

В силу своей событийно-управляемой природы выполнение машины состояний находится либо в переходе, либо в состоянии, чередуя эти два положения. Оно находится в переходе, когда диспетчеризуется событие, соответствующее по меньшей мере одному из связанных триггеров. Находясь в переходе, оно может выполнять ряд поведений, связанных с проходимыми путями.

ПРИМЕЧАНИЕ. Выполнение машины состояний может выполнять поведения даже тогда, когда оно уже установилось в устойчивой конфигурации состояний, — в случаях, когда с его активной конфигурацией состояний связаны поведения doActivity.

#### 14.2.3.2 Регионы

Регион обозначает фрагмент поведения, который может выполняться параллельно со своими ортогональными регионами. Два или более региона ортогональны друг другу, если они принадлежат одному и тому же состоянию или, на самом верхнем уровне, одной и той же машине состояний. Регион становится активным (то есть начинает выполняться), когда входит в него владеющее состояние или, если он принадлежит непосредственно машине состояний (то есть является регионом верхнего уровня), когда начинает выполняться владеющая машина состояний. Каждый регион владеет набором вершин и переходов, определяющих поведенческий поток внутри этого региона. Он может иметь собственное начальное псевдосостояние и собственное конечное состояние. Активация региона по умолчанию происходит, если в регион входят неявно, то есть не через входящий переход, завершающийся на одной из его составных вершин (например, на состоянии или псевдосостоянии истории), а либо

- через (локальный или внешний) переход, завершающийся на содержащем состоянии, либо

- в случае региона верхнего уровня — когда начинает выполняться машина состояний.

Активация по умолчанию означает, что выполнение начинается с перехода, исходящего из начального псевдосостояния региона, если оно определено. Однако если в регионе нет начального псевдосостояния, конкретный подход не определён. Один из возможных подходов — считать модель неопределённой. Другой — считать, что регион остаётся неактивным, хотя содержащее его состояние активно. Иначе говоря, содержащее составное состояние трактуется как простое (листовое) состояние.

Наоборот, явная активация происходит, когда в регион входят переходом, завершающимся на одной из содержащихся в регионе вершин. Когда один регион ортогонального состояния активируется явно, это приводит к активации по умолчанию всех его ортогональных регионов, если только в эти регионы тоже не входят явно (несколько ортогональных регионов могут быть явно активированы параллельно переходами, исходящими из одного псевдосостояния разделения).

#### 14.2.3.3 Вершины

Vertex — абстрактный класс, отражающий общие характеристики различных конкретных видов узлов графа машины состояний (состояний, псевдосостояний и ссылок на точки соединения). За некоторыми исключениями, описанными ниже, вершина может быть источником и/или целью любого числа переходов. Семантика вершины зависит от конкретного вида узла, который она представляет. В целом псевдосостояния и ссылки на точки соединения транзитны в том смысле, что выполнение составного перехода просто проходит через них, приходя по входящему переходу и уходя по исходящему без остановки. Состояние же и конечное состояние представляют устойчивые вершины, так что, когда выполнение машины состояний входит в них, оно остаётся в них, пока не произойдёт некоторое событие, запускающее переход, который переводит его в другое состояние, либо пока машина состояний не будет завершена.

#### 14.2.3.4 Состояния

Состояние моделирует ситуацию в выполнении поведения машины состояний, в течение которой выполняется некоторое инвариантное условие. В большинстве случаев это условие не задано явно, а подразумевается — обычно через имя, связанное с состоянием. Например, на рисунке 14.36, моделирующем поведение телефонного аппарата, состояния “Idle” и “Active” представляют ситуации, в которых телефон соответственно не используется и используется. Этот пример также показывает, что состояние не обязательно должно представлять полностью статичную ситуацию, поскольку в контексте состояния “Active” явно происходит некоторая подробная деятельность. Однако на протяжении всей этой деятельности телефон остаётся используемым (то есть «активным»).

##### 14.2.3.4.1 Виды состояний

Различают следующие виды состояний:

- простое состояние (isSimple = true);

- составное состояние (isComposite = true);

- состояние-подавтомат (isSubmachineState = true).

Простое состояние не имеет внутренних вершин и переходов. Составное состояние содержит по меньшей мере один регион, а состояние-подавтомат ссылается на целую машину состояний, которая концептуально считается «вложенной» в состояние. Составное состояние может быть либо простым составным состоянием ровно с одним регионом, либо ортогональным состоянием с несколькими регионами (isOrthogonal = true). Например, на рисунке 14.9 состояние “CourseAttempt” — пример составного состояния с одним регионом, а состояние “Studying” — составное состояние, содержащее три региона.

Любое состояние, заключённое в регионе составного состояния, называется подсостоянием этого составного состояния. Оно называется непосредственным подсостоянием, если не содержится ни в каком другом состоянии; иначе оно называется косвенным подсостоянием.

##### 14.2.3.4.2 Конфигурации состояний

В общем случае машина состояний может иметь несколько регионов, каждый из которых может содержать собственные состояния, некоторые из которых могут быть составными со своими несколькими регионами, и т. д. Следовательно, конкретное «состояние» выполняющегося экземпляра машины состояний представляется одной или несколькими иерархиями состояний, начиная с самых верхних регионов машины состояний и спускаясь по иерархии композиции к простым, или листовым, состояниям. Аналогично можно говорить о такой иерархии подсостояний внутри составного состояния. Эта сложная иерархия состояний называется конфигурацией состояний (состояния или машины состояний). Например, одна допустимая конфигурация состояний для выполнения машины состояний, изображённой на рисунке 14.9, такова: <CourseAttempt - Studying – (Studying::Lab2, Studying::TermProject, Studying::FinalTest)>. Выполняющийся экземпляр машины состояний может находиться одновременно ровно в одной конфигурации состояний, которая называется его активной конфигурацией состояний. Выполнение машины состояний представляется переходами от одной активной конфигурации состояний к другой в ответ на вхождения событий, соответствующие триггерам машины состояний.

Состояние называется активным, если оно входит в активную конфигурацию состояний. Конфигурация состояний называется устойчивой, когда:

- из этой конфигурации состояний больше не разрешён ни один переход и

- все поведения при входе этой конфигурации, если они есть, завершились (но не обязательно поведения doActivity этой конфигурации, которые, если определены, могут продолжать выполняться).

После того как она создана и завершила свой начальный переход, машина состояний всегда «находится» в некоторой конфигурации состояний. Однако поскольку состояния могут быть иерархическими и поскольку с переходами и состояниями могут быть связаны поведения, «вход» в иерархическую конфигурацию состояний представляет собой динамический процесс, завершающийся только после достижения устойчивой конфигурации состояний (как определено выше). Это создаёт некоторую потенциальную неоднозначность в том, когда именно машина состояний «находится» в конкретном состоянии внутри конфигурации состояний. Правила того, когда машина состояний считается «находящейся» в состоянии и когда считается, что она его «покинула», описаны ниже в разделах «Вход в состояние» и «Выход из состояния».

Конфигурация считается устойчивой, даже если в пуле событий этой машины состояний ожидают отложенные, завершающие или любые другие виды вхождений событий.

##### 14.2.3.4.3 Поведения при входе, при выходе и doActivity

Состояние может иметь связанное поведение при входе. Это поведение, если оно определено, выполняется всякий раз, когда в состояние входят через внешний переход. Кроме того, состояние может иметь связанное поведение при выходе, которое, если определено, выполняется всякий раз, когда состояние покидают.

Состояние может также иметь связанное поведение doActivity. Это поведение начинает выполняться при входе в состояние (но только после завершения поведения при входе) и выполняется параллельно с любыми другими поведениями, связанными с состоянием, пока:

- оно не завершится (в этом случае порождается событие завершения) или

- состояние не будет покинуто, и в этом случае выполнение поведения doActivity прерывается.

На выполнение поведения doActivity состояния не влияет срабатывание внутреннего перехода этого состояния.

##### 14.2.3.4.4 История состояния

Понятие истории состояния введено Дэвидом Харелом в исходном формализме схем состояний. Это удобное понятие, связанное с регионами составных состояний: регион хранит сведения о том, в какой конфигурации состояний он находился при последнем выходе из него. Это позволяет легко вернуться в ту же конфигурацию состояний, если требуется, при следующей активации региона (например, после возврата из обработки прерывания) или если есть локальный переход, возвращающийся к его истории. Это достигается просто завершением перехода на нужном виде псевдосостояния истории внутри региона. Преимущество этой возможности в том, что она избавляет пользователей от необходимости явно отслеживать историю в случаях, когда такое поведение желательно, что может существенно упростить модели машин состояний.

Предусмотрено два вида псевдосостояний истории. Глубокая история (deepHistory) представляет полную конфигурацию состояний при последнем посещении содержащего региона. Эффект тот же, как если бы переход, завершающийся на псевдосостоянии deepHistory, завершался вместо этого на самом внутреннем состоянии сохранённой конфигурации состояний, включая выполнение всех поведений при входе, встречающихся по пути. Мелкая история (shallowHistory) представляет возврат только к самому верхнему подсостоянию последней конфигурации состояний, в которое входят по правилу входа по умолчанию.

В случаях, когда переход завершается на псевдосостоянии истории, а состояние ранее не входилось (то есть предыдущей истории нет) или достигло своего конечного состояния, есть возможность принудительно перейти в конкретное подсостояние, используя механизм истории по умолчанию. Это переход, который исходит из псевдосостояния истории и завершается на конкретной вершине (состоянии истории по умолчанию) региона, содержащего псевдосостояние истории. Этот переход выполняется, только если выполнение приводит к псевдосостоянию истории, а состояние никогда ранее не было активным. Иначе выполняется соответствующий вход в регион по истории (см. выше). Если переход истории по умолчанию не определён, выполняется стандартный вход в регион по умолчанию, как объяснено ниже. Отложенные события

Состояние может задавать набор видов событий, которые могут быть отложены в этом состоянии. Это означает, что вхождения событий этих видов не будут диспетчеризоваться, пока это состояние остаётся активным. Вместо этого такие вхождения событий остаются в пуле событий, пока:

- не будет достигнута конфигурация состояний, в которой эти виды событий больше не откладываются, или

- отложенный вид события не будет использован явно в триггере перехода, источником которого является откладывающее состояние (то есть своего рода вариант переопределения).

Событие может откладываться составным состоянием или состоянием-подавтоматом, и в этом случае оно остаётся отложенным, пока составное состояние остаётся в активной конфигурации.

##### 14.2.3.4.5 Вход в состояние

Семантика входа в состояние зависит от вида состояния и способа, которым в него входят. Однако во всех случаях поведение при входе состояния выполняется (если определено) при входе, но только после завершения любого поведения-эффекта, связанного

с входящим переходом. Кроме того, если для состояния определено поведение doActivity, это поведение начинает выполняться сразу после выполнения поведения при входе. Оно выполняется параллельно с любыми последующими поведениями, связанными со входом в состояние, например с поведениями при входе подсостояний, в которые входят в рамках того же составного перехода.

Приведённое выше описание полностью охватывает случай простых состояний. Для составных состояний с единственным регионом существуют следующие варианты:

- Вход по умолчанию: эта ситуация возникает, когда составное состояние является непосредственной целью перехода (графически это обозначается входящим переходом, завершающимся на внешней границе составного состояния). После выполнения поведения при входе и порождения возможного выполнения поведения doActivity, если определено начальное псевдосостояние, вход в состояние продолжается из этой вершины по её исходящему переходу (известному как переход по умолчанию данного состояния). Если начальное псевдосостояние не определено, единый подход не определён. Одна из альтернатив — считать такую модель некорректно построенной. Вторая альтернатива — трактовать составное состояние как простое, завершая прохождение на этом состоянии, несмотря на его внутренние части.

- Явный вход: если входящий переход или его продолжения завершаются на непосредственно содержащемся подсостоянии составного состояния, то это подсостояние становится активным, и его поведение при входе выполняется после выполнения поведения при входе содержащего составного состояния. Это правило применяется рекурсивно, если переход завершается на косвенном (глубоко вложенном) подсостоянии.

- Вход по мелкой истории: если входящий переход завершается на псевдосостоянии shallowHistory региона составного состояния, активным подсостоянием становится то подсостояние, которое было активным последним перед этим входом, если только: o    это последнее активное подсостояние не является конечным состоянием, или o    это не первый вход в данное состояние. o    В двух последних случаях, если из псевдосостояния shallowHistory определён переход по мелкой истории по умолчанию, он будет выполнен. Иначе применяется вход в состояние по умолчанию.

- Вход по глубокой истории: правило для этого случая то же, что и для мелкой истории, за исключением того, что целевое псевдосостояние имеет вид deepHistory, а правило применяется рекурсивно ко всем уровням активной конфигурации состояний ниже данного.

- Вход через точку входа: если переход входит в составное состояние через псевдосостояние entryPoint, то выполняется поведение-эффект, связанное с исходящим переходом, который начинается в точке входа и проникает в состояние (но после того, как выполнено поведение при входе составного состояния).

Если составное состояние является также ортогональным состоянием с несколькими регионами, в каждый из его регионов также входят — либо по умолчанию, либо явно. Если переход завершается на границе составного состояния (то есть не входя в состояние), то во все регионы входят по правилу входа по умолчанию, приведённому выше. Если переход явно входит в один или несколько регионов (в случае разделения), в эти регионы входят явно, а в остальные — по умолчанию.

Независимо от того, как входят в состояние, машина состояний считается «находящейся» в этом состоянии ещё до того, как начнут выполняться какое-либо поведение при входе или поведение-эффект (если определено) этого состояния.

##### 14.2.3.4.6 Выход из состояния

При выходе из состояния — независимо от того, простое оно или составное, — последним шагом выхода после завершения всех других поведений, связанных с выходом, является выполнение поведения при выходе этого состояния. Если у состояния есть поведение doActivity, которое всё ещё выполняется при выходе из состояния, это поведение прерывается до начала выполнения поведения при выходе.

При выходе из составного состояния выход начинается с самого внутреннего состояния в активной конфигурации состояний. Это означает, что поведения при выходе выполняются последовательно, начиная с самого внутреннего активного состояния. Если выход происходит через псевдосостояние exitPoint, то поведение при выходе состояния выполняется после поведения-эффекта перехода, завершающегося на точке выхода.

При выходе из ортогонального состояния выполняется выход из каждого его региона. После этого выполняется поведение при выходе состояния.

Независимо от того, как выходят из состояния, машина состояний считается «покинувшей» это состояние только после того, как завершилось выполнение поведения при выходе (если оно определено) этого состояния. Инкапсулированные составные состояния

В некоторых ситуациях моделирования полезно инкапсулировать составное состояние, не позволяя переходам проникать непосредственно в состояние и завершаться на одной из его внутренних вершин. (Один из распространённых случаев — когда внутреннее устройство состояния в абстрактном классификаторе должно задаваться по-разному в разных уточнениях подтипов этого абстрактного классификатора.) Несмотря на инкапсуляцию, часто необходимо связать внутренние элементы составного состояния с входящими и исходящими переходами. Это делается посредством точек входа и выхода, которые реализуются псевдосостояниями entryPoint и exitPoint.

Точки входа представляют точки завершения (источники) для входящих переходов и точки начала (цели) для переходов, которые завершаются на некоторой внутренней вершине составного состояния. Фактически последнее является продолжением внешнего входящего перехода, с той оговоркой, что выполнение поведения при входе составного состояния (если оно определено) происходит между поведением-эффектом входящего перехода и поведением-эффектом исходящего перехода. Если внутри составного состояния нет исходящего перехода, то входящий переход просто выполняет вход в состояние по умолчанию.

Точки выхода — обратное точкам входа. То есть переходы, исходящие из вершины внутри составного состояния, могут завершаться на точке выхода. В корректно построенной модели такой переход должен иметь соответствующий внешний переход, исходящий из той же точки выхода и представляющий продолжение завершающего перехода. Если у составного состояния определено поведение при выходе, оно выполняется после любого поведения-эффекта входящего внутреннего перехода и до любого поведения-эффекта исходящего внешнего перехода.

##### 14.2.3.4.7 Состояния-подавтоматы и подавтоматы

Подавтоматы — средство, позволяющее многократно использовать одну спецификацию машины состояний. Они подобны инкапсулированным составным состояниям тем, что должны связывать входящие и исходящие переходы со своими внутренними вершинами. Однако если инкапсулированные составные состояния и их внутреннее устройство содержатся в машине состояний, в которой они определены, то подавтоматы, подобно макросам языков программирования, представляют собой отдельные спецификации поведения, которые могут быть определены в ином контексте, чем тот, где они используются (вызываются). Следовательно, они требуют более сложного связывания. Это достигается через понятие состояния-подавтомата (то есть состояний с isSubmachineState = true), которые представляют ссылки на соответствующие машины состояний-подавтоматов. Понятие ссылки на точку соединения (ConnectionPointReference) предоставлено для поддержки связывания между состоянием-подавтоматом и указанной машиной состояний. Ссылка на точку соединения представляет точку на состоянии-подавтомате, в которой переход либо завершается, либо начинается. То есть они служат целями для входящих переходов к состояниям-подавтоматам и источниками для исходящих переходов от состояний-подавтоматов. Каждой ссылке на точку соединения соответствует точка входа или выхода в указанной машине состояний-подавтомате. Это обеспечивает необходимый механизм связывания между вызовом подавтомата и его спецификацией.

Состояние-подавтомат подразумевает макроподобную вставку спецификации соответствующей машины состояний-подавтомата. Поэтому оно семантически эквивалентно составному состоянию. Регионы машины состояний-подавтомата — это регионы составного состояния. Поведения при входе, при выходе и поведения-эффекты и внутренние переходы определяются как содержащиеся в состоянии-подавтомате.

ПРИМЕЧАНИЕ. Каждое состояние-подавтомат представляет отдельное создание экземпляра подавтомата, даже если два или более состояний-подавтоматов ссылаются на один и тот же подавтомат.

В машину состояний-подавтомат можно войти через её начальное (initial) псевдосостояние или через любую из её точек входа (то есть это может означать вход в неортогональное или ортогональное составное состояние с регионами). Вход через начальное псевдосостояние имеет тот же смысл, что и для обычных составных состояний. Точка входа эквивалентна псевдосостоянию соединения (разделения — в случаях, когда составное состояние ортогонально): вход через точку входа означает, что выполняется поведение при входе составного состояния, а затем — переход от точки входа к целевой вершине внутри составного состояния. Любые сторожа, связанные с этими переходами из точки входа, должны вычисляться как истинные, чтобы спецификация была корректно построенной.

Аналогично, из машины состояний-подавтомата можно выйти в результате:

- достижения её конечного состояния,

- запуска группового перехода, исходящего из состояния-подавтомата, или

- через любую из её точек выхода.

Выход через конечное состояние или групповым переходом имеет тот же смысл, что и для обычных составных состояний.

#### 14.2.3.5 Ссылка на точку соединения

Как отмечено выше, ссылка на точку соединения представляет использование (в составе состояния-подавтомата) точки входа/выхода, определённой в машине состояний, на которую ссылается состояние-подавтомат. Ссылки на точки соединения состояния-подавтомата могут использоваться как источники/цели переходов. Они представляют входы в машину состояний-подавтомат, на которую ссылается состояние-подавтомат, или выходы из неё.

Ссылки на точки соединения являются источниками/целями переходов, означающих выходы из машины состояний-подавтомата или входы в неё.

Ссылка на точку соединения точки входа как цель перехода означает, что целью перехода является псевдосостояние entryPoint, определённое в подавтомате состояния-подавтомата. В результате в регионы машины состояний-подавтомата входят через соответствующие псевдосостояния entryPoint.

Ссылка на точку соединения точки выхода как источник перехода означает, что источником перехода является псевдосостояние точки выхода, определённое в подавтомате того состояния-подавтомата, у которого определена эта ссылка на точку соединения. Когда регион машины состояний-подавтомата достигает соответствующей точки выхода, состояние-подавтомат покидают через эту точку выхода.

#### 14.2.3.6 Конечное состояние

FinalState — особый вид состояния, означающий, что объемлющий регион завершён. Таким образом, переход в конечное состояние представляет завершение поведений региона, содержащего это конечное состояние.

#### 14.2.3.7 Псевдосостояние и вид псевдосостояния

Псевдосостояние — абстракция, охватывающая различные виды транзитных вершин графа машины состояний. Псевдосостояния обычно используются для сцепления нескольких переходов в более сложные составные переходы (см. ниже). Например, комбинируя переход, входящий в псевдосостояние разделения, с набором переходов, выходящих из этого псевдосостояния, мы получаем составной переход, который может войти в набор ортогональных регионов.

Конкретная семантика псевдосостояния зависит от вида псевдосостояния, который задаётся его атрибутом kind типа PseudostateKind. Ниже описаны различные виды и их семантика:

- initial — начальное псевдосостояние представляет точку начала региона; то есть это точка, из которой начинается выполнение содержащегося в нём поведения при входе в регион посредством активации по умолчанию. Оно является источником не более чем одного перехода, который может иметь связанное поведение-эффект, но не может иметь связанных триггера или сторожа. В регионе может быть не более одной начальной вершины.

- deepHistory — этот вид псевдосостояния является своего рода переменной, представляющей последнюю активную конфигурацию состояний владеющего региона. Как объяснено выше, переход, завершающийся на этом псевдосостоянии, означает восстановление региона в ту же конфигурацию состояний, но со всей семантикой входа в состояние (см. подпункт, описывающий вход в состояние). Поведения при входе всех состояний восстанавливаемой конфигурации выполняются в надлежащем порядке, начиная с самого внешнего состояния. Псевдосостояние deepHistory может быть определено только для составных состояний, и в регионе составного состояния может содержаться не более одного такого псевдосостояния.

- shallowHistory — как объяснено выше, этот вид псевдосостояния является своего рода переменной, представляющей последнее активное подсостояние содержащего его региона, но не подсостояния этого подсостояния. Переход, завершающийся на этом псевдосостоянии, означает восстановление региона в это подсостояние со всей семантикой входа в состояние. Из этого псевдосостояния может быть определён один

  исходящий переход, завершающийся на подсостоянии составного состояния. Это подсостояние является состоянием мелкой истории по умолчанию для составного состояния. Псевдосостояние shallowHistory может быть определено только для составных состояний, и в регион составного состояния может быть включено не более одного такого псевдосостояния.

- join — этот вид псевдосостояния служит общей целевой вершиной для двух или более переходов, исходящих из вершин в разных ортогональных регионах. Переходы, завершающиеся на псевдосостоянии объединения, не могут иметь сторожа или триггера. Подобно точкам соединения в сетях Петри, псевдосостояния объединения выполняют функцию синхронизации: все входящие переходы должны завершиться, прежде чем выполнение сможет продолжиться по исходящему переходу.

- fork — псевдосостояния разделения служат для разбиения входящего перехода на два или более переходов, завершающихся на вершинах в ортогональных регионах составного состояния. Переходы, исходящие из псевдосостояния разделения, не могут иметь сторожа или триггера.

- junction — этот вид псевдосостояния используется для соединения нескольких переходов в составные пути между состояниями. Например, псевдосостояние соединения может использоваться, чтобы слить несколько входящих переходов в один исходящий переход, представляющий общий путь продолжения. Либо оно может использоваться, чтобы разбить входящий переход на несколько сегментов исходящих переходов с разными ограничениями-сторожами. ПРИМЕЧАНИЕ. Такие ограничения-сторожа вычисляются до выполнения любого составного перехода, содержащего это псевдосостояние, поэтому это называется статическим условным ветвлением. Может случиться, что для конкретного составного перехода конфигурация путей переходов и значений сторожей такова, что составной переход не может достичь допустимой конфигурации состояний. В таких случаях весь составной переход блокируется, даже если его триггеры разрешены. (Чтобы в некоторых случаях избежать этой ситуации, можно связать с не более чем одним исходящим переходом предопределённый сторож, обозначаемый “else”. Этот переход разрешается, если все сторожа, прикреплённые к другим переходам, вычисляются как ложные.) Если более одного сторожа вычисляются как истинные, выбирается один из них. Алгоритм такого выбора не определён.

- choice — этот вид псевдосостояния подобен псевдосостоянию соединения (см. выше) и служит подобным целям, с тем отличием, что ограничения-сторожа на всех исходящих переходах вычисляются динамически, когда прохождение составного перехода достигает этого псевдосостояния. Следовательно, choice используется для реализации динамического условного ветвления. Он позволяет разбивать составные переходы на несколько альтернативных путей так, что решение о том, какой путь выбрать, может зависеть от результатов выполнений поведений, произведённых в том же составном переходе до достижения точки выбора. Если более одного сторожа вычисляются как истинные, выбирается один из соответствующих переходов. Алгоритм такого выбора не определён. Если ни один из сторожей не вычисляется как истинный, модель считается некорректно построенной. Чтобы этого избежать, рекомендуется для каждого псевдосостояния выбора определять один исходящий переход с предопределённым сторожем “else”.

- entryPoint — псевдосостояние entryPoint представляет точку входа для машины состояний или составного состояния, обеспечивающую инкапсуляцию внутреннего устройства состояния или машины состояний. В каждом регионе машины состояний или составного состояния, владеющего точкой entryPoint, имеется не более одного перехода от точки входа к вершине внутри этого региона. ПРИМЕЧАНИЕ. Если у владеющего состояния есть связанное поведение при входе, это поведение выполняется до любого поведения, связанного с исходящим переходом. Если задействовано несколько регионов, точка входа действует как псевдосостояние разделения.

- exitPoint — псевдосостояние exitPoint — это точка выхода машины состояний или составного состояния, обеспечивающая инкапсуляцию внутреннего устройства состояния или машины состояний. Переходы, завершающиеся на точке выхода в любом регионе составного состояния или машины состояний, на которую ссылается состояние-подавтомат, означают выход из этого составного состояния или состояния-подавтомата (с выполнением связанного с ним поведения при выходе). Если несколько переходов из ортогональных регионов внутри состояния завершаются на этом псевдосостоянии, то оно действует подобно псевдосостоянию объединения.

- terminate — вход в псевдосостояние завершения означает, что выполнение машины состояний немедленно прекращается. Машина состояний не покидает ни одного состояния и не выполняет никаких поведений при выходе. Любые выполняющиеся поведения doActivity автоматически прерываются. Вход в псевдосостояние завершения эквивалентен вызову действия уничтожения объекта.

#### 14.2.3.8 Переходы

Переход — это одна направленная дуга, исходящая из единственной исходной вершины и завершающаяся на единственной целевой вершине (источник и цель могут быть одной и той же вершиной), которая задаёт допустимый фрагмент поведения машины состояний. Он может иметь связанное поведение-эффект, которое выполняется при прохождении (выполнении) перехода.

ПРИМЕЧАНИЕ. Длительность прохождения перехода не определена, что допускает различные семантические истолкования, включая как «нулевое», так и ненулевое время.

Переходы выполняются как часть более сложного составного перехода, который переводит выполнение машины состояний из одной устойчивой конфигурации состояний в другую. Семантика составных переходов описана ниже.

В ходе выполнения экземпляр перехода называется:

- достигнутым, когда выполнение его машины состояний достигло его исходной вершины (то есть его исходное состояние входит в активную конфигурацию состояний);

- проходимым, когда он выполняется (вместе с любым связанным поведением-эффектом);

- завершённым, после того как он достиг своей целевой вершины.

Переход может владеть набором триггеров, каждый из которых задаёт событие, вхождение которого при диспетчеризации может запустить прохождение перехода. Триггер перехода называется разрешённым, если диспетчеризованное вхождение события соответствует его виду события. Когда для перехода определено несколько триггеров, они логически дизъюнктивны, то есть если разрешён любой из них, переход будет запущен.

##### 14.2.3.8.1 Виды переходов относительно источника

Семантика перехода зависит от его отношения к своей исходной вершине. Определены три различные возможности в зависимости от значения атрибута kind перехода:

- kind = external означает, что переход покидает свою исходную вершину. Если вершина — состояние, то выполнение этого перехода приведёт к выполнению любого связанного поведения при выходе этого состояния.

- kind = local противоположен external: переход не покидает своё содержащее состояние (и, следовательно, поведение при выходе содержащего состояния не выполняется). Однако для локальных переходов целевая вершина должна отличаться от исходной. Локальный переход может существовать только внутри составного состояния.

- kind = internal — особый случай локального перехода, являющегося самопереходом (то есть с одинаковыми исходным и целевым состояниями), при котором состояние никогда не покидается (и, таким образом, не входится заново), что означает, что при выполнении этого перехода не выполняются ни поведение при выходе, ни поведение при входе. Такой вид перехода может быть определён только тогда, когда исходная вершина — состояние.

##### 14.2.3.8.2 Переходы верхнего уровня (групповые)

Переходы, исходной вершиной которых является составное состояние, называются переходами верхнего уровня, или групповыми. Если они внешние, групповые переходы приводят к выходу из всех подсостояний составного состояния с выполнением любых определённых поведений при выходе, начиная с самых внутренних состояний активной конфигурации состояний. В случае локальных переходов будут выполнены поведения при выходе исходного состояния и поведения при входе целевого состояния, но не поведения содержащего состояния.

##### 14.2.3.8.3 Завершающие переходы и события завершения

Особый вид перехода — завершающий переход, имеющий неявный триггер. Событие, разрешающее этот триггер, называется событием завершения и означает, что все поведения, связанные с исходным состоянием завершающего перехода, завершили выполнение. В случае простых состояний событие завершения порождается, когда связанные поведения при входе и doActivity завершили выполнение. Если такие поведения не определены, событие завершения порождается при входе в состояние. Для составных состояний и состояний-подавтоматов событие завершения порождается при следующих обстоятельствах:

- все внутренние деятельности (например, поведения при входе и doActivity) завершили выполнение, и

- если состояние является составным, все его ортогональные регионы достигли конечного состояния, или

- если состояние является состоянием-подавтоматом, выполнение машины состояний-подавтомата достигло конечного состояния.

События завершения имеют приоритет диспетчеризации. То есть они диспетчеризуются раньше любых ожидающих вхождений событий в пуле событий. Если одновременно происходят два или более событий завершения, соответствующих нескольким ортогональным регионам (то есть в результате одного и того же вхождения события), порядок обработки таких вхождений завершения не определён. Завершение всех регионов верхнего уровня в машине состояний соответствует завершению поведения машины состояний и приводит к её прекращению. Сторожа переходов

Переход может иметь связанное ограничение-сторож. Переходы, у которых сторож вычисляется как ложный, блокируются. Сторожа вычисляются до того, как разрешается содержащий их составной переход, если только они не находятся на переходах, исходящих из псевдосостояния выбора. В последнем случае сторожа вычисляются при достижении точки выбора. Переход, не имеющий связанного сторожа, трактуется так, как если бы у него был сторож, всегда истинный. ПРИМЕЧАНИЕ. Завершающий переход тоже может иметь сторожа.

Ограничение-сторож может включать проверки ортогональных состояний текущей машины состояний или явно обозначенных состояний некоторого достижимого объекта (например, «в состоянии State1» или «не в состоянии State2»). Имена состояний могут быть полными с учётом вложенных состояний и регионов, которые их содержат, давая путевые имена вида “RegionA::State1::Region1::State2::State3”. Это может использоваться в случае, когда одно и то же имя состояния встречается в разных регионах составных состояний.

##### 14.2.3.8.4 Составные переходы

Как отмечено ранее, когда вхождение события запускает разрешённый переход или создаётся выполнение машины состояний, это может инициировать прохождение набора соединённых и вложенных переходов и вершин до достижения устойчивой конфигурации состояний. В общем случае след этого прохождения, называемый составным переходом, может быть представлен ациклическим направленным графом. Корнем (источником) этого графа может быть одно из следующего:

- переход с одним или несколькими определёнными триггерами;

- завершающий переход;

- набор переходов (включая, возможно, завершающие переходы), исходящих из разных ортогональных регионов и сходящихся на общем псевдосостоянии объединения;

- переход, исходящий из начального псевдосостояния самого верхнего региона (то есть региона, принадлежащего машине состояний); этот вариант применим только к случаям, когда экземпляр машины состояний создаётся.

Ветвление при выполнении составного перехода возникает всякий раз, когда выполняющийся переход выполняет вход по умолчанию в состояние с несколькими ортогональными регионами (с отдельной ветвью для каждого региона), или когда встречается псевдосостояние разделения. Общее поведение, получающееся в результате выполнения составного перехода, представляет собой частично упорядоченное множество выполнений поведений, связанных с проходимыми элементами, определяемое порядком, в котором встречаются элементы (вершины и переходы). Например, если переход, входящий в составное состояние, завершается на подсостоянии этого состояния, то поведение-эффект перехода было бы выполнено до выполнения поведения при входе составного состояния, а затем — поведение при входе подсостояния. Если при прохождении встречается псевдосостояние разделения, то поведения-эффекты отдельных исходящих ветвей, по крайней мере концептуально, выполняются параллельно друг с другом.

Если достигается точка выбора или соединения с несколькими исходящими переходами со сторожами, будет выполнен переход, сторож которого вычисляется как истинный. Если более одного сторожа вычисляются как истинные, для продолжения прохождения выбирается один из этих переходов. Алгоритм такого выбора не определён. В случае переходов, исходящих из псевдосостояния выбора, если при достижении псевдосостояния ни один сторож не вычисляется как истинный, модель некорректно построена.

##### 14.2.3.8.5 Принадлежность переходов

Владелец перехода явно не ограничен, хотя регион, в котором он содержится, должен прямо или косвенно принадлежать владеющей машине состояний. Предлагаемый владелец перехода — самый внутренний регион, содержащий и его исходную, и его целевую вершины.

#### 14.2.3.9 Обработка событий для машин состояний

##### 14.2.3.9.1 Парадигма выполнения до завершения

Обработка вхождений событий выполнением машины состояний соответствует общей семантике, определённой в пункте 13. При создании машина состояний выполняет свою инициализацию, в ходе которой она выполняет начальный составной переход, вызванный созданием, после чего входит в точку ожидания. В случае поведений машины состояний точка ожидания представляется устойчивой конфигурацией состояний. Она остаётся таковой, пока не будет диспетчеризовано событие, хранящееся в её пуле событий. Это событие вычисляется и, если оно соответствует допустимому триггеру машины состояний и есть по меньшей мере один разрешённый переход, который может быть запущен этим вхождением события, выполняется один шаг машины состояний. Шаг включает выполнение составного перехода и завершение на устойчивой конфигурации состояний (то есть в следующей точке ожидания). Затем этот цикл повторяется, пока машина состояний не завершит своё поведение или пока она не будет асинхронно прекращена некоторым внешним агентом.

Машины состояний могут реагировать на любые виды событий, описанные в пункте 13, а также на события завершения (см. выше).

ПРИМЕЧАНИЕ. Как объяснено выше, события завершения имеют приоритет и диспетчеризуются раньше любых ожидающих вхождений событий в пуле событий.

Вхождения событий обнаруживаются, диспетчеризуются и обрабатываются выполнением машины состояний по одному.

ПРИМЕЧАНИЕ. Порядок диспетчеризации событий оставлен неопределённым, что допускает различные алгоритмы планирования.

Этот цикл называется парадигмой выполнения до завершения, а соответствующий шаг машины состояний называется шагом выполнения до завершения. Выполнение до завершения означает, что при отсутствии исключений или асинхронного уничтожения объекта контекстного классификатора либо выполнения машины состояний ожидающее вхождение события диспетчеризуется только после того, как завершена обработка предыдущего вхождения и достигнута устойчивая конфигурация состояний. То есть вхождение события никогда не будет диспетчеризовано, пока выполнение машины состояний занято обработкой предыдущего. Эта поведенческая парадигма выбрана, чтобы избежать осложнений, возникающих из-за конфликтов параллельного доступа, которые могут возникнуть, когда машина состояний пытается реагировать на несколько одновременных или перекрывающихся событий.

Когда вхождение события обнаружено и диспетчеризовано, это может привести к разрешению одного или нескольких переходов к срабатыванию. Если ни один переход не разрешён и соответствующий вид события не входит ни в один из списков deferrableTriggers активной конфигурации состояний, диспетчеризованное вхождение события отбрасывается, и шаг выполнения до завершения завершается тривиально.

Из-за наличия ортогональных регионов возможно, что одно и то же вхождение события может запустить несколько переходов (в разных регионах). Порядок выполнения этих переходов оставлен неопределённым. Каждый ортогональный регион в активной конфигурации состояний, не содержащий вложенных ортогональных регионов (то есть «нижний» регион), может сработать не более одного перехода в результате текущего вхождения события. Когда все ортогональные регионы закончили выполнение перехода, текущее вхождение события полностью израсходовано, и шаг выполнения до завершения завершается.

Как упомянуто выше, возможно, что одно и то же вхождение события разрешает к срабатыванию несколько взаимно исключающих переходов в данном регионе. В таких случаях выбирается и выполняется только один. Какой из разрешённых переходов выбран, определяется алгоритмом выбора переходов, описанным ниже.

В ходе перехода может выполняться ряд поведений-действий. Если такое поведение содержит вызов синхронного обращения к другому объекту, выполняющему машину состояний, то шаг перехода не завершается, пока вызванный метод объекта не завершит свой шаг выполнения до завершения.

Выполнение до завершения может быть реализовано различными способами. Для активных классов оно может быть реализовано циклом событий, работающим в собственном потоке и читающим вхождения событий из пула. Для пассивных классов оно может быть реализовано с использованием монитора.

ПРИМЕЧАНИЕ К РЕАЛИЗАЦИИ. Выполнение до завершения часто ошибочно истолковывают так, будто это означает, что выполняющуюся машину состояний нельзя прервать, что, конечно, привело бы к проблемам инверсии приоритетов в некоторых системах, чувствительных ко времени. Однако это не так: в данной реализации поток, выполняющий шаг машины состояний, может быть приостановлен, позволяя работать потокам с более высоким приоритетом, и, как только базовая подсистема планирования потоков снова выделит ему процессорное время, он может безопасно возобновить выполнение и завершить обработку событий.

##### 14.2.3.9.2 Разрешённые переходы

Переход разрешён тогда и только тогда, когда:

- все его исходные состояния входят в активную конфигурацию состояний;

- хотя бы один из триггеров перехода имеет событие, которому соответствует вид события диспетчеризованного вхождения. В случае событий-сигналов соответствует любое вхождение того же или совместимого типа, что указан в триггере. Если один из триггеров предназначен для AnyReceiveEvent, то этот триггер удовлетворяется либо сигналом, либо событием вызова, при условии что нет другого триггера сигнала или события вызова для того же перехода или для любого другого перехода с той же исходной вершиной, что и у перехода с триггером AnyReceiveEvent (см. также 13.3.1);

- если существует по меньшей мере один полный путь от исходной конфигурации состояний к целевой конфигурации состояний или к динамическому псевдосостоянию выбора, на котором все условия-сторожа истинны (переходы без сторожей трактуются так, как если бы их сторожа всегда были истинны).

Поскольку одно и то же вхождение события может разрешить более одного перехода, разрешённость является необходимым, но не достаточным условием срабатывания перехода.

##### 14.2.3.9.3 Конфликтующие переходы

Возможно, что в машине состояний разрешено более одного перехода. В этом случае такие переходы могут конфликтовать друг с другом. Например, рассмотрим случай двух переходов, исходящих из одного состояния, запускаемых одним событием, но с разными сторожами. Если это событие происходит и оба условия-сторожа истинны, то за один шаг выполнения до завершения может сработать не более одного из этих переходов.

Два перехода называются конфликтующими, если они оба покидают одно и то же состояние, или, точнее, если пересечение множеств покидаемых ими состояний непусто. Одновременно могут срабатывать только переходы, находящиеся во взаимно ортогональных регионах. Это ограничение гарантирует, что новая активная конфигурация состояний, получающаяся в результате выполнения набора переходов, корректно построена.

Внутренний переход в состоянии конфликтует только с переходами, вызывающими выход из этого состояния.

##### 14.2.3.9.4 Приоритеты срабатывания

В ситуациях с конфликтующими переходами выбор того, какие переходы сработают, частично основан на неявном приоритете. Эти приоритеты разрешают некоторые, но не все конфликты переходов, поскольку определяют лишь частичный порядок. Приоритеты конфликтующих переходов основаны на их относительном положении в иерархии состояний. По определению, переход, исходящий из подсостояния, имеет более высокий приоритет, чем конфликтующий переход, исходящий из любого из содержащих его состояний.

Приоритет перехода определяется по его исходному состоянию. Приоритет переходов, сцепленных в составной переход, определяется по приоритету перехода с наиболее глубоко вложенным исходным состоянием.

В общем случае, если t1 — переход с исходным состоянием s1, а t2 имеет источник s2, то:

- если s1 является прямым или косвенно вложенным подсостоянием s2, то t1 имеет более высокий приоритет, чем t2;

- если s1 и s2 не входят в одну и ту же конфигурацию состояний, то разницы приоритетов между t1 и t2 нет.

##### 14.2.3.9.5 Алгоритм выбора переходов

Набор переходов, которые сработают, — это переходы в регионах текущей конфигурации состояний, удовлетворяющие следующим условиям:

- все переходы в наборе разрешены;

- внутри набора нет конфликтующих переходов;

- нет перехода вне набора, имеющего более высокий приоритет, чем какой-либо переход в наборе (то есть разрешённые переходы с наивысшими приоритетами входят в набор, а конфликтующие переходы с более низкими приоритетами остаются вне его).

Это может быть реализовано жадным алгоритмом выбора с прямолинейным прохождением активной конфигурации состояний. Состояния в активной конфигурации состояний проходятся начиная с самых внутренних вложенных простых состояний и двигаясь наружу. Для каждого состояния на данном уровне вычисляются все исходящие переходы, чтобы определить, разрешены ли они. Такое прохождение гарантирует, что принцип приоритета не нарушается. Единственный нетривиальный вопрос — разрешение конфликтов переходов между ортогональными состояниями на всех уровнях. Он решается прекращением поиска в каждом ортогональном состоянии, как только срабатывает переход внутри любого из его компонентов.

##### 14.2.3.9.6 Последовательность выполнения перехода

Каждый переход, кроме внутренних и локальных, вызывает выход из исходного состояния и вход в целевое состояние. Эти два состояния, которые могут быть составными, обозначаются соответственно как главный источник и главная цель перехода.

Главный источник — непосредственное подсостояние региона, содержащего исходные состояния, а главная цель — подсостояние региона, содержащего целевые состояния.

ПРИМЕЧАНИЕ. Переход из одного региона в другой в одном и том же непосредственно объемлющем составном состоянии не допускается.

После того как переход разрешён и выбран для срабатывания, выполняются в порядке следующие шаги:

1. Начиная с главного исходного состояния, состояния, содержащие главное исходное состояние, покидаются согласно правилам выхода из состояния (или выхода из составного состояния, если главное исходное состояние вложено), описанным ранее. 2      Серия выходов из состояний продолжается до достижения первого региона, который прямо или косвенно содержит и главное исходное, и главную целевую состояния. Регион, содержащий и главное исходное, и главное целевое состояния, называется их наименьшим общим предком. В этот момент выполняется поведение-эффект перехода, соединяющего подконфигурацию исходных состояний с подконфигурацией целевых состояний. («Подконфигурация» здесь означает то подмножество полной конфигурации состояний, которое содержится в регионе наименьшего общего предка.)

3. Выполняется вход в конфигурацию состояний, содержащую главное целевое состояние, начиная с самого внешнего состояния в регионе наименьшего общего предка, который содержит главное целевое состояние. Выполнение поведений следует правилам входа в состояние (или входа в составное состояние), описанным ранее.

Это выражение, написанное на некотором текстовом поверхностном языке, который может быть либо языком конкретного поставщика, либо некоторым стандартным языком (см. подпункт 16.1).

##### 14.2.4.4.1 Составное состояние

- раздел декомпозиции

Этот раздел показывает структуру композиции состояния в терминах регионов, состояний и переходов. Помимо (необязательного) раздела имени и раздела внутренних переходов состояние может иметь дополнительный раздел, содержащий вложенную диаграмму. Этот значок, состоящий из двух горизонтально расположенных и соединённых состояний, — необязательная визуальная подсказка о том, что состояние имеет декомпозицию, не показанную на данной диаграмме. ##### 14.2.4.4.2 Состояние-подавтомат

Состояние-подавтомат изображается как обычное состояние, где строка в разделе имени имеет следующий синтаксис:

<state-name> ‘:’ <name-of-referenced-StateMachine>

Символ состояния-подавтомата может содержать ссылки на одну или несколько точек входа и на одну или несколько точек выхода. Нотация для этих ссылок на точки соединения включает псевдосостояния входа и выхода на границе состояния-подавтомата. Имена — это имена соответствующих точек входа и выхода, определённых в указанной машине состояний (см. «Ссылка на точку соединения»).

#### 14.2.4.8 Переход

Текстовая нотация перехода по умолчанию определяется следующим выражением BNF:

[<trigger> [‘,’ <trigger>]* [‘[‘ <guard>’]’] [‘/’ <behavior-expression>]]

где <trigger> — стандартная нотация триггеров (см. подпункт 13.3.4), <guard> — логическое выражение для сторожа, а необязательное <behavior-expression> — выражение, задающее поведение-эффект, написанное на некотором текстовом поверхностном языке конкретного поставщика или стандартном языке (см. подпункт 16.1). Триггер может быть любого из стандартных видов триггеров. Триггеры событий-сигналов и триггеры событий вызова неразличимы по синтаксису и должны различаться по своему объявлению в другом месте.

Как альтернатива, в случаях когда поведение-эффект можно описать как последовательность действий на основе потока управления, существует графическое представление переходов и составных переходов, подобное нотации, используемой для деятельностей.

ПРИМЕЧАНИЕ. Хотя эта альтернативная нотация содержит графические элементы, напоминающие нотацию деятельностей, это отдельная форма, применимая только к машинам состояний, и её элементы отображаются на соответствующие понятия машин состояний. Эта нотация имеет форму направленного графа, состоящего из одного или нескольких графических символов, соединённых направленными дугами, представляющими поток управления (см. рисунок 14.32). Во всех случаях, кроме перехода, исходящего из начального псевдосостояния, начальный символ, имеющий форму стандартной нотации простого состояния, представляет исходное состояние перехода. Если этот переход имеет триггер на основе сигнала, то символ исходного состояния соединяется дугой

с особым символом приёма сигнала, описанным ниже. Если у перехода несколько триггеров, все они перечисляются в одном символе, как объяснено ниже.

Если переход исходит из начального псевдосостояния, начальный символ — это начальный символ, тот же, что используется для начального псевдосостояния: заполненный чёрный круг. В этом случае сразу за начальным символом символа приёма сигнала нет.

Кроме концевых символов, завершающих пути, в цепочке могут появляться, по обстоятельствам, любые из следующих символов:

- символ действия;

- символ точки выбора;

- символ отправки сигнала;

- символ слияния.

Завершающим символом в этих направленных графах всегда является либо символ, подобный состоянию, представляющий целевое состояние перехода, либо символ конечного состояния (тот же, что символ для конечного состояния).

##### 14.2.4.8.1 Символы действий

Каждый символ действия представляется прямоугольником с необязательной текстовой спецификацией действия. Он отображается либо на OpaqueAction, либо на SequenceNode, содержащий одно или несколько действий, выполняемых последовательно (см. подпункт 16.11.3) и являющихся частью деятельности, задающей поведение-эффект соответствующего перехода в составном переходе.

##### 14.2.4.8.2 Символ приёма сигнала

Символ приёма сигнала показывается пятиконечным многоугольником, похожим на прямоугольник с треугольной выемкой на одной из сторон (на любой). Он отображается на триггер перехода и не отображается на действие деятельности, задающей поведение-эффект. Имена сигналов триггера, а также любой сторож содержатся внутри символа следующим образом:

<trigger> [‘,’ <trigger>]* [‘[‘ <guard> ‘]’]

где <trigger> задан, как описано в подпункте 13.3.4, с ограничением, что допускаются только виды событий-сигналов и событий изменения. Символ триггера всегда первый в пути символов, и составной переход может иметь не более одного такого символа.

##### 14.2.4.8.3 Символ отправки сигнала

Он представляет особое действие отправки сигнала и отображается непосредственно на SendSignalAction, являющееся частью деятельности, описывающей поведение-эффект соответствующего перехода. Нотация соответствует нотации для SendSignalAction (см. подпункт 16.3.4).

##### 14.2.4.8.4 Символ точки выбора

- переходы вида internal явно на диаграммах не показываются;

## 14.3 Переопределение машины состояний

### 14.3.1 Краткое описание

### 14.3.3 Семантика

#### 14.3.3.1 Расширение машины состояний

Машина состояний может переопределять одну или несколько других машин состояний, и в этом случае она является расширением переопределяемых машин состояний. Регион расширяющей машины состояний может переопределять один или несколько регионов своих extendedStateMachines. Базовое поведение расширяющей машины состояний таково, как если бы она содержала объединение регионов расширяющей машины состояний и всех непереопределённых регионов всех её extendedStateMachines. Расширяющая машина состояний может также добавлять новые псевдосостояния connectionPoint или переопределять connectionPoints любой из своих extendedStateMachines.

Если машина состояний имеет контекстный классификатор с поведением (см. подпункт 13.2.3.4), то этот классификатор является также её контекстом переопределения (см. подпункт 9.2.3.3). Сюда относятся случаи, когда машина состояний является classifierBehavior общего классификатора с поведением или используется для задания метода поведенческой характеристики общего классификатора с поведением. Когда контекстный классификатор с поведением специализируется, связанная машина состояний может быть расширена соответствующей машиной состояний в контексте специализированного классификатора с поведением.

#### 14.3.3.2 Переопределение региона

Регион, являющийся регионом расширяющей машины состояний, может переопределять регион, являющийся регионом extendedStateMachine этой машины состояний. Регион, являющийся регионом переопределяющего состояния в расширяющей машине состояний (см. подпункт 14.3.3.3), может переопределять регион, являющийся регионом переопределяемого состояния в extendedStateMachine этой машины состояний. В любом случае переопределяющий регион называется расширением переопределяемого региона. Базовое поведение расширяющего региона таково, как если бы он содержал объединение вершин и переходов, содержащихся в расширяющем регионе, и всех непереопределённых вершин и переходов, содержащихся в его расширяемом регионе.

#### 14.3.3.3 Переопределение вершины

Вершина, определённая в расширяющем регионе, может переопределять вершину того же вида в расширяемом регионе этого расширяющего региона.

Состояние может быть переопределено только состоянием. Если переопределяющее состояние задаёт поведение при входе, при выходе и/или doActivity, то применяется именно оно, независимо от того, задаёт ли переопределяемое состояние подобное поведение. Однако если переопределяющее состояние не задаёт поведение при входе, при выходе и/или doActivity, но для переопределяемого состояния применимо соответствующее поведение, то поведение переопределяемого состояния применяется и к переопределяющему состоянию. Любые deferrableTriggers, применимые к переопределяемому состоянию, применяются также к переопределяющему состоянию, и переопределяющее состояние может добавлять новые deferrableTriggers. Если переопределяемое состояние не является состоянием-подавтоматом, переопределяющее состояние может также

- переопределять регионы переопределяемого состояния (если оно составное);

- добавлять регионы в переопределяемое состояние;

- переопределять псевдосостояния connectionPoint переопределяемого состояния (если оно составное);

- добавлять псевдосостояния connectionPoint в переопределяемое состояние.

Состояние-подавтомат может быть переопределено только состоянием-подавтоматом, подавтомат которого является расширением подавтомата переопределяемого состояния. Переопределяющее состояние может:

- переопределять ссылки на точки соединения переопределяемого состояния;

- добавлять ссылки на точки соединения в переопределяемое состояние.

Конечное состояние может быть переопределено только конечным состоянием.

Псевдосостояние может быть переопределено только псевдосостоянием того же вида. Если переопределяемое псевдосостояние принадлежит какому-либо состоянию как connectionPoint, то переопределяющее псевдосостояние должно быть connectionPoint переопределения владеющего состояния своего переопределяемого псевдосостояния.

Ссылка на точку соединения может быть переопределена только ссылкой на точку соединения, состояние которой является переопределением состояния переопределяемой ссылки на точку соединения.

#### 14.3.3.4 Переопределение перехода

Переход, определённый в расширяющем регионе, может переопределять переход, определённый в расширяемом регионе этого расширяющего региона. Исходная вершина переопределяющего перехода должна быть переопределением исходной вершины переопределяемого перехода. Целевая вершина переопределяющего перехода может быть либо переопределением целевой вершины переопределяемого перехода, либо добавленной вершиной. Любые триггеры, применимые к переопределяемому переходу, применяются также к переопределяющему переходу, и переопределяющий переход может добавлять новые триггеры. Если переопределяющий переход задаёт ограничение-сторож и/или поведение-эффект, то применяется именно оно. Однако если переопределяющий переход не задаёт ограничение-сторож и/или поведение-эффект, но существует ограничение-сторож и/или поведение-эффект, применимое к переопределяемому переходу, то сторож и/или эффект переопределяемого перехода применяется также к переопределяющему переходу.

### 14.3.4 Нотация

Расширяющая машина состояний показывается с ключевым словом «extended» после имени машины состояний на диаграмме для неё (например, см. рисунки 14.39 и 14.40). Аналогично ключевое слово «extended» может по выбору добавляться после имени расширяющего региона, переопределяющей вершины или переопределяющего перехода. Переопределяющие вершины и переходы рисуются пунктирными или светлыми линиями (например, см. рисунок 14.39). Вершины и переходы из extendedStateMachine, не переопределённые в расширяющей машине состояний, также могут показываться на диаграмме расширяющей машины состояний, нарисованные пунктирными или светлыми линиями. Наконец, если у региона, вершины или перехода isLeaf = true, после имени элемента может по выбору добавляться ключевое слово «final».

### 14.4.3 Семантика

#### 14.4.3.1 Протокольная машина состояний

Протокольная машина состояний всегда определяется в контексте классификатора. Она задаёт, какие поведенческие характеристики этого классификатора могут быть вызваны в данном состоянии протокола и при каких условиях, тем самым задавая допустимые последовательности вызовов. Таким образом, из внешней перспективы определяется спецификация жизненного цикла экземпляра классификатора.

Протокольные машины состояний помогают определить порядок вызова поведенческих характеристик классификатора, задавая:

- поведенческий контекст (то есть состояния и предусловия), в котором их можно допустимо вызвать;

- допустимые порядки вызовов;

- ожидаемые результаты (постусловия) вызовов.

Протокольная машина состояний даёт внешнее представление владеющего классификатора, каким его воспринимают партнёры. Это выходит за рамки того, что можно отразить предусловиями и постусловиями отдельных поведенческих характеристик, так как протокольные машины состояний задают также допустимые порядки вызовов разных характеристик. Это достигается спецификацией машины состояний, в которой триггеры переходов — вызовы характеристик, а сторожа переходов (протокольных переходов) задают предусловие, которое должно выполняться, чтобы вызов был допустим. Состояния этой машины состояний (протокольные состояния), будучи следствием прошлых последовательностей вызовов, отражают состояние протокола и тоже являются формой предусловия.

ПРИМЕЧАНИЕ. Поскольку протокольные машины состояний дают представление поведения классификатора «чёрным ящиком», их состояния не обязательно соответствуют состояниям внутренних поведенческих машин состояний. Истолкование протокольной машины состояний может быть различным:

1. Декларативные протокольные машины состояний, задающие допустимые переходы для вызовов поведенческих характеристик. Эффект вызова поведенческой характеристики не задан. Такая спецификация даёт лишь контракт для пользователя контекстного классификатора.

2. Исполняемые (времени выполнения) протокольные машины состояний, задающие все вхождения событий, которые объект может получать и обрабатывать, вместе с переходами, которые они запускают. В этом случае допустимые переходы для вызовов поведенческих характеристик должны точно совпадать с запускаемыми переходами, иначе возникает исключение времени выполнения. Вызов приводит к выполнению метода, связанного с вызываемой поведенческой характеристикой.

Спецификации для обоих истолкований одинаковы; разница лишь в прямой динамической импликации, которую даёт последнее истолкование.

Более сложные формы моделирования, встречающиеся в поведенческих машинах состояний, такие как составные переходы, машины состояний-подавтоматов, составные состояния и параллельные ортогональные регионы, также могут использоваться для протокольных машин состояний. Например, параллельные регионы позволяют выражать протоколы, в которых экземпляр может иметь несколько активных состояний одновременно. Машины состояний-подавтоматов и составные переходы могут использоваться для выделения общих частей сложных протокольных машин состояний.

Классификатор может иметь несколько протокольных машин состояний. Это может использоваться, например, когда у классификатора несколько родителей, каждый со своей протокольной машиной состояний, и протоколы ортогональны. Альтернатива этому — просто одна протокольная машина состояний с отдельными машинами состояний в параллельных регионах. Состояния в протокольных машинах состояний

Состояния протокольных машин состояний открыты пользователям их контекстных классификаторов. Состояние протокола представляет открытую устойчивую ситуацию своего контекстного классификатора: когда экземпляр классификатора не обрабатывает ни одного вызова поведенческой характеристики, пользователи этого экземпляра всегда могут знать его конфигурацию состояний.

Состояния протокольной машины состояний не могут иметь определённых поведений при входе, при выходе или doActivity.

#### 14.4.3.2 Протокольный переход

Протокольный переход задаёт допустимый переход для вызова поведенческой характеристики контекстного классификатора. Протокольные переходы имеют следующие особенности:

- предусловие (preCondition), которое специализирует атрибут guard перехода;

- триггер;

- постусловие (postCondition).

Протокольный переход задаёт, что (a) связанную (указанную) характеристику можно вызвать у экземпляра контекстного классификатора, если он находится в исходном состоянии и условие-сторож выполняется, и что (b) по завершении перехода экземпляр окажется в целевом состоянии, в котором будет выполняться постусловие.

Протокольные переходы не имеют связанного поведения-эффекта. Следствие протокольного перехода, выполненного в результате вызова поведенческой характеристики, неявно: это выполнение метода, соответствующего вызываемой поведенческой характеристике. В случае других видов триггеров следствия не заданы, кроме того что переход приведёт к другому состоянию при определённом постусловии, независимо от любых поведений, связанных с этим переходом.

##### 14.4.3.2.1 Неожиданный приём триггера

Истолкование приёма вхождения события, не соответствующего допустимому триггеру для текущего состояния, инварианта состояния или предусловия, не определено (например, оно может быть проигнорировано, отвергнуто или отложено; может быть возбуждено исключение; или приложение может остановиться с ошибкой). Семантически это соответствует нарушению предусловия, для которого в UML не определено никакого предопределённого поведения.

##### 14.4.3.2.2 Неожиданное поведение

Истолкование неожиданного поведения, то есть неожиданного результата перехода (неверное конечное состояние или инвариант конечного состояния либо постусловие), также не определено. Однако это следует истолковывать как ошибку реализации протокольной машины состояний.

##### 14.4.3.2.3 Эквивалентность предусловиям и постусловиям операций

Протокольный переход может быть семантически истолкован в терминах предусловий и постусловий связанной операции. достигнуто протокольное состояние “S2” при условии “C2”.

##### 14.4.3.2.4 Использование других видов событий в протокольных машинах состояний

Помимо вызовов поведенческих характеристик, для выражения поведения протокольных машин состояний могут использоваться другие события. Для протокольного перехода может быть задан триггер, не являющийся вызовом поведенческой характеристики. В этом случае такая спецификация является требованием к окружению, внешнему по отношению к протокольной машине состояний. То есть отправлять

вхождение события этого вида экземпляру контекстного классификатора допустимо только при условиях, заданных протокольной машиной состояний. Точное семантическое истолкование этого не определено.

#### 14.4.3.3 Соответствие протоколу

Протокольные машины состояний могут уточняться в более специфические протокольные машины состояний. Соответствие протоколу объявляет, что специфическая протокольная машина состояний задаёт протокол, соответствующий заданному общей протокольной машиной состояний.

Протокольная машина состояний принадлежит классификатору. Классификаторы, владеющие общей машиной состояний и связанной специфической машиной состояний, как правило, также соединены обобщением или реализацией.

Соответствие протоколу представляет объявление о том, что каждое правило и ограничение, заданное для общей протокольной машины состояний (инварианты состояний, предусловия и постусловия для операций, на которые ссылается протокольная машина состояний), применяются к специфической протокольной машине состояний.

### 14.5.2 FinalState (конечное состояние) [Class]

#### 14.5.2.1 Описание

Особый вид состояния, которое при входе в него означает, что объемлющий регион завершён. Если объемлющий регион непосредственно содержится в машине состояний и все другие регионы этой машины состояний также завершены, это означает, что поведение всей машины состояний завершено.

#### 14.5.2.2 Диаграммы

Поведенческие машины состояний

#### 14.5.2.3 Обобщения

State

#### 14.5.2.4 Операции

- isConsistentWith(redefiningElement: RedefinableElement) : Boolean {redefines RedefinableElement::isConsistentWith} запрос isConsistentWith() задаёт, что конечное состояние может быть переопределено только конечным состоянием.

  ```ocl
  pre: redefiningElement.isRedefinitionContextValid(self)
  ```

  ```ocl
  body: redefiningElement.oclIsKindOf(FinalState)
  ```

#### 14.5.2.5 Ограничения

- **no_exit_behavior**

  У конечного состояния нет поведения при выходе.

  ```ocl
  inv: exit->isEmpty()
  ```

- **no_outgoing_transitions**

  У конечного состояния не может быть исходящих переходов.

  ```ocl
  inv: outgoing->size() = 0
  ```

- **no_regions**

  У конечного состояния не может быть регионов.

  ```ocl
  inv: region->size() = 0
  ```

- **cannot_reference_submachine**

  Конечное состояние не может ссылаться на подавтомат.

  ```ocl
  inv: submachine->isEmpty()
  ```

- **no_entry_behavior**

  У конечного состояния нет поведения при входе.

  ```ocl
  inv: entry->isEmpty()
  ```

- **no_state_behavior**

  У конечного состояния нет поведения состояния (doActivity).

  ```ocl
  inv: doActivity->isEmpty()
  ```

### 14.5.3 ProtocolConformance (соответствие протоколу) [Class]

#### 14.5.3.1 Описание

Протокольная машина состояний может быть переопределена в более специфическую протокольную машину состояний или в поведенческую машину состояний. Соответствие протоколу объявляет, что специфическая протокольная машина состояний задаёт протокол, соответствующий общей протокольной машине состояний, либо что специфическая поведенческая машина состояний подчиняется протоколу общей протокольной машины состояний.

#### 14.5.3.2 Диаграммы

Протокольные машины состояний

#### 14.5.3.3 Обобщения

DirectedRelationship

#### 14.5.3.4 Концы ассоциаций

- generalMachine : ProtocolStateMachine [1..1]{subsets DirectedRelationship::target} (opposite A_generalMachine_protocolConformance::protocolConformance) задаёт протокольную машину состояний, которой соответствует специфическая протокольная машина состояний.

- specificMachine : ProtocolStateMachine [1..1]{subsets DirectedRelationship::source, subsets Element::owner} (opposite ProtocolStateMachine::conformance) задаёт протокольную машину состояний, которая соответствует общей протокольной машине состояний.

### 14.5.4 ProtocolStateMachine (протокольная машина состояний) [Class]

#### 14.5.4.1 Описание

Протокольная машина состояний всегда определяется в контексте классификатора. Она задаёт, какие поведенческие характеристики классификатора, в каком состоянии и при каких условиях могут быть вызваны, тем самым задавая допустимые последовательности вызовов поведенческих характеристик классификатора. Протокольная машина состояний задаёт возможные и допустимые переходы экземпляров своего контекстного классификатора вместе с поведенческими характеристиками, несущими эти переходы. Таким образом, для классификатора может быть задан жизненный цикл экземпляра — определением порядка, в котором могут активироваться поведенческие характеристики, и состояний, через которые экземпляр проходит за время своего существования.

#### 14.5.4.2 Диаграммы

Протокольные машины состояний, инкапсулированные классификаторы, интерфейсы

#### 14.5.4.3 Обобщения

StateMachine

#### 14.5.4.4 Концы ассоциаций

- ♦ conformance : ProtocolConformance [0..*]{subsets Element::ownedElement, subsets A_source_directedRelationship::directedRelationship} (opposite ProtocolConformance::specificMachine) соответствие между протокольными машинами состояний

#### 14.5.4.5 Ограничения

- **classifier_context**

  Протокольная машина состояний должна иметь контекст классификатора, а не контекст поведенческой характеристики.

  ```ocl
  inv: _'context' <> null and specification = null
  ```

- **deep_or_shallow_history**

  В протокольных машинах состояний не может быть псевдосостояний глубокой или мелкой истории.

  ```ocl
  inv: region->forAll (r | r.subvertex->forAll (v | v.oclIsKindOf(Pseudostate) implies
  ((v.oclAsType(Pseudostate).kind <> PseudostateKind::deepHistory) and
  (v.oclAsType(Pseudostate).kind <> PseudostateKind::shallowHistory))))
  ```

- **entry_exit_do**

  Состояния протокольной машины состояний не могут иметь поведений при входе, при выходе или doActivity.

  ```ocl
  inv: region->forAll(r | r.subvertex->forAll(v | v.oclIsKindOf(State) implies
  (v.oclAsType(State).entry->isEmpty() and v.oclAsType(State).exit->isEmpty() and
  v.oclAsType(State).doActivity->isEmpty())))
  ```

- **protocol_transitions**

  Все переходы протокольной машины состояний должны быть протокольными переходами.

  ```ocl
  inv: region->forAll(r | r.transition->forAll(t | t.oclIsTypeOf(ProtocolTransition)))
  ```

### 14.5.5 ProtocolTransition (протокольный переход) [Class]

#### 14.5.5.1 Описание

Протокольный переход задаёт допустимый переход для операции. Переходы протокольных машин состояний содержат следующую информацию: предусловие (сторож), триггер и постусловие. Каждый протокольный переход связан не более чем с одной поведенческой характеристикой, принадлежащей контекстному классификатору протокольной машины состояний.

#### 14.5.5.2 Диаграммы

Протокольные машины состояний

#### 14.5.5.3 Обобщения

Transition

#### 14.5.5.4 Концы ассоциаций

- ♦ postCondition : Constraint [0..1]{subsets Namespace::ownedRule} (opposite A_postCondition_owningTransition::owningTransition) задаёт постусловие перехода — условие, которое должно быть получено после срабатывания

  перехода. Это постусловие входит в постусловие операции, связанной с переходом.

- ♦ preCondition : Constraint [0..1]{subsets Transition::guard} (opposite A_preCondition_protocolTransition::protocolTransition) задаёт предусловие перехода. Оно задаёт условие, которое должно быть проверено перед срабатыванием перехода. Это условие-сторож, добавленное к исходному состоянию, будет вычислено как часть предусловия операции, на которую ссылается переход, если таковая есть.

- /referred : Operation [0..*]{} (opposite A_referred_protocolTransition::protocolTransition)

  эта ассоциация ссылается на связанную операцию. Она выводится из операции триггера события вызова, когда это применимо.

#### 14.5.5.5 Операции

- referred() : Operation [0..*] вывод для ProtocolTransition::/referred

  ```ocl
  body: trigger->collect(event)->select(oclIsKindOf(CallEvent))-
  >collect(oclAsType(CallEvent).operation)->asSet()
  ```

#### 14.5.5.6 Ограничения

- **refers_to_operation**

  Если протокольный переход ссылается на операцию (то есть имеет триггер события вызова, соответствующий операции), то эта операция должна применяться к контекстному классификатору машины состояний протокольного перехода.

  ```ocl
  inv: if (referred()->notEmpty() and containingStateMachine()._'context'->notEmpty()) then
  containingStateMachine()._'context'.oclAsType(BehavioredClassifier).allFeatures()-
  >includesAll(referred())
  else true endif
  ```

- **associated_actions**

  Протокольный переход никогда не имеет связанных поведений.

  ```ocl
  inv: effect = null
  ```

- **belongs_to_psm**

  Протокольный переход всегда принадлежит протокольной машине состояний.

  ```ocl
  inv: container.belongsToPSM()
  ```

### 14.5.6 Pseudostate (псевдосостояние) [Class]

#### 14.5.6.1 Описание

Псевдосостояние — абстракция, охватывающая различные виды транзитных вершин графа машины состояний. Экземпляр машины состояний никогда не останавливается в псевдосостоянии; вместо этого он выходит из псевдосостояния и входит в него в рамках одного шага выполнения до завершения.

#### 14.5.6.2 Диаграммы

Поведенческие машины состояний

#### 14.5.6.3 Обобщения

Vertex

#### 14.5.6.4 Атрибуты

- kind : PseudostateKind [1..1] = initial

  Определяет точный вид псевдосостояния и может быть одним из: entryPoint, exitPoint, initial, deepHistory, shallowHistory, join, fork, junction, terminate или choice.

#### 14.5.6.5 Концы ассоциаций

- state : State [0..1]{subsets NamedElement::namespace} (opposite State::connectionPoint)

  состояние, которому принадлежит это псевдосостояние и в котором оно появляется.

- stateMachine : StateMachine [0..1]{subsets NamedElement::namespace} (opposite StateMachine::connectionPoint) машина состояний, в которой определено это псевдосостояние. Применимо только к псевдосостояниям вида entryPoint или exitPoint.

#### 14.5.6.6 Операции

- isConsistentWith(redefiningElement: RedefinableElement) : Boolean {redefines RedefinableElement::isConsistentWith} запрос isConsistentWith() задаёт, что псевдосостояние может быть переопределено только псевдосостоянием того же вида.

  ```ocl
  pre: redefiningElement.isRedefinitionContextValid(self)
  ```

  ```ocl
  body: redefiningElement.oclIsKindOf(Pseudostate) and
  redefiningElement.oclAsType(Pseudostate).kind = kind
  ```

#### 14.5.6.7 Ограничения

- **transitions_outgoing**

  Все переходы, исходящие из вершины разделения, должны иметь целью состояния в разных регионах ортогонального состояния.

  ```ocl
  inv: (kind = PseudostateKind::fork) implies
  -- for any pair of outgoing transitions there exists an orthogonal state which contains the
  targets of these transitions
  -- such that these targets belong to different regions of that orthogonal state
  outgoing->forAll(t1:Transition, t2:Transition | let contState:State =
  containingStateMachine().LCAState(t1.target, t2.target) in
  ((contState <> null) and (contState.region
  ->exists(r1:Region, r2: Region | (r1 <> r2) and t1.target.isContainedInRegion(r1)
  and t2.target.isContainedInRegion(r2)))))
  ```

- **choice_vertex**

  В полной машине состояний вершина выбора должна иметь по меньшей мере один входящий и один исходящий переход.

  ```ocl
  inv: (kind = PseudostateKind::choice) implies (incoming->size() >= 1 and outgoing->size() >=
  1)
  ```

- **outgoing_from_initial**

  Исходящий переход из начальной вершины может иметь поведение, но не может иметь триггера или сторожа.

  ```ocl
  inv: (kind = PseudostateKind::initial) implies (outgoing.guard = null and outgoing.trigger-
  >isEmpty())
  ```

- **join_vertex**

  В полной машине состояний вершина объединения должна иметь по меньшей мере два входящих перехода и ровно один исходящий.

  ```ocl
  inv: (kind = PseudostateKind::join) implies (outgoing->size() = 1 and incoming->size() >= 2)
  ```

- **junction_vertex**

  В полной машине состояний вершина соединения должна иметь по меньшей мере один входящий и один исходящий переход.

  ```ocl
  inv: (kind = PseudostateKind::junction) implies (incoming->size() >= 1 and outgoing->size()
  >= 1)
  ```

- **history_vertices**

  Вершины истории могут иметь не более одного исходящего перехода.

  ```ocl
  inv: ((kind = PseudostateKind::deepHistory) or (kind = PseudostateKind::shallowHistory))
  implies (outgoing->size() <= 1)
  ```

- **initial_vertex**

  Начальная вершина может иметь не более одного исходящего перехода.

  ```ocl
  inv: (kind = PseudostateKind::initial) implies (outgoing->size() <= 1)
  ```

- **fork_vertex**

  В полной машине состояний вершина разделения должна иметь по меньшей мере два исходящих перехода и ровно один входящий.

  ```ocl
  inv: (kind = PseudostateKind::fork) implies (incoming->size() = 1 and outgoing->size() >= 2)
  ```

- **transitions_incoming**

  Все переходы, входящие в вершину объединения, должны исходить из разных регионов ортогонального состояния.

  ```ocl
  inv: (kind = PseudostateKind::join) implies
  -- for any pair of incoming transitions there exists an orthogonal state which contains the
  source vetices of these transitions
  -- such that these source vertices belong to different regions of that orthogonal state
  incoming->forAll(t1:Transition, t2:Transition | let contState:State =
  containingStateMachine().LCAState(t1.source, t2.source) in
  ((contState <> null) and (contState.region
  ->exists(r1:Region, r2: Region | (r1 <> r2) and t1.source.isContainedInRegion(r1)
  and t2.source.isContainedInRegion(r2)))))
  ```

### 14.5.8 Region (регион) [Class]

#### 14.5.8.1 Описание

Регион — часть верхнего уровня машины состояний или составного состояния, служащая контейнером для вершин и переходов машины состояний. Машина состояний или составное состояние может содержать несколько регионов, представляющих поведения, которые могут происходить параллельно.

#### 14.5.8.2 Диаграммы

Поведенческие машины состояний, переопределение машины состояний

#### 14.5.8.3 Обобщения

Namespace, RedefinableElement

#### 14.5.8.4 Концы ассоциаций

- extendedRegion : Region [0..1]{subsets RedefinableElement::redefinedElement} (opposite A_extendedRegion_region::region) регион, расширением которого является этот регион.

- /redefinitionContext : Classifier [1..1]{redefines RedefinableElement::redefinitionContext} (opposite A_redefinitionContext_region::region) ссылается на классификатор, в контексте которого этот элемент может быть переопределён.

- state : State [0..1]{subsets NamedElement::namespace} (opposite State::region)

  состояние, которому принадлежит регион. Если регион принадлежит состоянию, он не может принадлежать также машине состояний.

- stateMachine : StateMachine [0..1]{subsets NamedElement::namespace} (opposite StateMachine::region)

  машина состояний, которой принадлежит регион. Если регион принадлежит машине состояний, он не может принадлежать также состоянию.

- ♦ subvertex : Vertex [0..*]{subsets Namespace::ownedMember} (opposite Vertex::container)

  набор вершин, принадлежащих этому региону.

- ♦ transition : Transition [0..*]{subsets Namespace::ownedMember} (opposite Transition::container)

  набор переходов, принадлежащих региону.

#### 14.5.8.5 Операции

  ```ocl
  endif
  ```

- containingStateMachine() : StateMachine операция containingStateMachine() возвращает машину состояний, в которой определён этот регион.

  ```ocl

  then
  state.containingStateMachine()
  else
  stateMachine
  endif
  ```

- isConsistentWith(redefiningElement : RedefinableElement) : Boolean {redefines RedefinableElement::isConsistentWith()} запрос isConsistentWith задаёт, что регион может быть переопределён любым регионом, для которого допустим контекст переопределения (см. операцию isRedefinitionContextValid). Отметим, что требования согласованности переопределения вершин и переходов внутри переопределяющего региона задаются операциями isConsistentWith и isRedefinitionContextValid для вершины (и её подклассов) и перехода.

  ```ocl

  ```

  ```ocl

  ```

- isRedefinitionContextValid(redefinedElement : RedefinableElement) : Boolean {redefines RedefinableElement::isRedefinitionContextValid()} запрос isRedefinitionContextValid() задаёт, надлежащим ли образом контексты переопределения региона связаны с контекстами переопределения указанного региона, чтобы этот элемент мог переопределить другой. Содержащая машина состояний или содержащее состояние переопределяющего региона должны переопределять содержащую машину состояний или содержащее состояние переопределяемого региона.

  ```ocl
  body: if redefinedElement.oclIsKindOf(Region) then
  let redefinedRegion : Region = redefinedElement.oclAsType(Region) in
  if stateMachine->isEmpty() then
  -- the Region is owned by a State
  (state.redefinedState->notEmpty() and state.redefinedState.region-
  >includes(redefinedRegion))
  else -- the region is owned by a StateMachine
  (stateMachine.extendedStateMachine->notEmpty() and
  stateMachine.extendedStateMachine->exists(sm : StateMachine |
  sm.region->includes(redefinedRegion)))
  endif
  else
  false
  endif
  ```

- redefinitionContext() : Classifier контекст переопределения региона — ближайшая содержащая машина состояний.

  ```ocl

  ```

### 14.5.9 State (состояние) [Class]

#### 14.5.9.1 Описание

Состояние моделирует ситуацию, в течение которой выполняется некоторое (обычно неявное) инвариантное условие.

#### 14.5.9.2 Диаграммы

Поведенческие машины состояний, переопределение машины состояний, узлы объектов

#### 14.5.9.3 Обобщения

Namespace, Vertex

#### 14.5.9.4 Специализации

FinalState

#### 14.5.9.5 Атрибуты

- /isComposite : Boolean [1..1]

  Состояние с isComposite=true называется составным состоянием. Составное состояние — это состояние, содержащее по меньшей мере один регион.

- /isOrthogonal : Boolean [1..1]

  Состояние с isOrthogonal=true называется ортогональным составным состоянием. Ортогональное составное состояние содержит два или более регионов.

- /isSimple : Boolean [1..1]

  Состояние с isSimple=true называется простым состоянием. Простое состояние не имеет регионов и не ссылается ни на какую машину состояний-подавтомат.

- /isSubmachineState : Boolean [1..1]

  Состояние с isSubmachineState=true называется состоянием-подавтоматом. Такое состояние ссылается на другую машину состояний (подавтомат).

#### 14.5.9.6 Концы ассоциаций

- ♦ connection : ConnectionPointReference [0..*]{subsets Namespace::ownedMember} (opposite ConnectionPointReference::state) точки соединения входа и выхода, используемые вместе с этим (подавтоматным) состоянием, то есть соответственно как цели и источники в регионе с состоянием-подавтоматом. Ссылка на точку соединения ссылается на соответствующее определение псевдосостояния точки соединения в машине состояний, на которую ссылается состояние-подавтомат.

- ♦ connectionPoint : Pseudostate [0..*]{subsets Namespace::ownedMember} (opposite Pseudostate::state)

  псевдосостояния входа и выхода составного состояния. Это могут быть только псевдосостояния entryPoint или exitPoint, и они должны иметь различные имена. Они могут быть определены только для составных состояний.

- ♦ deferrableTrigger : Trigger [0..*]{subsets Element::ownedElement} (opposite A_deferrableTrigger_state::state) список триггеров, которые являются кандидатами на сохранение машиной состояний, если они не запускают ни одного перехода из состояния (не потребляются). Отложенный триггер сохраняется, пока машина состояний не достигнет конфигурации состояний, в которой он больше не откладывается.

- ♦ doActivity : Behavior [0..1]{subsets Element::ownedElement} (opposite A_doActivity_state::state)

  необязательное поведение, выполняемое, пока элемент находится в состоянии. Выполнение начинается при входе в это состояние и прекращается либо само по себе по завершении, либо при выходе из состояния — в зависимости от того, что наступит раньше.

- ♦ entry : Behavior [0..1]{subsets Element::ownedElement} (opposite A_entry_state::state)

  необязательное поведение, выполняемое всякий раз при входе в это состояние, независимо от перехода, которым в состояние вошли. Если оно определено, поведения при входе всегда выполняются до завершения прежде любых внутренних поведений или переходов, выполняемых внутри состояния.

- ♦ exit : Behavior [0..1]{subsets Element::ownedElement} (opposite A_exit_state::state)

  необязательное поведение, выполняемое всякий раз при выходе из этого состояния, независимо от того, каким переходом из него вышли. Если оно определено, поведения при выходе всегда выполняются до завершения только после того, как завершились все внутренние поведения и поведения переходов.

- ♦ region : Region [0..*]{subsets Namespace::ownedMember} (opposite Region::state)

  регионы, принадлежащие непосредственно состоянию.

- ♦ stateInvariant : Constraint [0..1]{subsets Namespace::ownedRule} (opposite A_stateInvariant_owningState::owningState) задаёт условия, которые всегда истинны, когда это состояние является текущим. В протокольных машинах состояний инварианты состояний — дополнительные условия к предусловиям исходящих переходов и к постусловию входящих переходов.

- submachine : StateMachine [0..1] (opposite StateMachine::submachineState)

  машина состояний, которая должна быть вставлена вместо (подавтоматного) состояния.

#### 14.5.9.7 Операции

- containingStateMachine() : StateMachine {redefines Vertex::containingStateMachine()} запрос containingStateMachine() возвращает машину состояний, которая содержит состояние прямо или транзитивно.

  ```ocl
  body: container.containingStateMachine()
  ```

- isComposite() : Boolean составное состояние — состояние, имеющее по меньшей мере один регион.

  ```ocl
  body: region->notEmpty()
  ```

- isConsistentWith(redefiningElement : RedefinableElement) : Boolean {redefines RedefinableElement::isConsistentWith()} запрос isConsistentWith задаёт, что неконечное состояние может быть переопределено только неконечным состоянием (это переопределяется в FinalState, чтобы позволить переопределять конечное состояние конечным), а если переопределяемое состояние является состоянием-подавтоматом, то переопределяющее состояние должно быть состоянием-подавтоматом, подавтомат которого является переопределением подавтомата переопределяемого состояния. Отметим, что требования согласованности переопределения регионов и псевдосостояний connectionPoint внутри составного состояния и точек соединения состояния-подавтомата задаются операциями isConsistentWith и isRedefinitionContextValid для региона и вершины (и её подклассов — псевдосостояния и ссылки на точку соединения).

  ```ocl
  pre: redefiningElement.isRedefinitionContextValid(self)
  ```

  ```ocl
  body: redefiningElement.oclIsTypeOf(State) and
  let redefiningState : State = redefiningElement.oclAsType(State) in
  submachine <> null implies (redefiningState.submachine <> null and
  redefiningState.submachine.extendedStateMachine->includes(submachine))
  ```

- isOrthogonal() : Boolean ортогональное состояние — составное состояние, имеющее по меньшей мере 2 региона.

  ```ocl
  body: region->size () > 1
  ```

- isSimple() : Boolean простое состояние — состояние без регионов.

  ```ocl
  body: (region->isEmpty()) and not isSubmachineState()
  ```

- isSubmachineState() : Boolean только состояние-подавтомат ссылается на другую машину состояний.

  ```ocl
  body: submachine <> null
  ```

#### 14.5.9.8 Ограничения

- **entry_or_exit**

  Точками соединения могут служить только псевдосостояния entryPoint или exitPoint.

  ```ocl
  inv: connectionPoint->forAll(kind = PseudostateKind::entryPoint or kind =
  PseudostateKind::exitPoint)
  ```

- **submachine_states**

  Только состояния-подавтоматы могут иметь ссылки на точки соединения.

  ```ocl
  inv: isSubmachineState implies connection->notEmpty( )
  ```

- **composite_states**

  Только составные состояния могут иметь определённые псевдосостояния входа или выхода.

  ```ocl

  ```

- **destinations_or_sources_of_transitions**

  Ссылки на точки соединения, используемые как цели или источники переходов, связанных с состоянием-подавтоматом, должны быть определены как точки входа или выхода в машине состояний-подавтомате.

  ```ocl
  inv: self.isSubmachineState implies (self.connection->forAll (cp |
  cp.entry->forAll (ps | ps.stateMachine = self.submachine) and
  cp.exit->forAll (ps | ps.stateMachine = self.submachine)))
  ```

- **submachine_or_regions**

  Состоянию не разрешается иметь одновременно и подавтомат, и регионы.

  ```ocl
  inv: isComposite implies not isSubmachineState
  ```

### 14.5.10 StateMachine (машина состояний) [Class]

#### 14.5.10.1 Описание

Машины состояний могут использоваться для выражения событийно-управляемых поведений частей системы. Поведение моделируется как прохождение графа вершин, соединённых одной или несколькими связанными дугами переходов, которые запускаются диспетчеризацией последовательных вхождений событий. В ходе этого прохождения машина состояний может выполнить последовательность поведений, связанных с различными элементами машины состояний.

#### 14.5.10.2 Диаграммы

Поведенческие машины состояний, переопределение машины состояний, протокольные машины состояний

#### 14.5.10.3 Обобщения

Behavior

#### 14.5.10.4 Специализации

ProtocolStateMachine

#### 14.5.10.5 Концы ассоциаций

- ♦ connectionPoint : Pseudostate [0..*]{subsets Namespace::ownedMember} (opposite Pseudostate::stateMachine) точки соединения, определённые для этой машины состояний. Они представляют интерфейс машины состояний, когда она используется как часть состояния-подавтомата.

- extendedStateMachine : StateMachine [0..*]{redefines Behavior::redefinedBehavior} (opposite A_extendedStateMachine_stateMachine::stateMachine) машины состояний, расширением которых является эта машина состояний.

- ♦ region : Region [1..*]{subsets Namespace::ownedMember} (opposite Region::stateMachine)

  регионы, принадлежащие непосредственно машине состояний.

- submachineState : State [0..*] (opposite State::submachine)

  ссылается на подавтомат (подавтоматы) в случае состояния-подавтомата. Несколько машин указываются в случае параллельного состояния.

#### 14.5.10.6 Операции

- LCA(s1 : Vertex, s2 : Vertex) : Region операция LCA(s1,s2) возвращает регион, являющийся наименьшим общим предком вершин s1 и s2, исходя из иерархии вложенности машины состояний.

  ```ocl
  body: if ancestor(s1, s2) then
  s2.container
  else
  if ancestor(s2, s1) then
  s1.container
  else
  LCA(s1.container.state, s2.container.state)
  endif
  endif
  ```

- ancestor(s1 : Vertex, s2 : Vertex) : Boolean запрос ancestor(s1, s2) проверяет, является ли вершина s2 предком вершины s1.

  ```ocl
  body: if (s2 = s1) then
  true
  else
  if s1.container.stateMachine->notEmpty() then
  true
  else
  if s2.container.stateMachine->notEmpty() then
  false
  else
  ancestor(s1, s2.container.state)
  endif
  endif
  endif
  ```

- isConsistentWith(redefiningElement : RedefinableElement) : Boolean {redefines RedefinableElement::isConsistentWith()} запрос isConsistentWith задаёт, что машина состояний может быть переопределена любой другой машиной состояний, для которой допустим контекст переопределения (см. операцию isRedefinitionContextValid). Отметим, что требования согласованности переопределения регионов и псевдосостояний connectionPoint, принадлежащих машине состояний, задаются операциями isConsistentWith и isRedefinitionContextValid для региона и вершины (и её подкласса — псевдосостояния).

  ```ocl
  pre: redefiningElement.isRedefinitionContextValid(self)
  ```

  ```ocl
  body: true
  ```

- isRedefinitionContextValid(redefinedElement : RedefinableElement) : Boolean {redefines RedefinableElement::isRedefinitionContextValid()} запрос isRedefinitionContextValid задаёт, надлежащим ли образом контекст переопределения машины состояний связан с контекстами переопределения машины состояний, которую она переопределяет. Требование состоит в том, что контекстный классификатор с поведением переопределяющей машины состояний должен специализировать контекстный классификатор переопределяемой машины состояний. Если у переопределяющей машины состояний нет контекстного классификатора с поведением, то и у переопределяемой машины состояний не должно быть контекстного классификатора с поведением, но вместо этого она должна специализировать переопределяющую машину состояний.

  ```ocl
  body: redefinedElement.oclIsKindOf(StateMachine) and
  let parentContext : BehavioredClassifier =
  redefinedElement.oclAsType(StateMachine).context in
  if context = null then
  parentContext = null and self.allParents()→includes(redefinedElement)
  else
  parentContext <> null and context.allParents()->includes(parentContext)
  endif
  ```

- LCAState(v1 : Vertex, v2 : Vertex) : State эта служебная функция подобна LCA, за исключением того, что возвращает ближайшее составное состояние, содержащее обе входные вершины.

  ```ocl
  body: if v2.oclIsTypeOf(State) and ancestor(v1, v2) then
  v2.oclAsType(State)
  else if v1.oclIsTypeOf(State) and ancestor(v2, v1) then
  v1.oclAsType(State)
  else if (v1.container.state->isEmpty() or v2.container.state->isEmpty()) then
  null.oclAsType(State)
  else LCAState(v1.container.state, v2.container.state)
  endif endif endif
  ```

#### 14.5.10.7 Ограничения

- **connection_points**

  Точки соединения машины состояний — это псевдосостояния вида entryPoint или exitPoint.

  ```ocl
  inv: connectionPoint->forAll (kind = PseudostateKind::entryPoint or kind =
  PseudostateKind::exitPoint)
  ```

- **classifier_context**

  Контекстный классификатор машины состояний не может быть интерфейсом.

  ```ocl
  inv: _'context' <> null implies not _'context'.oclIsKindOf(Interface)
  ```

- **method**

  Машина состояний, являющаяся методом поведенческой характеристики, не может иметь точек соединения входа и выхода.

  ```ocl
  inv: specification <> null implies connectionPoint->isEmpty()
  ```

- **context_classifier**

  Контекстный классификатор машины состояний-метода поведенческой характеристики должен быть классификатором, которому принадлежит эта поведенческая характеристика.

  ```ocl
  inv: specification <> null implies ( _'context' <> null and
  specification.featuringClassifier->exists(c | c = _'context'))
  ```

### 14.5.11 Transition (переход) [Class]

#### 14.5.11.1 Описание

Переход представляет дугу ровно между одной исходной вершиной и ровно одной целевой вершиной (источник и цель могут быть одной и той же вершиной). Он может входить в составной переход, который переводит машину состояний из одной устойчивой конфигурации состояний в другую, представляя полную реакцию машины состояний на вхождение запустившего его события.

#### 14.5.11.2 Диаграммы

Поведенческие машины состояний, переопределение машины состояний, протокольные машины состояний

#### 14.5.11.3 Обобщения

Namespace, RedefinableElement

#### 14.5.11.4 Специализации

ProtocolTransition

#### 14.5.11.5 Атрибуты

- kind : TransitionKind [1..1] = external

  Указывает точный вид перехода.

#### 14.5.11.6 Концы ассоциаций

- container : Region [1..1]{subsets NamedElement::namespace} (opposite Region::transition)

  обозначает регион, которому принадлежит этот переход.

- ♦ effect : Behavior [0..1]{subsets Element::ownedElement} (opposite A_effect_transition::transition)

  задаёт необязательное поведение, выполняемое при срабатывании перехода.

- ♦ guard : Constraint [0..1]{subsets Namespace::ownedRule} (opposite A_guard_transition::transition)

  сторож — это ограничение, дающее тонкий контроль над срабатыванием перехода. Сторож вычисляется, когда машина состояний диспетчеризует вхождение события. Если сторож в этот момент истинен, переход может быть разрешён, иначе он блокируется. Сторожа должны быть чистыми выражениями без побочных эффектов. Выражения-сторожа с побочными эффектами некорректно построены.

- redefinedTransition : Transition [0..1]{subsets RedefinableElement::redefinedElement} (opposite A_redefinedTransition_transition::transition) переход, переопределяемый этим переходом.

- /redefinitionContext : Classifier [1..1]{redefines RedefinableElement::redefinitionContext} (opposite A_redefinitionContext_transition::transition) ссылается на классификатор, в контексте которого этот элемент может быть переопределён.

- source : Vertex [1..1] (opposite Vertex::outgoing)

  обозначает исходную вершину (состояние или псевдосостояние) перехода.

- target : Vertex [1..1] (opposite Vertex::incoming)

  обозначает целевую вершину, достигаемую при выполнении перехода.

- ♦ trigger : Trigger [0..*]{subsets Element::ownedElement} (opposite A_trigger_transition::transition)

  задаёт триггеры, которые могут запустить переход.

#### 14.5.11.7 Операции

- containingStateMachine() : StateMachine запрос containingStateMachine() возвращает машину состояний, которая содержит переход прямо или транзитивно.

  ```ocl
  body: container.containingStateMachine()
  ```

- isConsistentWith(redefiningElement : RedefinableElement) : Boolean {redefines RedefinableElement::isConsistentWith()} запрос isConsistentWith задаёт, что переопределяющий переход согласован с переопределяемым переходом при условии, что исходная вершина переопределяющего перехода переопределяет исходную вершину переопределяемого перехода.

  ```ocl
  pre: redefiningElement.isRedefinitionContextValid(self)
  ```

  ```ocl
  body: redefiningElement.oclIsKindOf(Transition) and
  redefiningElement.oclAsType(Transition).source.redefinedTransition = source
  ```

- redefinitionContext() : Classifier контекст переопределения перехода — ближайшая содержащая машина состояний.

  ```ocl
  body: containingStateMachine()
  ```

#### 14.5.11.8 Ограничения

- **state_is_external**

  Переход вида external может исходить из любой вершины, кроме точек входа.

  ```ocl
  inv: (kind = TransitionKind::external) implies
  not (source.oclIsKindOf(Pseudostate) and source.oclAsType(Pseudostate).kind =
  PseudostateKind::entryPoint)
  ```

- **join_segment_guards**

  Сегмент объединения не должен иметь сторожей или триггеров.

  ```ocl
  inv: (target.oclIsKindOf(Pseudostate) and target.oclAsType(Pseudostate).kind =
  PseudostateKind::join) implies (guard = null and trigger->isEmpty())
  ```

- **state_is_internal**

  Переход вида internal должен иметь состоянием свой источник, а его источник и цель должны совпадать.

  ```ocl
  inv: (kind = TransitionKind::internal) implies
  (source.oclIsKindOf (State) and source = target)
  ```

- **outgoing_pseudostates**

  Переходы, исходящие из псевдосостояний, не могут иметь триггера.

  ```ocl
  inv: source.oclIsKindOf(Pseudostate) and (source.oclAsType(Pseudostate).kind <>
  PseudostateKind::initial) implies trigger->isEmpty()
  ```

- **join_segment_state**

  Сегмент объединения всегда должен исходить из состояния.

  ```ocl
  inv: (target.oclIsKindOf(Pseudostate) and target.oclAsType(Pseudostate).kind =
  PseudostateKind::join) implies (source.oclIsKindOf(State))
  ```

- **fork_segment_state**

  Сегмент разделения всегда должен иметь целью состояние.

  ```ocl
  inv: (source.oclIsKindOf(Pseudostate) and source.oclAsType(Pseudostate).kind =
  PseudostateKind::fork) implies (target.oclIsKindOf(State))
  ```

- **state_is_local**

  Переход вида local должен иметь источником составное состояние или точку входа.

  ```ocl
  inv: (kind = TransitionKind::local) implies
  ((source.oclIsKindOf (State) and source.oclAsType(State).isComposite) or
  (source.oclIsKindOf (Pseudostate) and source.oclAsType(Pseudostate).kind =
  PseudostateKind::entryPoint))
  ```

- **initial_transition**

  Начальный переход на самом верхнем уровне региона машины состояний не имеет триггера.

  ```ocl
  inv: (source.oclIsKindOf(Pseudostate) and container.stateMachine->notEmpty()) implies
  trigger->isEmpty()
  ```

- **fork_segment_guards**

  Сегмент разделения не должен иметь сторожей или триггеров.

  ```ocl
  inv: (source.oclIsKindOf(Pseudostate) and source.oclAsType(Pseudostate).kind =
  PseudostateKind::fork) implies (guard = null and trigger->isEmpty())
  ```

- **transition_vertices**

  Исходная и целевая вершины перехода должны содержаться в той же машине состояний, что и переход.

  ```ocl
  inv: let stateMachine = self.containingStateMachine() in
  source.containingStateMachine() = stateMachine and
  target.containingStateMachine() = stateMachine
  ```

### 14.5.12 TransitionKind (вид перехода) [Enumeration]

#### 14.5.12.1 Описание

TransitionKind — тип-перечисление, используемый для различения различных видов переходов.

#### 14.5.12.2 Диаграммы

- Поведенческие машины состояний

#### 14.5.12.3 Литералы

- **internal**

  Означает, что переход, если он запущен, происходит без выхода из исходного состояния и входа в него (то есть не вызывает смены состояния). Это означает, что условие входа или выхода исходного состояния не будет вызвано. Внутренний переход может быть выполнен, даже если машина состояний находится в одном или нескольких регионах, вложенных в связанное состояние.

- **local**

  Означает, что переход, если он запущен, не покинет составное (исходное) состояние, но покинет и заново войдёт в любое состояние внутри составного состояния, которое входит в текущую конфигурацию состояний.

- **external**

  Означает, что переход, если он запущен, покинет составное (исходное) состояние.

### 14.5.13 Vertex (вершина) [Abstract Class]

#### 14.5.13.1 Описание

Вершина — абстракция узла графа машины состояний. Она может быть источником или назначением любого числа переходов.

#### 14.5.13.2 Диаграммы

Поведенческие машины состояний

#### 14.5.13.3 Обобщения

NamedElement, RedefinableElement

#### 14.5.13.4 Специализации

ConnectionPointReference, Pseudostate, State

#### 14.5.13.5 Концы ассоциаций

- container : Region [0..1]{subsets NamedElement::namespace} (opposite Region::subvertex)

  регион, содержащий эту вершину.

- /incoming : Transition [0..*]{} (opposite Transition::target)

  задаёт переходы, входящие в эту вершину.

- /outgoing : Transition [0..*]{} (opposite Transition::source)

  задаёт переходы, исходящие из этой вершины.

- redefinedVertex : Vertex [0..1]{subsets RedefinableElement::redefinedElement} (opposite A_redefinedVertex_vertex::vertex) вершина, переопределением которой является эта вершина.

- /redefinitionContext : Classifier [1..1]{redefines RedefinableElement::redefinitionContext} (opposite A_redefinitionContext_vertex::vertex) ссылается на классификатор, в контексте которого этот элемент может быть переопределён.

#### 14.5.13.6 Операции

- containingStateMachine() : StateMachine операция containingStateMachine() возвращает машину состояний, в которой определена эта вершина.

  ```ocl
  body: if container <> null
  then
  -- the container is a region
  container.containingStateMachine()
  else
  if (self.oclIsKindOf(Pseudostate)) and ((self.oclAsType(Pseudostate).kind =
  PseudostateKind::entryPoint) or (self.oclAsType(Pseudostate).kind =
  PseudostateKind::exitPoint)) then
  self.oclAsType(Pseudostate).stateMachine
  else
  if (self.oclIsKindOf(ConnectionPointReference)) then
  self.oclAsType(ConnectionPointReference).state.containingStateMachine() -- no
  other valid cases possible
  else
  null
  endif
  endif
  endif
  ```

- incoming() : Transition [0..*] вывод для Vertex::/incoming.

  ```ocl
  body: Transition.allInstances()->select(target=self)
  ```

- outgoing() : Transition [0..*] вывод для Vertex::/outgoing

  ```ocl
  body: Transition.allInstances()->select(source=self)
  ```

- isContainedInState(s : State) : Boolean эта служебная операция возвращает истину, если вершина содержится в состоянии s (входном аргументе).

  ```ocl
  body: if not s.isComposite() or container->isEmpty() then
  false
  else
  if container.state = s then
  true
  else
  container.state.isContainedInState(s)
  endif
  endif
  ```

- isContainedInRegion(r : Region) : Boolean этот служебный запрос возвращает истину, если вершина содержится в регионе r (входном аргументе).

  ```ocl
  body: if (container = r) then
  true
  else
  if (r.state->isEmpty()) then
  false
  else
  container.state.isContainedInRegion(r)
  endif
  endif
  ```

- isConsistentWith(redefiningElement: RedefinableElement) : Boolean {redefines RedefinableElement::isConsistentWith} запрос isRedefinitionContextValid задаёт, что контекст переопределения переопределяющей вершины надлежащим образом связан с контекстом переопределения переопределяемой вершины, если владелец переопределяющей вершины является переопределением владельца переопределяемой вершины. Отметим, что владельцем вершины может быть регион, машина состояний (для псевдосостояния connectionPoint) или состояние (для псевдосостояния connectionPoint или ссылки на точку соединения) — все они являются переопределяемыми элементами.

  ```ocl
  body: redefinedElement.oclIsKindOf(Vertex) and
  owner.oclAsType(RedefinableElement).redefinedElement->includes(redefinedElement.owner)
  ```

- redefinitionContext() : Classifier контекст переопределения вершины — ближайшая содержащая машина состояний.

  ```ocl
  body: containingStateMachine()
  ```
