# Корпус рисунков: ожидаемые модели

Здесь лежат **ожидаемые модели** диаграмм учебного пособия «Упражнения по UML-моделированию
системы регистрации на курсы в среде Visual Paradigm 16.3» (ВМК МГУ, Малышко В. В.).

Это не снимки и не эталонные картинки, а **структура**: какие элементы должны быть на диаграмме и
как они связаны. Геометрии в корпусе нет — она появляется при сборке диаграммы нашим редактором.
Таблица всех 54 рисунков, разбор пробелов и приоритеты — [docs/CORPUS.md](../../docs/CORPUS.md).

## 1. Что в каталоге

| Файл | Что это |
|---|---|
| `<номер>.json` | Ожидаемая модель одного рисунка. Имя — номер рисунка без точек: `3102.json` = Рис. 3.1.2, `4306.json` = Рис. 4.3.6, `1001a.json` = Рис. 1.1a |
| `MANIFEST.json` | Все 54 рисунка: номер, файл снимка, упражнение, тип, группа, воспроизводимость, пробелы. Здесь же словарь кодов пробелов и их частоты |

Моделей **48** — по одной на каждую диаграмму. Шесть рисунков диаграммами не являются (окно среды
1.1 и 1.1a, деревья модели 4.1.1, 5.1.2, 5.2.9, 5.2.16): файлов моделей у них нет, записи о них
есть только в `MANIFEST.json` с `group: "ui"` и `model: null`.

Снимки, по которым составлены модели, — в [`app/reference/vp163/`](../../app/reference/vp163/),
их описание — в [INDEX.md](../../app/reference/vp163/INDEX.md). Текст упражнений —
[docs/uml-tutorial.md](../../docs/uml-tutorial.md).

## 2. Формат файла

Схема `uml-model/3` — та же, что у проектного файла редактора (`app/src/model/model.js`):
элементы и связи живут в модели, диаграмма — это вид на них. Отличие одно: геометрия не нужна,
поэтому `shapes` и `connectors` пусты.

```json
{
  "schema": "uml-model/3",
  "source": { "figure": "3102", "figureNo": "3.1.2", "exercise": "3.1",
              "type": "usecase", "diagramName": "Main",
              "group": "diagram", "reproducible": "частично",
              "altText": "…", "notes": "…", "gaps": ["…"], "gapIds": ["…"] },
  "elements": [
    { "id": "e1", "kind": "actor", "name": "Студент" },
    { "id": "e2", "kind": "usecase", "name": "Зарегистрироваться на курсы",
      "stereotype": "sea level usecase" }
  ],
  "relationships": [
    { "id": "r1", "kind": "association", "from": "e1", "to": "e2",
      "fromMultiplicity": "", "toMultiplicity": "", "navigable": "from" }
  ],
  "diagrams": [ { "id": "d1", "name": "Main", "type": "usecase",
                  "shapes": [], "connectors": [] } ],
  "expect": { "operations": [], "rules": [], "generalizationSets": [] }
}
```

### 2.1 `source` — откуда модель и насколько она полна

| Поле | Что значит |
|---|---|
| `figure` | Имя файла модели и снимка без расширения (`3102`) |
| `figureNo` | Номер рисунка в пособии (`3.1.2`) |
| `exercise` | Упражнение, в котором рисунок приведён (`3.1`, `4.3.A`, `5.2.F`) |
| `type` | Тип диаграммы из `app/notation/uml.json` → `typeOrder` |
| `diagramName` | Имя диаграммы, если текст его называет (`Main`, `Login Basic Flow`) |
| `group` | `diagram` — готовая диаграмма; `ui` — снимок интерфейса |
| `reproducible` | `да` — модель без пробелов; `частично` — собрана, но с пробелами; `нет` — текст не даёт состава |
| `altText` | Дословный alt-текст рисунка из HTML-версии пособия |
| `notes` | Что именно показано и откуда взято; сюда же вынесены оговорки |
| `gaps` | Человекочитаемый список: чего не хватает, чтобы воспроизвести рисунок точно |
| `gapIds` | Те же пробелы кодами из словаря `MANIFEST.json` → `gapVocabulary` |

`reproducible` не выставляется на глаз: `да` стоит только там, где список `gapIds` пуст.
Поэтому «да» в корпусе пять, и это осмысленный результат, а не оценка качества моделей.

`gapIds` — **историческая запись**: чем была бедна схема, когда модель читали с рисунка.
Схема с тех пор расширилась (`uml-model/3`, план Э2-бис: `ownerId`, `operands`, `seq`,
`multiObject`, `stopped`, `regions`, `internals`, `laneId`, `represents`, `behaviorRef`,
`refersTo`, `classifierId`, `fromQualifiers`). Поэтому `gapIds` не переписываются задним
числом, а остаток считается пробами: `node app/tests/gaps.mjs` — каждая проба гоняет поле
через serialize → deserialize и падает, если поле потерялось. Было 17 кодов `model.*`,
осталось 0.

### 2.2 `elements` — что на диаграмме

| Поле | Что значит |
|---|---|
| `id` | `e1`, `e2`, … — уникален внутри файла |
| `kind` | Тип фигуры из `app/notation/uml.json` → `shapes` (`class`, `actor`, `lifeline`, `fragment`, …) |
| `name` | Имя как в тексте пособия. Если текст имени не даёт — `не названо в тексте` |
| `stereotype` | Стереотип, если он назван (`subject`, `boundary`, `control`, `entity`, `layer`, `table`, …) |
| `attributes` / `operations` / `literals` | Члены: `{ "vis", "name", "type", "default", "isStatic", "isDerived", "isID" }`; у операции сигнатура в `name`, возвращаемый тип в `type` |
| `note` | Пояснение к элементу, когда смысл не виден из полей |
| `operator` | Оператор фрагмента (`alt`, `opt`, `loop`, `ref`) |

Поля `abstract`, `isStatic`, `isDerived`, `isID`, `navigable` и блок `generalizationSets` —
уже часть формата (`app/src/model/model.js`, `app/src/io/umljson.js`) и записаны так же, как там.

Дополнительные поля ниже — те, которых в `uml-model/3` **пока нет**, но которые нужны, чтобы
модель соответствовала рисунку. Они собраны здесь, чтобы этап 2 (семантика) видел точный список:

| Поле | Где | Что значит |
|---|---|---|
| `multiObject` | линия жизни | Множественная линия жизни (флажок `Multi-object`) |
| `stopped` | линия жизни | Завершённая линия жизни (крестик) |
| `composite`, `regions` | состояние | Композитное состояние и число регионов |
| `lane` | узел деятельности | Дорожка, в которой лежит узел |
| `represents` | дорожка | Элемент модели, который представляет дорожка (поле `Represents`) |
| `behaviorRef` | узел действия | Ссылка `Behavior` у действия вызова деятельности |
| `structuredNode` | узел деятельности | `ConditionalNode` / `LoopNode` с регионами |
| `classifier` | экземпляр | Тип экземпляра (поле `Add Classifier`) |
| `templateParameters` | пакет | Параметры параметризованного пакета |

### 2.3 `relationships` — связи между элементами

| Поле | Что значит |
|---|---|
| `id` | `r1`, `r2`, … — уникален внутри файла |
| `kind` | Тип связи из `app/notation/uml.json` → `connectors` |
| `name` | Имя связи, сообщения или операции |
| `stereotype` | Стереотип связи (`bind`, `include`, `extend`, …) |
| `from`, `to` | Идентификаторы элементов. `to: null` — потерянное сообщение (нет получателя) |
| `fromMultiplicity`, `toMultiplicity` | Кратности полюсов; пустая строка — кратность не показана |
| `fromRole`, `toRole` | Имена полюсов |
| `navigable` | Направление навигации: `from` — от `from` к `to`, `to` — обратно, `both`, `none`. Поле опущено там, где текст направление не называет (это пробел источника `source.navigation`, а не формата) |
| `setId` | Идентификатор набора обобщений (`GS1`); сам набор описан в блоке `generalizationSets` верхнего уровня |
| `asynchronous` | Асинхронное сообщение |
| `defect` | Связь участвует в намеренном дефекте рисунка |
| `note` | Пояснение |

`navigable` — то самое поле, от которого зависит правило «у варианта использования одно основное
действующее лицо»: `from` на ассоциации «действующее лицо → вариант использования» и означает
«основное действующее лицо».

### 2.3a `generalizationSets` — наборы обобщений

Необязательный блок верхнего уровня, как в `model.js`:

```json
"generalizationSets": [
  { "id": "GS1", "name": "Набор обобщений", "disjoint": true, "covering": true,
    "members": ["FullTimeStudent", "PartTimeStudent"] }
]
```

Обобщение ссылается на набор полем `setId`; `covering: true` печатается на диаграмме как
ограничение `complete`, `disjoint: true` — как `disjoint`.

### 2.4 `diagrams` — вид

Одна диаграмма на файл: `{ "id": "d1", "name", "type", "shapes": [], "connectors": [] }`.
`shapes` и `connectors` пусты намеренно: корпус описывает структуру, а не раскладку, и не должен
ломаться от изменений в раскладке. Все элементы и связи файла относятся к этой диаграмме.

### 2.5 `expect` — что проверять, когда элементами это не выразить

Необязательный блок. Содержит факты, которые нельзя записать элементами, но которые обязаны быть
верны после сборки диаграммы:

| Поле | Что значит |
|---|---|
| `operations` | Операции, которые должны появиться в классах (`LoginForm::login()`, `DataAccess::getUserByLogin(l:string):User`) |
| `rules` | Правила, которые обязаны выполняться или, наоборот, нарушаться (дефект рисунка) |

## 3. Соглашения

1. **Имена не выдумываются.** Имя берётся из текста упражнения или из глоссария пособия. Если
   текст его не даёт, стоит строка `не названо в тексте`, а причина — в `source.gaps`.
2. **Порядок сообщений.** На диаграмме последовательности порядок задаётся вертикальной
   координатой, а геометрии в корпусе нет. Порядок сообщений — это порядок объектов в массиве
   `relationships`.
3. **Фрагменты и ссылки на взаимодействие** — обычные элементы (`fragment`, `interactionUse`);
   какие сообщения они покрывают, корпус не выражает (это пробел формата, см. `model.fragmentCoverage`).
4. **Ссылки на элементы вне диаграммы** (например, тип экземпляра на диаграмме размещения)
   записываются строкой имени в поле (`classifier`), а не идентификатором: идентификатор указывал
   бы на элемент, которого в файле нет.
5. **Один файл — один рисунок.** Если два рисунка показывают одну диаграмму на разных стадиях
   (4.3.2 и 4.3.3), это два независимых файла: каждый описывает состояние на своём рисунке.
6. **Геометрия не переносится.** Координаты, размеры и стили в корпус не попадают.

## 4. Соответствие формату редактора

Файл корпуса — почти проектный файл `uml-model/3`. Два отличия в именах полей:

| Корпус | `app/src/model/model.js` и `app/src/io/umljson.js` |
|---|---|
| `diagrams[].type` | `diagrams[].kind` |
| `diagrams[].connectors` | `diagrams[].links` |

Оба отличия — из постановки задачи на корпус. При загрузке файла корпуса в редактор их нужно
переименовать (и добавить геометрию): `deserialize` читает `diagrams[].kind`, поэтому файл с
полем `type` откроется как диаграмма классов, а связи из `connectors` не попадут в модель.
Поле `source` разбору не мешает: `deserialize` читает `schema`, `elements`, `relationships` и
`diagrams`, а остальные ключи верхнего уровня сохраняет при записи (`extrasOf`).

Поля из §2.2–2.3, помеченные как отсутствующие в формате (`navigable`, `abstract`, `derived`,
`isID`, `isStatic`, `multiObject`, `stopped`, `asynchronous`, `lane`, `classifier`, …), редактор
сейчас не читает и не пишет — это заявка этапу 2.

## 5. Как добавить рисунок

1. Взять номер из `app/reference/vp163/INDEX.md` (имя файла = номер без точек) и найти упражнение
   в [docs/uml-tutorial.md](../../docs/uml-tutorial.md).
2. Выписать из текста элементы, их имена и стереотипы; всё, чего текст не даёт, помечать
   `не названо в тексте`.
3. Собрать файл `<номер>.json` по образцу соседнего файла того же типа (например, `3102.json` для
   вариантов использования, `4202.json` для последовательности, `5101.json` для пакетов).
4. Заполнить `source`: `notes` — что показано и откуда; `gaps` — чего не хватает; `gapIds` — коды
   из `MANIFEST.json` → `gapVocabulary`. Новый код сначала добавить в словарь.
5. Добавить запись в `MANIFEST.json` (`figures[]`) и обновить `counts`/`gapCounts`.
6. Прогнать проверку из §6 и поправить `docs/CORPUS.md`, если поменялись числа.

## 6. Проверка

Из корня проекта:

```sh
python3 - <<'PY'
import json, glob, os
nota = json.load(open('app/notation/uml.json'))
shapes, conns, types = set(nota['shapes']), set(nota['connectors']), set(nota['typeOrder'])
bad = []
for p in sorted(glob.glob('tests/corpus/*.json')):
    if os.path.basename(p) == 'MANIFEST.json':
        continue
    d = json.load(open(p, encoding='utf-8'))
    ids = [e['id'] for e in d['elements']]
    if d['schema'] != 'uml-model/3': bad.append((p, 'schema'))
    if d['source']['type'] not in types: bad.append((p, 'type'))
    if len(ids) != len(set(ids)): bad.append((p, 'dup ids'))
    for e in d['elements']:
        if e['kind'] not in shapes: bad.append((p, e['kind']))
    for r in d['relationships']:
        if r['kind'] not in conns: bad.append((p, r['kind']))
        for end in ('from', 'to'):
            if r[end] is not None and r[end] not in ids: bad.append((p, r['id']))
print('файлов:', len(glob.glob('tests/corpus/*.json')) - 1, 'ошибок:', len(bad))
for b in bad: print(b)
PY
```

Ожидаемый вывод: `файлов: 48 ошибок: 0`.
