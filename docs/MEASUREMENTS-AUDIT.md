## 2. Масштаб снимка

**Результат: коэффициент масштаба 1.00 — снимок 728 × 511 не пересэмплирован: это пиксели
экрана один к одному.** При этом само окно на снимке не 1440 × 900: полезная часть кадра
без рамки окна — примерно 709 × 502 px (x 8…716, y 1…502). То есть формулировка `INDEX.md` («снимок уменьшен относительно
реального окна») верна только в смысле «показано окно меньшего размера», а не «картинка
сжата»: уменьшения изображения не было.

Доказательства (все — из `1001.png`):

| Признак | Что измерено | Что это доказывает |
|---|---|---|
| 1-px линии не «размазаны» | строка `y=137` ровно `109.0` на всём протяжении x 20…700 (std **0.00**), соседи сверху и снизу — ровно `240.0`; строка `y=474` — `136.3`, соседи `244`/`240` | при уменьшении 1-px линия заняла бы 2–3 строки с промежуточными значениями |
| Вертикальная граница панели | столбец `x=211` — ровно `160.0` на 330 строках (два уникальных значения: 160 и 240); `x=212` — ровно `199.0` | то же по горизонтали: пересэмплирования нет |
| Тень панели — ровно 4 ступени | `x=210…213` = `136.3`, `160`, `199`, `225`, затем `240` — каждая ступень постоянна по всей высоте | это намеренный 4-px градиент, а не сглаживание края |
| Значок приложения | тёмный бокс логотипа `x 9…22, y 7…22` — 14 × **16** px | слот иконки 16 × 16 при 1:1 |
| Чёрный текст | в полосе меню `y 10…18` есть пиксели ровно `(0,0,0)` (p1 = 0.0) | у уменьшенного текста чёрного ядра не остаётся |
| JPEG-артефакты | тысячи почти одинаковых серых (`240,241,241`, `241,242,242`, …) | снимок проходил через JPEG — отсюда ±1 уровень шума, но не геометрия |

**Погрешность.** По геометрии её практически нет: масштаб ровно **1.00**, линии и значки
целые, дробных краёв не бывает — остаточный шум JPEG даёт ±1 уровень яркости, но не
±1 пиксель положения. Две неопределённости важнее самой геометрии:

1. **DPI экрана автора неизвестен.** Пиксели снимка — пиксели устройства. Если Windows
   работала при 125 %, «логические» размеры надо делить на 1.25 (панель 202 → 162,
   статусбар 28 → 22). Ни одна гипотеза о DPI не даёт 236: 202 · 1.0 = 202,
   202 / 1.25 = 162, 202 · 1.25 = 253. Значение 236 не получается ни при каком разумном
   коэффициенте.
2. **Размер окна в снимке другой.** Полезная часть кадра — около **709 × 502** px
   (x 8…716, y 1…502), а не 1440 × 900. Поэтому «пересчёт в пиксели окна» ниже — это
   умножение на 1.00. Сравнивать его с окном 1440 × 900 всё равно осмысленно, потому что
   полосы окна и ширина панелей в VP не вычисляются из размера окна: высота статусбара —
   константа темы, а ширина панели задаётся пользователем (доказательство — 202 px на
   рис. 1.1 против 328 px на рис. 1.1a при одинаковой ширине кадра 728 px).

**Почему доли здесь — неправильная мера.** Соблазн сравнить «долю левой панели от ширины
окна» (202 / 709 = 28.5 % против 236 / 1440 = 16.4 %) ведёт к ложному выводу: панель в VP
не тянется вместе с окном, её ширину задаёт пользователь перетаскиванием. Доли меняются
от размера окна, а сама панель — нет. Поэтому вердикты в §3 вынесены по абсолютным
пикселям, а не по процентам.

### Контргипотеза: масштаб 13/14 (проверена и отклонена)

Честности ради надо назвать единственную альтернативу, которая «спасает» часть чисел.
Две измеренные величины связаны с заявленными ровно коэффициентом 13/14:

```
84 · 13/14 = 78.0   ← высота полосы палитры → заявленная высота тулбара
28 · 13/14 = 26.0   ← высота нижней полосы  → заявленная высота статусбара
202 · 13/14 = 187.6 ← ширина левой панели   → 236 не получается
```

То есть если бы снимок был уменьшен в 14/13 раза (оригинал ≈ 784 × 550), два числа из семи
сошлись бы точно. Гипотеза отклонена по трём причинам:

1. **Нет следов пересэмплирования.** При уменьшении в 14/13 1-px линия попадала бы то на
   одну строку, то на две, с промежуточными значениями по длине. Строка `y=137` имеет
   ровно `109.0` на всех 680 столбцах (std 0.00), строка `y=474` — ровно `136.3`, столбец
   `x=211` — ровно `160.0` на 330 строках. Ни одного «промежуточного» края в кадре нет.
2. **Она не объясняет главное число.** 236 при любом коэффициенте не получается
   (202 · 14/13 = 217.6), поэтому вердикт по левой панели от неё не зависит.
3. **Она необъяснима по происхождению.** 784 × 550 — не стандартный размер окна и не
   1440 × 900 · 13/14 (это 1337 × 836). Совпадение 78/84 = 26/28 = 13/14 может быть и
   простой арифметикой: 78 = 13 · 6, 84 = 14 · 6, 26 = 13 · 2, 28 = 14 · 2.

Вывод: рабочая оценка масштаба остаётся **1.00**; в таблице §3 пересчёт дан по ней, а
13/14 упомянута как граница неопределённости. Ни один вердикт от выбора между 1.00 и
0.9286 не меняется.

## 4. Разбор каждого значения

### 4.1. `toolbar height` = 78 px — не подтверждается

Искал полосы по профилю строк: разделители нашлись на `y = 29` (102.9), `y = 52` (109.0
над свободным от панели участком), `y = 137` (109.0), `y = 474` (143.3) и `y = 503` (80.4).
Между ними — четыре полосы: **28 / 22 / 84 / 28** px (§2). Ни одна не равна 78.

Что это за полосы: верхняя (28 px) содержит логотип 16 × 16 в `x 9…22` и строку текста
`x 30…558`; следующая (22 px) — ряд мелких значков с шагом ~20 px по всей ширине
(группы столбцов `x 27…55`, `x 87…124`, `x 155…180`, `x 212…238`, …); третья (84 px) —
ряд из восьми пар «значок + подпись»: значки высотой ~30 px (`y 61…92`), подписи
высотой 10–12 px (`y 96…109`).

78 не получается ни из одной трактовки: «панель инструментов» = 22 (−56 px), «палитра» =
84 (+6 px), «верхняя строка + панель инструментов» = 28 + 1 + 22 = 51 (−27 px), «вся
верхняя часть окна» = 136 (+58 px). Ближайшее — 84, и разница 6 px больше погрешности
(±1 px), то есть это не «78, измеренные неточно», а другое число.

Отдельно: в приложении `--toolbar-h` (78) задаёт `#toolbar`, где в одной строке живут и
меню («Файл», «Экспорт»), и кнопки инструментов, — то есть наш тулбар соответствует
верхней строке и панели инструментов рисунка (51 px), а не палитре (84 px). При любой
трактовке 78 не сходится.

### 4.2. `left panel width` = 236 px — не подтверждается

Граница панели ищется как столбец, тёмный почти на всей высоте рабочей области. На
рис. 1.1 таких столбцов в зоне x 200–260 четыре: `x=210` (136.3 — первая ступень тени),
`x=211` (160.0 — собственно граница), `x=212` (199.0), `x=213` (225.0). Правее — ровный
фон `241` (полоса значков). Слева от границы фон панели — `(255,255,255)` в точке (100,200).

Отсюда ширина левой панели: **x 8…209 = 202 px** (206 px, если считать тень 210…213).

Правее тени, в `x 214…251` (38 px, фон `240/241`), идёт узкая вертикальная полоса со
значками, а `x=252` — ещё одна 1-px линия (`136.3`), за которой уже холст. Если кто-то
мерил «левую панель» вместе с этой полосой, получилось бы **x 8…251 = 244 px** — это
ближайший к 236 вариант, но и он расходится на 8 px. Ни одна из четырёх возможных
трактовок (202 — панель, 206 — с тенью, 244 — с полосой значков, 252 — от края окна)
не даёт 236.

Контрольный кадр `1001a.png` даёт другую границу: `x=336` (136.3), `x=337` (160.0),
`x=338` (199.0), `x=339` (225.0) — то есть **x 8…335 = 328 px**. Разница между кадрами
126 px при одном и том же приложении и одной и той же диаграмме.

Это и есть главный вывод по этому числу: ширина левой панели в VP — **не константа
оформления, а состояние сессии** (пользователь тянет сплиттер). Поэтому «236» не может
быть «измерено со скриншота» как свойство программы: на двух снимках из одной книги
стоят 202 и 328. Значение 236 — это ширина панели в каком-то третьем, не сохранённом
сеансе, либо просто совпадающее на вид число.

Погрешность здесь ни при чём: 202 против 236 — это 34 px (14 %) при точности ±1 px;
даже по контргипотезе 13/14 (§2) вышло бы 217.5, всё равно не 236.

### 4.3. `right panel width` = 300 px — проверить нельзя

Правой панели на рисунке 1.1 нет. Холст (белый лист и серый фон вокруг) занимает
`x 252…716`; столбец `x=716` — правая граница листа (значение 136.3 от y=171 до y=474),
дальше `x 717…719` — фон `241`, `x=720` — рамка окна (в среднем `(90,103,116)`), `x 727` — внешняя рамка.

То есть от листа до рамки окна 4 px, места для панели шириной 300 px в кадре физически
нет (кадр шириной 728 px). Проверить значение по этому рисунку невозможно — ни
подтвердить, ни опровергнуть. Единственное, что можно сказать: в этом сеансе правая
панель была скрыта (`View → Panes`).

### 4.4. `status bar height` = 26 px — не подтверждается (расхождение 2 px)

Нижняя полоса — единственный кандидат на статусбар: она идёт во всю ширину клиентской
области, ограничена сверху разделителем `y=474` (`130,135,144`) и снизу `y=503`,
и занимает строки **y 475…502 = 28 px**.

Содержимое полосы проверено рангами тёмных пикселей. Тёмные пиксели (`< 200`) есть только
в столбцах `0, 2…5, 7` (рамка окна), `650…667`, `685…699` (две иконки) и `720, 722…725, 727`
(рамка). Больше ничего: ни текста, ни разделителей секций.

| Что | Где | RGB |
|---|---|---|
| фон полосы, левый край | (100, 480) | `(250,250,251)` |
| фон полосы, середина | (300, 490) | `(245,245,246)` |
| фон полосы, правый край | (600, 500) | `(239,240,241)` |
| верхняя граница полосы | (300, 474) | `(130,135,144)` |
| иконка 1 (18 × 12) | x 650…667, y 485…496 | в точке (660,490) — `(139,184,229)`, голубая |
| иконка 2 (15 × 17) | x 685…699, y 481…497 | в точке (692,489) — `(205,205,205)` |

Итог: **28 px**, а не 26. Разница 2 px (7.7 %) при точности ±1 px — на границе
погрешности, но не внутри неё: полоса ровная, границы однозначные, и 26 px она не бывает
ни в одной строке. Скорее всего это разница версий (16.3 против 17.3) или темы, но
заявленному источнику («этот скриншот») значение 26 не соответствует.

### 4.5. `zoom on the sample sheet` = 75 % — проверить нельзя

Заявленный источник — «status bar of the reference screenshot». В статусбаре рисунка 1.1
**нет ни одного текстового пикселя**: все тёмные пиксели полосы перечислены выше, и они
принадлежат двум иконкам и рамке окна. Строки «75 %» (как и «100 %», и любого другого
числа) в кадре нет.

Косвенно масштаб тоже не восстанавливается: лист диаграммы пуст — область `x 254…714,
y 173…270` имеет ровно одно значение `255` (минимум = максимум = 255, ни одного пикселя
темнее 240). На пустом листе нет ни фигур, ни сетки, по которым можно было бы оценить
масштаб.

И главное: масштаб в VP — **состояние сессии** (ползунок/меню зума), а не свойство окна.
Даже если бы «75 %» было видно, это была бы настройка конкретного сеанса, а не число,
которое стоит закреплять в листе механики как характеристику программы.

### 4.6. `visibility icon public colour` = `#1a7f37` — проверить нельзя

Заявлено: «green filled circle on the attribute rows of «Заказ»». На рисунке 1.1 нет ни
класса «Заказ», ни какого-либо другого класса: лист диаграммы пуст (см. 4.5), а в левой
панели — дерево модели без раскрытых атрибутов.

| что это на самом деле | значок палитры в полосе `y 53…136`; средний цвет блока `y 75…89, x 135…149` — `(89,174,92)`, то есть светло-зелёная заливка иконки, а не глиф видимости |

Ни один пиксель кадра не равен `#1a7f37`; ближайшее совпадение — деталь постороннего

Отдельно стоит отметить, **откуда взялись имена классов в заявке**. «Заказ» и

Дополнительно проверены **все 54 рисунка** набора на насыщенность (`max−min > 40`):

## 5. Чего по рисунку 1.1 проверить НЕЛЬЗЯ

Честный список, чтобы через месяц никто не считал эти пункты «проверенными»:

1. **Правая панель (300 px).** Её в кадре нет; холст доходит до рамки окна.
2. **Масштаб 75 %.** В статусбаре нет текста вообще, а лист пуст — масштаб не читается ни
   прямо, ни косвенно. Плюс сам масштаб — состояние сессии, а не свойство окна.
3. **Цвета значков видимости.** В кадре нет ни одного класса с атрибутами; во всей книге
   диаграммы классов — чёрно-белые (0.00 % насыщенных пикселей).
4. **Текст и цвет текста статусбара.** В полосе `y 475…502` нет ни одного текстового
   пикселя — только две иконки справа. Строка вида «75 % — фигуры 7 · связи 4 профиль:
   428 стереотипов», которая в аудите (§3.1) названа «текстом самого приложения», на
   рисунке 1.1 отсутствует.
5. **Ширина левой панели как константа.** Два кадра одной книги дают 202 и 328 px —
   значит, это пользовательская настройка. Любое «одно истинное» число здесь невозможно
   без указания сеанса.
6. **DPI экрана автора.** Неизвестен; все абсолютные пиксели — пиксели устройства. При
   125 % все размеры в «логических» пикселях были бы на 20 % меньше измеренных.
7. **Версия.** Рисунок — 16.3, лист механики — 17.3. Любое расхождение в 2–6 px может
   быть версионным, но проверить это по данному набору нечем: по указателю
   (`INDEX.md`) полных окон в наборе только два — 1.1 и 1.1a; остальные 52 рисунка —
   фрагменты панелей и диаграмм.
8. **Заголовок или меню — верхняя строка.** По кадру однозначно не отличить: в ней есть
   логотип 16 × 16 и строка текста с межбуквенными промежутками 1–2 px. На вердикты это
   не влияет (ни 28, ни 22, ни 84 не равны 78), но в отчёте это стоит помнить.

## 6. Вывод

**Счёт по семи значениям:** подтверждено — **0**; не подтверждено — **3** (высота
тулбара 78, ширина левой панели 236, высота статусбара 26); проверить нельзя — **4**
(правая панель 300, масштаб 75 %, цвета `#1a7f37` и `#b3261e`).

Три главных вывода:

1. **Из трёх чисел, которые вообще можно проверить, не подтвердилось ни одно, а остальные
   четыре проверить нечем.** При этом сами числа не абсурдны: 26 против 28 — это 2 px,
   78 против ближайшей полосы (84) — 6 px, а обе пары связаны коэффициентом 13/14 (§2).
   Похоже, что они сняты с того же интерфейса либо в другом сеансе, либо при другом
   масштабе отображения, — но не выдуманы из воздуха. Заявленный же источник —
   «reference screenshot 1440x900» — указывает на файл, которого в проекте не было, и на
   размер, которого у рисунка нет (728 × 511).
2. **Два «числа оформления» на самом деле являются состоянием сессии.** Ширина левой
   панели (202 в 1001 против 328 в 1001a) и масштаб (75 %) задаются пользователем. Их
   нельзя закреплять в листе механики как свойство программы — только как «значение по
   умолчанию в таком-то сеансе».
3. **Цветовые значения из этого набора рисунков не извлекаются в принципе.** Классы с
   атрибутами в кадре отсутствуют, а все 12 рисунков диаграмм классов — чистые градации
   серого. Ссылка «screen: green filled circle on the attribute rows of «Заказ»» указывает
   на сцену, которой в источнике нет.

## Приложение. Как воспроизвести

```python
from PIL import Image
import numpy as np

im = np.array(Image.open('app/reference/vp163/1001.png').convert('RGB')).astype(int)
g  = im.mean(axis=2)
H, W = g.shape                                    # 511, 728

# 1) горизонтальные разделители: строка темнее обоих соседей больше чем на 20.
#    Два диапазона столбцов: 20..700 (через всю ширину) и 220..700 (правее левой панели,
#    белый фон которой местами совпадает по яркости с разделителем и скрывает его).
seps = []
for y in range(1, H - 1):
    for x0, x1 in ((20, 700), (220, 700)):
        a, b, c = g[y - 1, x0:x1], g[y, x0:x1], g[y + 1, x0:x1]
        if ((b < a - 20) & (b < c - 20)).mean() > 0.85:
            seps.append(y)
            print('разделитель', y, round(float(b.mean()), 1), f'(x{x0}..{x1})')
            break
for y0, y1 in zip(seps, seps[1:]):
    print(f'  полоса y{y0 + 1}..{y1 - 1} = {y1 - y0 - 1} px')

# 2) вертикальные границы панелей в рабочей области
band = g[140:470]
cnt  = (band < 215).sum(axis=0)
print('границы:', [x for x in range(W) if cnt[x] > 0.85 * band.shape[0]])

# 3) ширина левой панели: где кончается белый фон панели
print('край панели:', [(x, round(g[300, x], 1)) for x in range(206, 216)])

# 4) содержимое статусбара: какие столбцы вообще имеют тёмные пиксели
cols = sorted(set(np.nonzero((g[475:503] < 200).any(axis=0))[0].tolist()))
print('тёмные столбцы статусбара:', cols)

# 5) пуст ли лист диаграммы
page = im[173:271, 254:715]
print('лист: min', page.min(), 'max', page.max())

# 6) ближайший пиксель к заявленному цвету
for name, rgb in {'public': (26, 127, 55), 'private': (179, 38, 30)}.items():
    flat = im.reshape(-1, 3)
    d = np.sqrt(((flat - np.array(rgb)) ** 2).sum(axis=1))
    i = int(np.argmin(d))
    y, x = divmod(i, W)
    print(name, flat[i], 'в точке', (x, y), 'Δ =', round(float(d[i]), 1))
```

Две честные оговорки к скрипту:

- строка `y=171` попадает в список потому, что это верхняя кромка белого листа
  (лист занимает `y 172…273`, `x 254…714`), а не полоса окна. Поэтому «полоса y138…170
  = 33 px» — это верхний отступ холста над листом, а не отдельная панель.
- `y=52` находится только в диапазоне `x20..700`: над левой панелью разделитель местами
  совпадает по яркости с фоном панели и в правом диапазоне не детектируется. Средняя
  яркость самой строки над свободным от панели участком — `109.0`, как и у `y=137`.
