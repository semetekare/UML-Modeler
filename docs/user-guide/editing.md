# Операции приложения: формат, команды, проверки, справочник

Документ описывает **собранное приложение** — то, что человек открывает
`./serve.sh`: файл модели, команды меню с клавишами, панель «Проверки» и
читалку справочника. Всё сверено с кодом, а не с памятью; адрес файла назван у
каждого раздела.

Прошлая версия этого документа описывала формат `uml-class-diagram/1` — одна
плоская диаграмма, `shapes` + `connectors`, члены строкой — и заканчивалась
таблицей «чего у нас нет» на 76 строк. И формы, и таблицы больше нет:
`uml-class-diagram/1` читается только как старый файл при миграции
(`app/src/io/umljson.js#migrateV1`), а всё, что там было перечислено как пробел —
модель/вид, `abstract`, флаги членов, навигация, агрегация, наборы обобщений,
вложенные диаграммы, пакеты, 14 типов диаграмм, профиль стереотипов — сегодня
есть в коде. Ниже только то, что есть, и адреса, по которым это видно.

---

## 1. Формат `uml-model/3`

Источник истины — `app/src/model/model.js` (`SCHEMA`, умолчания, создание) и
`app/src/io/umljson.js` (`serialize` — что и в каком порядке пишется,
`deserialize` — что читается и как ремонтируется).

### 1.1 Три сущности вместо одной

| Что | Где живёт | Что хранит | Сколько раз на файл |
|---|---|---|---|
| **элемент** | `elements[]` | имя, вид, стереотип, документация, члены, tagged values | один, сколько бы видов у него ни было |
| **связь** | `relationships[]` | вид, имя, стереотип, документация, концы-**элементы**, кратности, роли, tagged values | одна, даже если показана на трёх листах |
| **диаграмма** | `diagrams[]` | имя, вид, владелец, `shapes[]`, `links[]` | сколько нужно |
| **вид фигуры** | `diagrams[].shapes[]` | `elementId` + геометрия | по одному на каждый лист |
| **вид связи** | `diagrams[].links[]` | `relId` + два конца, привязанные к фигурам | по одному на каждый лист |

Отсюда всё, что человек видит руками: переименование элемента меняет его на
всех листах; `Delete` снимает вид, а элемент и его связи остаются;
`Shift+Delete` удаляет элемент, все его виды, все связи с ним и диаграммы,
которые ему принадлежат; `Delete` на связи снимает только вид связи.

### 1.2 Элемент

Обязательны `id` и `kind`. Остальное пишется, только когда не равно умолчанию
(§1.5).

| Поле | Тип | Что значит |
|---|---|---|
| `id` | строка | стабильный идентификатор |
| `kind` | строка | вид нотации: `class`, `interface`, `lifeline`, `message`… — словарь в `notation/uml.json` |
| `name` | строка | имя; пустое — это пустое имя, а не отсутствие |
| `stereotype` | строка | **имя** стереотипа: то, что нарисовано и что переживёт отсутствие профиля |
| `stereotypeId` | строка | уточнение — какая запись профиля имелась в виду, когда одно имя покрывает несколько определений |
| `documentation` | строка | описание элемента |
| `abstract` | `true` | абстрактный классификатор (UML 2.5.1 §9.2.4) → имя курсивом |
| `emptyCompartments` | `1` / `2` | «пустые отделения»: 1 — да, 2 — нет; `0`/отсутствие — «как на диаграмме» |
| `ownerId` | строка | владелец: пакет, компонент, узел, класс (§12.2, §11.4.6) |
| `attributes` / `operations` / `literals` / `slots` | массив членов | таблицы отделений |
| `entry` / `do` / `exit` / `extensionPoints` | массив строк | текстовые компартменты деятельности и ВИ |
| `note` | строка | текст примечания (только у видов с `wrap`) |
| `operator` | строка | оператор фрагмента (`alt`, `opt`, `loop`, `ref`…) |
| `timeline` | `[{state, from, to}]` | состояния шкалы времени, в процентах окна |
| `taggedValues` | `[{name, value}]` | значения тегов стереотипа |
| поля Э2-бис | — | 17 штук, §2 |

**Член** — одна строка из четырёх полей и трёх флагов:
`{vis, name, type, default, isStatic, isDerived, isID}`, где `vis` —
`public|private|protected|package`. У операции подпись целиком лежит в `name`
(`updateStudent(st:Student)`), тип возврата — в `type`; поэтому атрибуты и
операции — одна форма строки и одна таблица в коде.

Флаги рисуются, а не пишутся буквами в имени: `isStatic` → подчёркивание,
`isDerived` → `/` перед именем, `isID` → `{id}` после строки.

### 1.3 Связь

| Поле | Тип | Что значит |
|---|---|---|
| `id` | строка | идентификатор связи |
| `kind` | строка | `association`, `generalization`, `dependency`, `message`, `transition`… |
| `name`, `stereotype`, `stereotypeId`, `documentation` | строки | как у элемента |
| `from`, `to` | `elementId` или `null` | концы; `null` — свободный конец у сообщения (§2) |
| `fromMultiplicity` / `toMultiplicity` | строка | кратность (`0..1`, `1..*`) — только у видов, где кратность положена |
| `fromRole` / `toRole` | строка | имя полюса — только там, где роли положены |
| `fromQualifiers` / `toQualifiers` | массив строк | квалификаторы полюса (§11.4.4) |
| `navigable` | `none|from|to|both` | навигация ассоциации (§11.5.4) |
| `fromAggregation` / `toAggregation` | `none|shared|composite` | вид агрегации на конце |
| `setId` | строка | членство в наборе обобщений |
| `seq` | целое | разрежённый порядок сообщения |
| `asynchronous` | `true` | асинхронное сообщение |
| `local` | `true` | локальный переход (не выходит из состояния) |
| `taggedValues` | массив | как у элемента |

Агрегация пишется, только когда **отличается от смысла вида связи**:
«Агрегация» — это `shared` на исходном конце по определению, поэтому нетронутая
связь не пишет ничего (`defaultAggregation()` в `model.js`). Кратности и роли тоже
пишутся не у всех видов — за это отвечают `multiplicity` и `roles` в словаре
нотации.

### 1.4 Диаграмма, вид фигуры, вид связи

```
diagrams[]: { id, name, kind, ownerElementId?, shapes[], links[] }
shapes[]:   { id, elementId, x, y, w, h, fixedH?, fill? }
links[]:    { id, relId,
              from: { shapeId, side, t? } | null,
              to:   { shapeId, side, t? } | null,
              route?, waypoints?, rounded?, ldx?, ldy?, y? }
```

- `ownerElementId` — вложенная диаграмма: лист принадлежит элементу модели и
  виден под ним в дереве.
- `fixedH` — высоту задаёт содержимое (отделения класса, текст примечания), а не
  человек.
- `fill` — заливка: сплошная или градиент, направление из 16.
- `route: 'direct'` — прямая линия без автоматического маршрута.
- `waypoints` — изломы, поставленные человеком, в мировых координатах.
- `rounded` — `small` (6 px) или `large` (16 px); `off` не пишется.
- `ldx` / `ldy` / `y` — сдвиг подписи связи и её вертикаль на листе
  последовательности.
- У конца связи `side` — сторона фигуры (`top/right/bottom/left`), `t` — доля
  вдоль стороны; `0.5` (середина) не пишется.

### 1.5 Правило умолчаний — и почему оно такое

**Поле пишется только тогда, когда его значение не равно умолчанию.** `false`,
`0`, `none`, пустая строка и пустой список в файл не попадают: `clean()`
выбрасывает `undefined`, а каждый канонизатор сам решает, что считать умолчанием.

Причина не в красоте файла. Модель — это ещё и **эталон миграции**: любой файл,
написанный до появления поля, обязан открыться и пересохраниться **побайтово**,
иначе нечем доказать, что новая семантика ничего не сломала. Эталон лежит в
`tests/fixtures/old-v3.json` в корне проекта (4067 символов, 4611 Б);
`app/tests/stereotypes.mjs` и `app/tests/smoke.mjs` гоняют его через
`deserialize → serialize` и сверяют байты — и с профилем, и без него.

Из того же правила следуют три:

- **Ничего не пишется «на будущее»**: поле, которое пишется, но не читается, —
  дефект, а не запас.
- **Смысл в модели, знак на листе**: ни одно поле не кодирует внешний вид —
  курсив, подчёркивание, ромбы, крестик и наклонные черты рисует рендерер по
  смыслу.
- **Порядок ключей фиксирован** (списки `ELEMENT_KEYS`, `REL_KEYS`, …), позиции
  целые, id стабильны: два одинаковых состояния модели дают одинаковые байты.

### 1.6 Чтение: ремонт вместо потери, миграция вместо отказа

`deserialize` не падает на мелочах, а чинит и говорит об этом в `repairs[]`
(строки уходят в подсказку статусбара):

- неизвестный `kind` → заменяется известным;
- связь без элемента на конце или без второго конца → пропускается с замечанием;
- нет `id` → выдаётся новый;
- битая ссылка (`setId`, `stereotypeId`, `ownerId`, `laneId`, `refersTo`,
  `classifierId`, `behaviorRef`) → снимается, имя и смысл остаются;
- битые ссылки внутри `operands[].messages` и `regions[]` → снимаются
  (`validateRefs`).

Старые схемы читаются и переводятся: `uml-model/2` (связи лежали в диаграмме) и
`uml-class-diagram/1` (одна диаграмма, члены строкой). Сохранение всегда пишет
`uml-model/3`. Файл с чужим `schema` — единственная настоящая ошибка чтения.

## 2. Что добавилось после Э2-бис: 17 полей

Причина партии: корпус пособия (48 моделей) насчитал 17 кодов `model.*`, которых
формат не выражал. План и обоснование каждого поля —
план `PLAN-E2BIS` §3 (приватные заметки); здесь — что человек получает.

| # | Поле | Где | Что значит (UML 2.5.1) | Что видно на листе |
|---|---|---|---|---|
| 1 | `ownerId` | элемент | владение: пакет → элементы, компонент/узел → вложенные классификаторы, класс → вложенные классы (§12.2, §11.4.6) | вложенность в дереве модели; фигура стоит там, куда её поставили |
| 2 | `multiObject` | линия жизни | на одной линии несколько экземпляров (§17.3.4) | две наклонные черты у головы |
| 3 | `stopped` | линия жизни | линия завершена (§17.3.4) | крест в конце линии |
| 4 | `operands[]` | фрагмент | операнды со сторожами и покрытием: `{id, guard, messages[]}` (§17.6.1) | разделители и подписи сторожей |
| 5 | `from` / `to` = `null` | связь-сообщение | найденное/потерянное сообщение (§17.4.4): конец без элемента — смысл, а не обрыв файла | линия обрывается кружком |
| 6 | `seq` | связь-сообщение | разрежённый порядок (10, 20, 30), чтобы вставка не перенумеровывала всё | сообщение стоит на своей высоте |
| 7 | `asynchronous` | связь-сообщение | асинхронное сообщение (§17.4.3) | открытая стрелка вместо залитой |
| 8 | `refersTo` | элемент `interactionUse` | id диаграммы, на которую ссылается | — (ссылка модели, не знак) |
| 9 | `classifierId` | элемент `object` / `instance` | классификатор экземпляра | — (ссылка модели) |
| 10 | `laneId` | узел деятельности | дорожка, в которой узел стоит | положение уже видно |
| 11 | `represents` | дорожка | элемент, который дорожка представляет (§15.2.4) | `: имя` в шапке дорожки |
| 12 | `behaviorRef` | действие | деятельность, которую действие вызывает (§15.3.1) | `«имя»` под названием |
| 13 | `regions[]` | узел деятельности | регионы: `{id, name, nodes[], edges[]}` (§15.3.4) | рамка региона |
| 14 | `regions[]` | состояние | подобласти: `{id, name, states[], transitions[]}` | рамка региона внутри состояния |
| 15 | `internals[]` | состояние | внутренние переходы без исходного и целевого состояния: `{trigger, guard, effect}` (§14.5.10) | строка `trigger [guard] / effect` внутри состояния |
| 16 | `local` | переход | локальный переход — не выходит из состояния при переходе в подобласть | линией не отличается; хранится смысл |
| 17 | `fromQualifiers` / `toQualifiers` | связь-ассоциация | квалификаторы полюса (§11.4.4) | маленький прямоугольник у полюса |

Три вещи, которые легко перепутать:

- **Покрытие фрагмента хранится на операнде, а не на сообщении.** Одно сообщение
  может попасть в два фрагмента (`alt` внутри `loop`); полем на сообщении это
  невыразимо.
- **`regions[]` — одно имя поля для двух видов.** У деятельности это
  `nodes`/`edges`, у состояния — `states`/`transitions`; форма одна, смысл задаёт
  вид элемента.
- **`seq` главный для всей диаграммы, если он есть хотя бы у одного сообщения.**
  Остальные получают порядок по геометрии и идут после.

Все 17 полей необязательные: файл без них открывается и пересохраняется теми же
байтами. Поэтому `schema` остался `uml-model/3`, а не `uml-model/4`.

## 3. Операции: меню, клавиши, что делает каждая

Меню собирает `app/src/ui/toolbar.js`, палитру команд — `app/src/ui/commands.js`,
клавиатуру — `app/src/main.js`. Ниже — фактическое содержимое, а не замысел.

### 3.1 Файл

| Команда | Клавиши | Что делает |
|---|---|---|
| Новая модель | — | пустая модель с одним листом «Диаграмма 1»; при несохранённых правках спрашивает подтверждение |
| Открыть… (\*.uml.json) | `Ctrl+O` | диалог файла; ошибка разбора показывается окном, а не в консоли |
| Загрузить пример (классы) | — | демонстрационная модель классов |
| Пример: все 14 типов UML | — | по листу на каждый тип |
| Сохранить `<имя файла>` | `Ctrl+S` | сначала фиксирует открытый редактор, потом пишет канонический JSON и скачивает его |
| Импорт PlantUML… (.puml, .plantuml, .txt) | — | читает текст **на новый лист**; открытая модель не заменяется |
| Импорт PlantUML: вставить текст… | — | то же, но текст вставляют в окно |
| Новая диаграмма (любой из 14 типов) | — | «+» у списка диаграмм: имя и тип |

Перетаскивание файла в окно открывает его так же, как «Открыть».

### 3.2 Правка

| Команда | Клавиши | Что делает |
|---|---|---|
| Отменить | `Ctrl+Z` | шаг назад; история — 100 шагов (`MAX_HISTORY` в `state/store.js`) |
| Повторить | `Ctrl+Shift+Z` | шаг вперёд |
| Вырезать | `Ctrl+X` | в буфер и с листа |
| Копировать | `Ctrl+C` | в буфер; копируются и элементы модели |
| Вставить | `Ctrl+V` | на том же листе — новые элементы, на другом — вид существующего |
| Дублировать | `Ctrl+D` | новый элемент со сдвигом на шаг сетки |
| Выровнять по левому краю / центру / правому | — | нужно 2+ фигуры; те же шесть кнопок появляются в инспекторе |
| Выровнять по верху / середине / низу | — | то же |
| Равные промежутки по горизонтали / вертикали | — | нужно 2+ фигуры |
| Снять с диаграммы | `Delete`, `Backspace` | убирает вид; элемент, связи и другие листы не трогаются |
| Удалить элемент / связь из модели | `Shift+Delete` | элемент: все виды, все связи с ним, его диаграммы; связь: на всех листах |
| Переименовать выделенное | `F2`, `Enter` | поле правки прямо на листе |

Пункты выравнивания и распределения неактивны, пока фигур меньше двух — это видно
в меню, а не выясняется нажатием.

### 3.3 Вид

| Команда | Клавиши | Что делает |

| Сетка (галочка) | — | шаг 10 px, привязка при перетаскивании |
| Пиктограммы стереотипов (галочка) | — | значок в углу фигуры вместо фигуры; флаг живёт **в модели**, поэтому лист открывается так же, как сохранён |
| Левая панель / правая панель | — | кнопки в шапке |
| Курс | — | вход и выход из режима курса (переключатель) |

| Акцент | — | 6 пресетов цвета интерфейса и выделения |

Масштаба в меню «Вид» нет: им владеет строка состояния — там он и меню

|---|---|

### 3.4 Экспорт

| Команда | Что делает |
|---|---|

### 3.5 Инструменты (полоса над листом) и их клавиши

Клавиша у каждого типа своя — словарь `keys` в `notation/uml.json` для
конкретного типа; `V` — всегда «Выбор». Набор инструментов тоже зависит от типа:
палитра одного листа не предлагает инструмент другого.

| Тип | Клавиши |
|---|---|
| Class | `C` класс · `I` интерфейс · `E` перечисление · `P` пакет · `N` примечание · `A` ассоциация · `G` обобщение · `D` зависимость · `R` реализация |
| Component | `C` компонент · `I` интерфейс · `O` порт · `P` пакет · `N` примечание · `A` сборка · `D` зависимость · `R` реализация |
| Composite Structure | `A` часть · `O` порт · `C` класс · `K` компонент · `L` кооперация · `N` примечание · `R` коннектор · `D` делегирование |
| Deployment | `N` узел · `D` устройство · `E` среда выполнения · `A` артефакт · `C` компонент · `T` примечание · `P` развёртывание · `K` путь связи |

## 4. Проверки: три слоя и что каждый обещает

Наборы правил — `app/notation/rules/uml-2.5.1.json` (констрейнты стандарта: у
каждого пункт, страница, OCL, уровень `error`/`warning`, сообщение и подсказка),
`app/notation/rules/practice.json` (советы без пункта) и `projectRules[]` в файле
модели (договорённости команды). Движок — `app/src/rules/` (`engine.js`, реестр
`registry.js`, по маленькой функции на проверку), панель —
`app/src/ui/checks.js`. Сколько правил в каждом слое, здесь не написано: числа
считаются из набора и печатаются в `docs/RULES-COVERAGE.md` и
`material/rules-coverage/report.md`, иначе документ снова разойдётся с данными.

Слой стандарта покрывает кратности и концы связей, обобщения и циклы,
интерфейсы, актёров и варианты использования, фрагменты последовательности,
узлы деятельности (fork/join/merge/decision/final), псевдосостояния и конечные
состояния, объекты и экземпляры, порты, развёртывание, компоненты, владение и
вложенные взаимодействия. Полная таблица с пунктами и уровнями — в
`docs/RULES-COVERAGE.md` (собирается из `coverage.json`), разбор каждого
толкования — в `app/RULES-COVERAGE.md`.

**Чего модель не выражает** — и это не «не успели»: у каждого такого правила в
`app/src/rules/coverage.js` названо поле или конструкция, которых в схеме нет.
Панель показывает их свёрнутым списком «Не проверяется: N правил — модель не
выражает»; N берётся из самого списка.

| Правило | Чего не хватает |
|---|---|
| `association-specialization-ends` (11.8.1.8) | концы обобщения, которые могут указывать на связь, а не только на элемент: обобщение с id связи загрузчик выбрасывает |
| `association-end-typed` (11.8.1.8) | необязательный конец ассоциации — нетипизированного конца не бывает |
| `stereotype-binary-association` (12.4.9.6) | нужен `memberEnd` вместо пары `from`/`to`: при двух концах равенство выполняется всегда |
| `usecase-binary-association` (18.2.5.6) | тот же `memberEnd` |
| `transition-same-container` (14.5.11.8) | нужен контейнер у состояния (`regions`) и признак `local` у перехода |
| `package-element-visibility` (12.4.5.8) | нужна видимость **элемента** — у члена она есть, у элемента нет |

Второй слой — **практика моделирования** (`notation/rules/practice.json`):
элемент-сирота, элемент не на листе, элемент без имени, дублирующаяся связь,
связь не на листе, изолированная фигура, совпадающие имена стереотипов,
классификатор объекта не того вида, действие вызывает не деятельность, дорожка
представляет не классификатора, ссылка на взаимодействие ведёт не туда, линия
жизни представляет не классификатор, сигнатура сообщения называет несуществующую
операцию. Уровень у всех — «предупреждение», пункта UML нет вовсе, вместо него
`rationale`: почему такую модель труднее читать. Раздел появляется, только когда
в нём что-то есть.

Третий слой — **правила проекта** (`projectRules[]` в файле модели): условие по
белому списку полей и операторов без `eval`, свой счётчик `· проект N`. Это
договорённость команды, а не требование UML, и в «предупреждения» стандарта она
не подмешивается. Разбор — `app/RULES-COVERAGE.md` §5, как читать — `docs/uml/validation.md`.

Где смотреть:

| Что | Файл |
|---|---|
| текст правил, пункты, OCL | `app/notation/rules/uml-2.5.1.json`, `practice.json` |
| проверки (по функции на `check`) | `app/src/rules/*.js`, реестр — `registry.js` |
| невыразимые и чего не хватает | `app/src/rules/coverage.js` |
| правила проекта: формат и проверка | `app/src/rules/dsl.js`, `project.js` |
| панель, кнопка «Проверить», список «не проверяется» | `app/src/ui/checks.js` |
| объяснение покрытия по пунктам | `docs/RULES-COVERAGE.md`, `app/RULES-COVERAGE.md` |
| тесты движка и фикстуры | `app/tests/rules.mjs` (число проверок печатает прогон) |

Проверки ничего не блокируют: движок только читает модель, поэтому файл с
нарушениями сохраняется и открывается как обычный. Строка замечания стандарта
показывает уровень, сообщение, что именно нашлось, подсказку и кнопку с номером
пункта — она открывает дословный текст констрейнта, его OCL и страницу офлайн, а не
уводит в интернет. Клик по строке выделяет виноватый объект и, если его вид на
другом листе, переключает лист. «Только ошибки» убирает предупреждения и слой
практики целиком. Правило без функции в реестре и не записанное невыразимым —
ошибка загрузки набора, а не тихий пропуск: она видна в панели и в статусбаре
(`проверки: —`), а модельер продолжает работать.

**Сбой проверки не выдаётся за нарушение.** Правило, бросившее исключение на
кривых данных, отключается до конца прогона, а остальные правила отрабатывают:
раньше одно падение отменяло весь прогон и панель показывала пустоту — то есть
«0 нарушений» при непроверенной модели. Запись о сбое (`status: 'failed'`,
`app/src/rules/finding.js`) идёт отдельным разделом «Проверки, которые не
выполнились»: у неё нет ни кнопки пункта, ни перехода к объекту — винить некого,
правило не дошло до разбора элементов. В счётчик нарушений она не входит, но и не
прячется: статусбар получает хвост `· не проверено N`, бейдж кнопки считает
сбои, а «все чисто» при упавшем правиле не пишется — вместо него «Нарушений не
найдено среди отработавших правил». Разбор — `app/src/rules/engine.js`, `run`.

**Цикл показывается путём, а не симптомом.** У `generalization-cycle` (9.9.4.8) и
`usecase-include-cycle` (18.2.5.6) `targets` — это весь путь обхода
(`[A, B, C]`, для петли `[A]`), а `detail` называет его словами: «Цикл обобщения:
«A» → «B» → «C» → «A»». Замечаний по-прежнему по одному на каждый элемент цикла,
путь у каждого начинается с него — панель ведёт к первому, а в подробностях видна
вся цепочка. Обход общий для обоих правил: `app/src/rules/cycle-path.js`.

## 5. Справочник: полки, поиск, F1, «Оригинал / Русский»

Читалка живёт **внутри `#center`, соседом листа** (`app/src/ui/reference.js`,
разметка — `#ref` в `app/index.html`): текст и диаграмма видны одновременно,
рисовать можно, не закрывая статью. Это не четвёртая вкладка справа и не модальное
окно. Кнопка в шапке — переключатель; `Esc` закрывает.

### 5.1 Шесть полок

Список — `SHELVES` в `reference.js`, счётчики — из данных полки.

| Полка | Что на ней |
|---|---|
| **Нотация** | 51 фигура и 27 связей: что рисует каждая и чем отличается от соседа |
| **Правила** | те же 25 ограничений UML 2.5.1 с сообщениями и подсказками |
| **Спецификация** | полный текст стандарта: 25 разделов, 3 690 пунктов |
| **Пособие** | 20 упражнений учебника — как построить модель шаг за шагом |
| **Стереотипы** | 428 записей профиля Visual Paradigm, по базовым типам |
| **PlantUML** | 169 конструкций языка: как то же самое записать текстом |

Клик по названию полки открывает её **указатель** — страницу, где перечислено всё,
что на полке лежит (пустой id у полки означает именно «полка целиком», а не
ошибку). Битая ссылка даёт внятное «не найдено», а не пустую страницу.

### 5.2 Поиск

Поле — в шапке читалки, ищет **сразу по всем шести полкам**. Русский запрос
разворачивается в английский таблицей псевдонимов (`reference/terms.json`), потому
что в спецификации нет ни одного кириллического словоупотребления: «квалификатор»
и «qualifier» ведут в один и тот же пункт 9.5.3. Выдача идёт порциями по 40 строк,
с переходом к статье.

### 5.3 F1 — справка по выделенному

`F1` на выделенной фигуре или связи открывает **статью нотации этого вида**
(`openNotation(kind, key)`): для фигуры — по `element.kind`, для связи — по
`relation.kind`. Выделение и лист при этом не трогаются — ровно ради этого читалка
стоит рядом. Если статьи нет, в статусбаре появляется строка «F1: статьи нотации
для «X» нет», а не пустая панель. `preventDefault` обязателен: иначе браузер
откроет свою справку и уведёт со страницы.

### 5.4 Переключатель «Оригинал / Русский»

Стоит в шапке статьи полки «Спецификация». Переключается **файл, а не место**: у
перевода те же id статей, что у оригинала, поэтому «Русский» открывает
`reference/spec-ru/<NN>.json` той же статьёй. Метка «неофиц. перевод» стоит только
там, где на экране правда русский текст. Если пункта в переводе нет — показывается
оригинал и одна строка «перевода этого пункта нет»: перевод необязателен, оригинал
обязан открываться и без него. Выбор помнится в `localStorage` (`ref.lang`) и в
файл модели не уезжает.

### 5.5 Режимы раскладки

Кнопка в шапке читалки переключает три состояния по кругу: **рядом** (лист +
420 px), **страница** (статья 480 + оглавление 200), **широко** (инспектор скрыт:
дерево 200 + статья 480 + оглавление 200). Если после открытия листу осталось бы
меньше 360 px, читалка не открывается и говорит почему.
