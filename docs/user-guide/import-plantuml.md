# Импорт PlantUML — что читается, что теряется

> **Итог.** `.puml` читается в `uml-model/3` настоящим разбором по грамматике,
> вынутой из `plantuml.jar`: **115 конструкций из 169** переносятся в модель,
> **15** распознаются и осознанно отбрасываются (цвет, ссылка, `hide`), **39**
> не поддержаны и уходят в отчёт построчно. Раскладку импорт **не делает** —
> он ставит фигуры ровной сеткой в порядке объявления, и дальше двигает человек.

Написано по Э7 плана `PLAN-FULL` §7 (приватные заметки). Экспорт
(`material/plantuml-export/`, `docs/user-guide/export-plantuml.md`) с тех пор поправлен по
итогам кругового теста: навигация «к началу» пишется стрелкой, концы связей
больше не переставляются, а всё, что в текст не выразить, называется в файле
комментарием `' ! …` (§4 ниже).

---

## 1. Что сделано

| Файл | Что делает |
|---|---|
| `app/src/io/plantuml.js` | `parse(text) → {model, warnings, frames, blocks}`. Чистая функция: без DOM, без сети, без Java. Детерминирована — один текст даёт побайтово ту же модель |
| `app/src/io/plantuml-layout.js` | `seed(model, {frames, blocks})` — затравочная раскладка. Те же числа, что в `mechanics.json`, никакой оптимизации |
| `app/src/ui/import-puml.js` | «Файл → Импорт PlantUML…», «вставить текст», слияние в **новый лист** текущей модели, тост с итогом и кнопкой «Подробности» |
| `app/tests/plantuml-import.mjs` | 24 проверки: разбор, круговой тест 48 моделей, устойчивость `parse → emit → parse`, оракул jar, намеренная поломка, инварианты раскладки, таблица покрытия 169 конструкций |
| `docs/user-guide/import-plantuml.md` | этот отчёт |

Импорт ничего не заменяет: он добавляет лист к открытой модели, id при
столкновении переиздаются, существующие элементы и связи не трогаются.

## 2. Грамматика: 115 из 169

Источник — `docs/plantuml-grammar.json` (169 конструкций, вынуты рефлексией из
`plantuml.jar` 1.2021.00). Таблица «id → статус → минимальный пример» лежит в
`app/tests/plantuml-import.mjs` (`FORMS`), и проверка **G1** сверяет её с
грамматикой: ни одной выдуманной конструкции, ни одной пропущенной, а **G2**
прогоняет каждую строку через парсер и требует заявленного поведения.

| Семейство | Всего | Читается | Отброшено с причиной | Не поддержано |
|---|---:|---:|---:|---:|
| class | 55 | 42 | 8 | 5 |
| sequence | 42 | 23 | 5 | 14 |
| activity | 46 | 30 | 0 | 16 |
| usecase | 13 | 9 | 1 | 3 |
| state | 13 | 11 | 1 | 1 |
| **итого** | **169** | **115** | **15** | **39** |

«Отброшено с причиной» — это оформление, у которого в нашей модели нет поля:
`class Foo #red`, `[[ссылка]]`, `$метки`, `hide members`, `newpage`, `box`.
Такая строка не молчит: она попадает в отчёт как «оформление не переносится».

### Что не поддержано (39) и почему

| Группа | Конструкции | Почему |
|---|---|---|
| Внешние стрелки кадра | `[->`, `->]` | у нашей модели нет «внешнего» участника; стрелка уходит в отчёт |
| Якоря и разделители | `{a} <-> {b}`, `== Phase ==`, `...`, `\|\|\|`, `divider` | оформление последовательности, не данные |
| Сокращения активации | `Alice++`, `autoactivate on`, `return text` | активация у нас — элемент, а не знак в строке; сокращение неоднозначно |
| Заметки на связи | `note on link`, `note across` | в модели заметка не крепится к связи |
| Фигуры-«флажки» | `() :User:`, `<> Foo`, `(A)`, `circle`, `diamond` | в нашей нотации таких фигур нет (кроме `circle`→вариант использования) |
| Управление выводом | `remove Foo`, `layout_new_line`, `skin rose`, `footbox on`, `ignore newpage` | это команды отрисовки PlantUML, а не UML |
| Деятельность | `repeat`, `switch/case`, `split`, `group`, `partition`, `goto`, `label`, `backward`, `break`, `link/nolink` | наша модель деятельности хранит граф, а эти формы задают его иначе; перенос без потерь невозможен, поэтому честнее не читать |
| State | `--` (параллельные регионы) | регионы в модели есть, но `--` не говорит, где кончается регион |
| Usecase | `archimate` | другая нотация |
| Ссылки | `url of X is` | у элемента нет поля URL |

Каждая такая строка даёт `warnings` с номером и текстом — приложение не падает и
не молчит.

## 3. Затравочная раскладка: не автораскладка

Правила (реализация — `app/src/io/plantuml-layout.js`):

1. **Порядок — порядок объявления.** Никакой сортировки: человек ищет фигуры там,
   где написал их сам.
2. **Один уровень — один ряд**, шаг `ширина + 40`. Ряд переносится только если
   лист станет шире 1400 px — это предел страницы, а не оптимизация.
3. **Вложенное — внутрь рамки**: пакет/граница растёт под содержимое, дети стоят
   в своём ряду с отступом 20.
4. **Связи не участвуют в раскладке вообще.** Наличие стрелки не двигает ни одну
   фигуру — это и есть обещание («программа не двигает фигуры ради красоты
   линий»).
5. **Последовательность**: линии жизни в ряд с шагом 80, сообщения вниз с шагом
   30 — этот `y` не украшение, а порядок сообщений (модель хранит порядок как
   вертикаль). Фрагмент — прямоугольник вокруг накрытых сообщений.
6. **Деятельность**: дорожки колонками по 200, узлы вниз с шагом 120.
7. **Состояния**: вертикальная цепь с шагом 140.

Числа — все из `mechanics.json`, и каждое несёт свой вид источника
(`app/MECHANICS.md` §21): **code** — сетка 10 (`v/dap/r#<init>`), шаг линий 80 и
шаг сообщений 30 (`v/dal/ak#<init>+0x0025/+0x002b`, там же видно, что
относительные расстояния 0 = «авто»); **record** — класс 190×170, пакет
140×100, заметка 80×70, подпись имени 14, линия жизни 120/шапка 40/актёр 70,
подпись фрагмента 18; **decision** — шаг деятельности 120, дорожка 200, шаг
состояний 140, зазор 40, отступ рамки 20, лист 720×440, перенос 1400. Решение
это не отговорка: у оригинала своей раскладки нет вообще (его же образец
деятельности стоит на y 53/171/269/382, промежутки 118/98/113), а Auto Layout
он держит в отдельном блоке `v/dap/o` — ровно та автораскладка, от которой
владелец и уходит. Единственное осознанное расхождение с `notation/uml.json` —
дорожка шириной 200 вместо 420: иначе две дорожки налезают друг на друга; это
зафиксировано в проверке F4.

Где правило было неоднозначным, выбрано самое тупое:

* актёры **не** выносятся в левую колонку, хотя §7.2 плана это предлагает:
  порядок объявления важнее «красивой» композиции;
* `ref over` ставится на полосу сообщения (иначе экспорт не найдёт его концы);
* заметки — отдельным рядом под содержимым;
* при переполнении ряда — перенос, а не ужатие.

## 4. Круговой тест: 48 моделей корпуса

Метод (`app/tests/plantuml-import.mjs`, секция B, и `material/plantuml-export/roundtrip.mjs`):

```
model → emit() → .puml → parse() → seed() → model'
```

Сравнивается **смысл**, а не координаты: элементы по видам, имена,
стереотипы, `abstract`, члены с видимостью/типом/значением/флагами; связи по
видам, концам, кратностям, ролям, навигации, стереотипу. Раскладка намеренно
другая и в сравнение не входит.

| Результат | Было | Стало |
|---|---:|---:|
| Совпало полностью (строгий знак равенства) | 25 из 48 | **44 из 48** |
| Разошлось **только** в полях, которых нет в тексте | 22 | 3 |
| Не сравнимо (граф деятельности не дерево) | 1 | 1 |
| **Расхождений по вине импорта** | **0** | **0** |

**Оба пробела импорта закрыты:** `parseSequence` больше не выбрасывает
`stereotypes`, а `ARROW_FORMS` знает `'<-->'`. Экспорт соответственно начал
писать `<<стереотип>>` у участника (18 файлов) вместо предупреждения о потере.

### Что именно разошлось и почему

| Причина | Моделей | Поле | Чья сторона |
|---|---:|---|---|
| `abstract` у актёра не выгружается | 1 (3201) | `actor.abstract` | **PlantUML**: `abstract actor` — синтаксическая ошибка в 1.2021 (проверено `-syntax` и `-tsvg`) |
| Навигация «в обе стороны» на конце с ромбом | 2 (5223, 5301) | `navigable` | **PlantUML**: головка на конце с ромбом невыразима — `o<-->`, `<o--`, `o<--` дают синтаксическую ошибку |
| Граф деятельности — не дерево | 1 (3402) | узлы/связи дублируются | **обе**: язык выражает деятельность деревом, модель хранит граф |

Все три невыразимы в PlantUML 1.2021, и каждая названа в файле строкой
`' ! …`, а `check.mjs` (фаза 4, 153 утверждения) требует, чтобы такая строка
была у каждой потери.

### Что исправлено по дороге

| Модели | Было | Стало |
|---|---|---|
| 3102, 3201 (навигация «к началу») | `e16 -- e5` — стрелка срезана, концы переставлены | `e5 <-- e16` — стрелка у своего конца, кратности не сдвинулись |
| 5223, 5301 («в обе стороны») | `e3 o--> e1` — концы переставлены, кратности потеряны | `e1 "1" o-- "0..1" e3` + комментарий о потере навигации |
| 18 моделей (линия жизни) | стереотип не выгружался, в файле — предупреждение | `participant e5 as "dao:IDBAccess" <<interface>>` |
| все виды, печатаемые как `class` | `abstract` только классу/типу данных | `abstract` пишется всем таким видам |

Проверка **B1** теперь зелёная: `24 ok, 0 fail · строго 44/48, объяснено 3,
пропущено 1, непонятно 0`.

### Что было нужно от импорта — выполнено

Обе правки сделаны 2026-11-06, и круг вырос с 26 до 44 из 48:

1. **Стереотип участника.** `parseSequence` теперь берёт `stereotypes` из
   `takeStereotypes()` и кладёт первый в `extra.stereotype`.
2. **Форма `<-->`.** Добавлена в `ARROW_FORMS`.

Проверено намеренной поломкой: удаление `'<-->'` роняет **A4** («каждый вид
связи читается своим видом»), но **не** B1 — экспорт эту форму не пишет,
поэтому корпус её не ловит.


### Что это значит для эксплуатации

Круг «модель → .puml → модель» **не теряет ничего из того, что попало в
текст**, и с этого момента экспорт ещё и не молчит о том, что в текст не
попало: каждая потеря — строка `' ! …`, а четвёртая фаза `check.mjs` падает,
если строка пропала. Потери, которые остаются, названы поимённо и объяснены —
все три невыразимы в языке PlantUML 1.2021, а не в нашем коде.

## 5. Устойчивость: `parse → emit → parse`

Проверка **C1**: для всех 54 эталонных `.puml` (48 корпусных + 6 синтетических)
повторный цикл даёт ту же модель. Единственное исключение — заметка на
диаграмме последовательности: сам экспорт заметок в последовательности не
пишет, поэтому на втором круге её нет (это потеря экспорта, не импорта).
Проверка **C2** идёт дальше и требует, чтобы повторный экспорт давал **тот же
текст** (сравнивается набор строк): 48 из 48 корпусных файлов.

Две оговорки, обе про фикстуры, а не про импорт:

* `3102.puml` и `3201.puml` сняты до того, как в модель добавили элемент `e10`:
  в файле есть связь `e3 --> e10`, но нет объявления `usecase e10`. Импорт
  такую строку пропускает с предупреждением (и не выдумывает класс `e10`).
  Синтетические фикстуры (смешанная диаграмма ссылается на фигуры по кавычкам,
  коммуникация рисует сообщения линиями без головки) нарочно не совпадут с
  нашей записью — их и не сравниваем.

## 6. Оракул jar

Проверка **D1**: каждый импортированный `.puml` выгружается заново и
прогоняется через `java -jar plantuml.jar -syntax`. Это отвечает на вопрос «мы
поняли текст так же, как PlantUML»: если наш повторный экспорт не разбирается,
значит мы прочитали конструкцию неверно. Сейчас — 54 из 54 без ошибок
(PlantUML 1.2021.00, OpenJDK 17).

Если Java или jar не найдены, проверка печатает `skip` и **не валит прогон**:
основной набор (`node tests/plantuml-import.mjs`, `types.mjs`, `smoke.mjs`)
работает без Java.

## 7. Намеренная поломка

Проверка **E1** берёт настоящий `plantuml.js`, вырезает из таблицы стрелок
`*--`, импортирует испорченную копию и требует, чтобы круг **упал**. Пока
падает так:

```
ok    E1 · испорченный парсер обязан провалить круговой тест — поймано: 1 композиций потеряно на 4401
```

Это защита от «тест зелёный, потому что ничего не проверяет».

## 8. Отчёт человеку

После импорта показывается тост:

```
Импортировано: 40 элементов, 35 связей, 3 строки пропущено   [Подробности]
```

«Подробности» открывает список: номер строки, текст строки, причина. В модель
попадает всё, что удалось прочитать; нечитаемое не молчит.

## 9. Как проверять

```bash
cd app
node tests/plantuml-import.mjs            # 24 проверки: разбор, круг, jar, поломка
node tests/plantuml-import.mjs --verbose  # + причины по каждой модели
node tests/types.mjs                      # 230 сценариев, включая 7 про импорт
node tests/smoke.mjs                      # 32 проверки через настоящий интерфейс
```

Java не обязательна; без неё D1 печатает `skip`.
