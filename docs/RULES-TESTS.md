## 1. Как запускать

```sh
node tests/rules/check.mjs            # прогон, код возврата 0 — всё сошлось
node tests/rules/check.mjs --verbose  # плюс каждое замечание с адресом
```

Зависимостей нет: Node читает `app/notation/uml.json` с диска, применяет его тем же
`applyPackage`, что и страница (`loadNotation` в браузере делает то же самое по HTTP), и
дальше работает настоящим `deserialize`/`serialize` из `app/src/io/umljson.js`. Приложение
не запускается и не правится.

Одно предупреждение Node (`MODULE_TYPELESS_PACKAGE_JSON`) — не ошибка: в `app/package.json`
нет `"type": "module"` (и не должно появиться без нужды), поэтому Node определяет формат
модуля по синтаксису. Так же ведёт себя `app/tests/smoke.mjs`.

### Как устроена фикстура

```json
{
  "schema": "uml-model/3",
  "id": "m-mult-upper-ge-lower",
  "name": "mult-upper-ge-lower — верхняя граница кратности меньше нижней",
  "elements": [ { "id": "e1", "kind": "class", "name": "Заказ",
                  "documentation": "Правило «mult-upper-ge-lower»: …\nUML 2.5.1, п. 7.8.8.8, констрейнт MultiplicityElement::upper_ge_lower: «The upper bound must be greater than or equal to the lower bound.»\nУ конца «Заказ» стоит кратность 5..2: …" },
                { "id": "e2", "kind": "class", "name": "Клиент" } ],
  "relationships": [ { "id": "r1", "kind": "association", "from": "e1", "to": "e2",
                       "fromMultiplicity": "5..2" } ],
  "diagrams": [ { "id": "d1", "name": "Диаграмма 1", "kind": "class",
                  "shapes": [ … две фигуры … ],
                  "links":  [ … одна связь … ] } ],
  "currentDiagramId": "d1"
}
```

- На диаграмме-заглушке одна фигура (правило про элемент) или ровно две (правило про
  связь); фигуры и связь нужны, чтобы модель открывалась в редакторе и нарушение было
  видно, а не только вычислимо.
- `documentation` **первого элемента** — пункт стандарта, имя констрейнта и его дословный
  текст; дальше — что именно нарушено в этой модели. Текст берётся из
  `docs/rules-uml-2.5.1.json` дословно, и `check.mjs` это проверяет (см. §2).
- Файлы канонические: `serialize(deserialize(x))` даёт те же байты. Поэтому в них нет
  пустых строк, `null` и значений по умолчанию — ровно как их пишет редактор.

## 2. Что доказывает прогон

85 проверок, все проходят. По каждому правилу с фикстурой:

| Утверждение | Почему оно нужно |
|---|---|
| `<правило>.json` читается `deserialize` с пустым `repairs` | нарушение семантическое, а не «файл не той схемы»; иначе движок ловил бы битый JSON, а не модель |
| `serialize(deserialize(x))` совпадает с файлом байт в байт | фикстура каноническая, а не «примерно такая»; заодно доказано, что она переживает круг чтения-записи |
| `documentation` содержит пункт, имя и дословный текст констрейнта | ссылка на стандарт не отстаёт от правила |
| в фикстуре не больше двух элементов и двух связей, по фигуре на элемент и по связи на связь | минимальность проверяется машинно, а не на глаз |
| проверка правила даёт ≥ 1 замечание на `<правило>.json` | правило действительно ловит нарушение |
| ни одна другая проверка не срабатывает на `<правило>.json` | нарушение одно: фикстура минимальна, а правила не подменяют друг друга |
| на `<правило>.ok.json` не срабатывает **ни одна** проверка | правило не срабатывает на пустом месте; движок, красящий всё подряд, здесь падает |
| 48 моделей корпуса дают 0 замечаний | контроль в обратную сторону: правильные диаграммы учебника не красятся |

Последняя строка — самая важная. Без неё набор фикстур доказывал бы только
чувствительность, а не избирательность. Корпус даёт 48 моделей, 197 связей и 0 замечаний;
два файла (5.2.10 и 5.2.18) загрузчик чинит, снимая связь с потерянным концом, — это долг
схемы из плана `PLAN-E2BIS` §3.2 (приватные заметки), а не нарушение правил.

### Побочные наблюдения из таблицы

- Правило `namespace-members-distinguishable` считалось непроверяемым («нужны сигнатуры
  операций»), но это верно только для перегрузки. Сигнатура операции в `uml-model/3`
  хранится **внутри** `name` (`updateStudent(st:Student)`), поэтому две перегрузки и так
  имеют разные имена и различимы, а два одноимённых атрибута — нет. Нарушение строится.
- Правило `stereotype-generalizes-stereotype` тоже проверяемо: в нотации есть фигура
  `stereotype` (`kind: "stereotype"`), то есть стереотип — полноценный элемент модели, а не
  только метка в поле `stereotype` у класса.
- Правило `actor-association-targets` проверяемо, хотя выглядит «про актёров и варианты
  использования»: запрещена любая цель, кроме варианта использования, компонента и класса.

## 4. Правила, которых в `uml-model/3` не выразить

> **Это состояние на момент заморозки прототипа, а не сегодняшнее.** Часть причин с тех
> пор перестала быть верной: поле появилось, правило переехало в реестр проверок или
> оказалось тавтологией схемы. Актуальный статус каждого констрейнта — `status` и
> `reason` в [`coverage.json`](../material/rules-coverage/coverage.json), сводка — в
> [`report.md`](../material/rules-coverage/report.md). Раздел оставлен как объяснение,
> почему прототип этих правил не проверяет: он заморожен. Примеры устаревших причин
> прямо здесь: §4.1 (`element-not-own-self`) и §4.3
> (`component-no-nested-classifier`) — оба правила в приложении **есть**, потому что
> владение в схеме появилось (`ownerId` и членство в регионе).

Причина у всех одна: нужного поля в схеме нет. Ниже — какого именно и где оно описано.
План `PLAN-E2BIS` §3 (приватные заметки) —
единственный список недостающих полей; здесь только ссылки на его пункты, без пересказа.

### 4.1 `element-not-own-self` — нет владения элементами

`elements` — плоский массив; у элемента нет `ownerId`, поэтому «пакет внутри себя» записать
нечем. Вложенность в схеме выражается только для диаграмм (`diagrams[].ownerElementId`), а
это владение видом, а не элементом. Нужен `ownerId` — PLAN §3.1, партия Б1.

### 4.2 `association-end-typed` — конец ассоциации всегда типизирован

Тип конца — это сам факт связи: `from`/`to` указывают на элементы. Связь с концом без
элемента загрузчик выбрасывает (`Связь N пропущена: её элемент не найден`), то есть
нетипизированного конца в модели не бывает. Нужен необязательный конец связи
(`from`/`to` = `null`); в плане он есть только для сообщений — PLAN §3.2.

### 4.3 `component-no-nested-classifier` — компонент ничего не содержит

То же отсутствие владения, что в §4.1: у компонента нет `nestedClassifier`. Нужен `ownerId`
— PLAN §3.1, партия Б1.

### 4.4 `package-element-visibility` — нет ни владения, ни видимости элемента

Здесь не хватает **двух** полей сразу: `packagedElement` (владение) и `visibility` у самого
элемента. Второго нет даже у членов вне их строки: видимость есть только у члена
(`{ vis, name, type, default }`), у элемента её нет вовсе. `ownerId` — PLAN §3.1; поля
видимости элемента в плане нет.

### 4.5 `stereotype-binary-association` — нет небинарных ассоциаций

Стереотип как элемент есть, но `memberEnd->size() = 2` выполняется всегда: у связи ровно два
конца. Нужен список концов (`memberEnd`) вместо пары `from`/`to`; в плане его нет.

### 4.6 `transition-same-container` — нет машины состояний и вложенности

Сравнивать нечего: `containingStateMachine()` не определён ни у состояния, ни у перехода —
регионов и вложенных состояний в схеме нет. Нужны `regions` у состояния и `local` у
перехода — PLAN §3.7, партия Б8.

### 4.7 `usecase-binary-association` — нет небинарных ассоциаций

То же, что §4.5, без стереотипа: `memberEnd->size() = 2` в схеме всегда.

### 4.8 Чего не хватает сверх плана

Четыре пробела всплыли именно из правил и в PLAN-E2BIS не перечислены:

| Пробел | Какое правило упирается | Комментарий |
|---|---|---|
| видимость **элемента** (`visibility` у элемента, не у члена) | `package-element-visibility` | в плане есть только видимость члена |
| необязательный конец **ассоциации** | `association-end-typed` | план делает `null`-концы только для сообщений (§3.2) |
| список концов ассоциации (`memberEnd`) | `usecase-binary-association`, `stereotype-binary-association`, `association-aggregation-binary-only` | пара `from`/`to` — это уже решение «все ассоциации бинарные» |
| кратность **члена** (атрибута, параметра операции) | `mult-upper-ge-lower`, `mult-lower-non-negative` | у члена есть `name/type/default`, кратности нет; PLAN §3.8 добавляет квалификаторы, но не кратность. Поэтому `appliesTo` этих двух правил поля `member` больше не называет: правило, обещающее проверить несуществующее поле, хуже честной границы |

## 5. Где стандарт пришлось толковать

Каждое толкование записано и в `check.mjs` рядом с проверкой. Ни одно не выдумано «под
фикстуру»: в каждом случае буквальное чтение OCL даёт заведомо неверный результат.

### 5.1 Границы берутся такими, какими их отдают запросы 7.8.8.7

`upperBound()` по стандарту — `if (upperValue=null or upperValue.unlimitedValue()=null) then 1
else upperValue.unlimitedValue() endif`, `lowerBound()` устроен так же. Значит, у
некорректной границы значение по умолчанию — **1**, а не «ничего». Отсюда два следствия:

- `1..1.5` нарушает только `upper_is_unlimitedNatural`: сравнение `upper_ge_lower` на нём
  сходится (1 ≥ 1). Так и выбраны фикстуры — одна опечатка, одно правило;
- модель может нарушить и два правила сразу, и это не двойной счёт: `3..1.5` даёт
  `upper_is_unlimitedNatural` (1.5 — не `UnlimitedNatural`) и `upper_ge_lower` (1 < 3).
  Движок обязан сообщить оба: оба констрейнта действительно нарушены.

Пустая строка и текст без цифр (см. §5.2) — другое дело: это отсутствие кратности, и ни одно
из четырёх правил к ней не применяется.

### 5.2 Строка без цифр в поле кратности — не кратность

Корпус пособия пишет в `fromMultiplicity`/`toMultiplicity` текст «не названо в тексте» —
пометку «в тексте не сказано» (`4103.json`, `4203.json`). Это не значение кратности, и
правила кратности такую пометку не судят. Признак: в строке нет ни одной цифры (и это не
`*`). Иначе движок ругался бы на честную пометку источника.

### 5.3 `composite-upper-bound-le-1`: проза и OCL противоречат друг другу

Проза: «A multiplicity on the **composing end** … must not have an upper bound greater than
1». OCL рядом: `isComposite and association <> null implies opposite.upperBound() <= 1` — то
есть про **противоположный** конец. Это расхождение внутри самого стандарта, а не наше
чтение: `isComposite` стоит на конце-целом (9.9.17: «the object containing the attribute is a
container for the object or value contained in the attribute»), значит `opposite` — конец-часть,
и буквальный OCL запретил бы обычную
композицию «1 ◆—— 0..\*», где у части верхняя граница как раз больше 1. Выбрано: проверяем
конец с ромбом (проза + `message`/`hint` правила). Если когда-нибудь понадобится чтение по
OCL, менять придётся одну строку в `composite-upper-bound-le-1` и одну фикстуру.

### 5.4 `namespace-members-distinguishable`: пространство имён — сам элемент

Вложенности элементов нет, поэтому пространство имён — это элемент, владеющий членами, а
«метакласс» члена — его полка: два атрибута — два `Property`, атрибут и операция —
`Property` и `Operation`. По `isDistinguishableFrom` (7.8.9, `NamedElement`) члены разных метаклассов
различимы при любых именах, поэтому дубли ищутся внутри одной полки. Сигнатура операции
лежит в `name`, поэтому перегрузки различимы, как и требует
`BehavioralFeature::isDistinguishableFrom`.

### 5.5 `usecase-no-association-to-usecase`: субъект не выражается

OCL: `usecases->size() > 1 implies usecases->collect(subject)->size() > 1`. Поля `subject` в
схеме нет, поэтому `collect(subject)` пуст, `size()` даёт 0, и **любая** ассоциация между
двумя вариантами использования оказывается нарушением: субъект у них один — не задан ни у
кого. Это же и советует `hint` правила. Проверка написана так, что при появлении `subject`
она станет точнее без переписывания: разные субъекты — не нарушение.

### 5.6 `actor-association-targets`: вид элемента → метакласс

`oclIsKindOf` требует метамодели, а у нас вид нотации. В `check.mjs` есть маленькая таблица
`METACLASS`/`SUPERCLASS` (класс, компонент, узел, устройство, интерфейс, перечисление,
стереотип, актёр, вариант использования…). Из неё следуют два неочевидных вывода:

- **компонент — вид класса** (`Component → Class`), поэтому проза «UseCases, Components, and
  Classes» и OCL сходятся;
- **актёр — не класс** (`Actor → BehavioredClassifier → Classifier`), поэтому ассоциация
  «актёр — актёр» нарушает и OCL, и прозу, хотя интуитивно кажется допустимой.

Виды, которых в таблице нет (пакет, состояние, объект, заметка), проверка пропускает: их
типизация — предмет отдельного разговора о метамодели, и выдумывать за неё вердикт нельзя.

### 5.7 `association-aggregation-binary-only`: проверяема только половина

Проза говорит про арность («Only binary Associations can be aggregations»), а арность в
схеме всегда 2 — эта половина невыразима (§4.5). OCL состоит из двух конъюнктов, и второй
(`memberEnd->exists(aggregation = AggregationKind::none)`) выразим: агрегация на обоих концах.
Фикстура проверяет именно его, и в сводке правило помечено как покрытое «только по OCL».

### 5.8 Кратности членов не проверяются

У члена в схеме нет поля кратности: она может быть только текстом внутри `type`
(`courses: Course[0..*]`). Разбирать тип как запись кратности — значит гадать по свободному
тексту, поэтому проверки смотрят только на концы связей. По той же причине из `appliesTo`
правил `mult-upper-ge-lower` и `mult-lower-non-negative` убрано поле
`member: ["attribute", "operation-parameter"]`: у члена в `uml-model/3` поля кратности нет
вовсе — `member()` это `{vis, name, type, default}`. У `mult-lower-is-integer` и
`mult-upper-is-unlimited-natural` поля `member` не было изначала: проверка литерала
относится к кратности на любом носителе, и это намеренно. Пробел записан в §4.8.

## 6. Что осталось за рамками

- **Движок, а не проверка в редакторе.** `check.mjs` — функции «модель → замечания»;
  панели проблем и правил «показывать/скрывать» в прототипе нет. В приложении панель есть
  (`app/src/ui/checks.js`), но она читает тот же набор и те же проверки.
- **Только правила слоя стандарта, и только те, что знает прототип.** Остальные
  констрейнты стандарта в прототип не извлекались — их счёт и причины
  ([`RULES-SOURCE.md`](RULES-SOURCE.md) §«Сколько констрейнтов»). Правила практики —
  не констрейнты стандарта: у них нет пункта, и в прототипе их нет вовсе.
- **Только `uml-model/3`.** Файлы `uml-model/2` и `uml-class-diagram/1` загрузчик переводит в
  третью версию, и проверки работают уже с результатом; сами миграции не тестируются.
- **Наборы обобщений** (`generalizationSets`) в правила не входят: констрейнтов
  `GeneralizationSet` в наборе нет.
