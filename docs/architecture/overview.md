# Архитектура UML Modeler

Правила, которые нельзя нарушать, и причины, по которым они такие.
Документ существует потому, что эти правила жили только в комментариях и в голове
автора: следующий агент, не прочитав их, ломает то, что работает.

**База:** `app/` · **Формат:** `uml-model/3` · **Проверки:** `tests/*.mjs`

---

## 1. Слои и направление зависимостей

```
util.js
  ↑
model/notation.js ──► model/model.js ──► model/geometry.js
                          ↑                    ↑
                    io/umljson.js              │
                    io/stereotypes.js          │
                    state/store.js ────────────┤
                          ↑                    │
                    ui/render.js ──────────────┘
                          ↑
                    ui/canvas.js ──► ui/panels.js
                          ↑              ↑
              ui/toolbar.js · ui/toolstrip.js · ui/commands.js · ui/dialog.js
                          ↑
                       main.js
```

Замерено: **19 модулей, 74 связи импорта, 0 циклов.**

| Слой | Знает про | НЕ знает про |
|---|---|---|
| `model/` | только себя и `util.js` | DOM, состояние, UI |
| `io/` | `model/` | DOM, UI |
| `state/` | `model/` | DOM, UI |
| `ui/` | всё ниже | — |
| `main.js` | всё | — |

**Правило:** импорт идёт только вверх по стрелкам. `model/` не может импортировать
`ui/`, `io/` не может импортировать `state/`. Если понадобилось — значит логика
лежит не в том слое.

`model/` — чистые данные и вычисления: одна и та же модель даёт одну и ту же
геометрию. Поэтому её можно тестировать без браузера и переиспользовать в экспорте.

## 2. Нотация — данные, а не код

`notation/uml.json` описывает **51 фигуру, 27 связей, 14 типов диаграмм**.
Рендерер выбирает функцию по полю `style`:

```js
// src/ui/render.js
const fn = RENDERERS[def.style] ?? renderClassifier
```

**Правило:** новый тип диаграммы или новая фигура добавляются записью в
`notation/uml.json`, а не ветвлением в рендерере. Если для фигуры нужен новый
способ рисования — добавляется новый `style` в таблицу `RENDERERS`, и он
переиспользуется всеми фигурами с этим `style`.

`notation/index.json` перечисляет пакеты; сейчас он грузит ровно один — `uml`.
Второй пакет не создаётся: все 14 типов живут в одном файле, потому что у них
общая метамодель (как `MODEL_ELEMENT` в `.vpp`).

## 3. Модель отделена от вида

```
elements[]        — что существует: имя, тип, стереотип, члены, tagged values
relationships[]   — связи между элементами
diagrams[].shapes[] — где и какого размера фигура; хранит ТОЛЬКО elementId и геометрию
diagrams[].links[]  — вид связи; хранит relId и маршрут
```

**Следствия, которые обязаны сохраняться:**

- переименование элемента — одна правка, видно на всех диаграммах;
- `Delete` на фигуре снимает **вид**, элемент и его связи остаются;
- `Shift+Delete` удаляет **элемент** со всеми видами, связями и вложенными диаграммами;
- одну связь можно показать на нескольких диаграммах.

**Правило:** фигура не хранит имя, стереотип и члены. Если код читает `shape.name` —
это ошибка: имя живёт в `elementOf(model, shape)`.

## 4. Детерминированность — инвариант, а не пожелание

Одна и та же модель даёт **побайтово одинаковый** `*.uml.json` и **одинаковую**
картинку. Это проверяется тестом («файл пересохраняется байт в байт»).

Из этого следует:

- ключи сериализуются в фиксированном порядке (`MODEL_KEYS`, `ELEMENT_KEYS`,
  `REL_KEYS`, `DIAGRAM_KEYS`, `SHAPE_KEYS`, `LINK_KEYS` в `src/io/umljson.js`);
- необязательное поле с пустым значением **не пишется вообще**, а не пишется как `null`;
- порядок вычисляется, а не хранится: номер сообщения на Sequence — это его `y`,
  перетащили выше — номер пересчитался.

**Правило:** нельзя добавлять поле в сериализацию, не добавив его в список ключей
и в тест на побайтовое совпадение.

## 5. Числа — только из листа механики

`mechanics.json` (~65 значений) — единственный источник размеров, толщин, цветов и
отступов. `build.mjs` превращает нужные из них в `src/mechanics.generated.js`,
откуда их берут `theme.js` и `canvas.js`.

**Правило:** не хардкодить в CSS и JS число, которое уже есть в листе. Если числа
нет — добавить его в `mechanics.json` **с источником** (адрес в коде VP, запись в
`.vpp`, файл и строка) или пометить `estimated: true`. Запись «reference screenshot»
без файла в `reference/` недопустима.

Каждое значение обязано быть либо измеренным, либо честно помеченным. Проверка
Craft Anything считает «число встречается в коде» — это **не** проверка
правильности источника.

## 6. Чего нельзя делать

| Нельзя | Почему |
|---|---|
| Править файлы в `ui-kit/` и `sync-kit/` | это вендорные копии; своё — в `src/brand/brand.css` переопределением переменных |
| Удалять `ui-kit/fonts/licenses/` | шрифты свободные, но лицензии обязаны ехать вместе с ними |
| Хардкодить числа раскладки | см. §5 |
| Добавлять зависимости, сборщик, транспиляцию | приложение — чистые ES-модули, работает офлайн через `./serve.sh` |
| Менять `SCHEMA` без функции миграции | старые файлы (`uml-model/2`, `uml-class-diagram/1`) обязаны открываться |
| Хранить смысл в фигуре | см. §3 |
| Копировать графику Visual Paradigm | иконки рисуются в VectorCraft (`tools/make-icons.py`) |

## 7. Где что лежит

```
app/
├── index.html            оболочка: панели, полоса инструментов, вкладки
├── build.mjs             «сборка» = копия сайта в dist/ + mechanics.generated.js
├── serve.sh              статический сервер; --screenshot снимает окно
├── mechanics.json        лист чисел с источниками
├── MECHANICS.md          разбор источников (адреса в коде VP и записях .vpp)
├── README.md             что умеет, палитры типов, формат файла
├── notation/
│   ├── index.json        список пакетов (сейчас один: uml)
│   └── uml.json          51 фигура, 27 связей, 14 типов, стили, ключи
├── material/
│   ├── stereotypes.xml   профиль: 428 стереотипов, 98 tagged values
│   └── uml-scope.json    область переноса (что входит в UML 2.5)
├── reference/vp163/      54 рисунка пособия — материал для корпуса и курса
├── src/
│   ├── main.js           точка входа: клавиши, файлы, старт
│   ├── util.js           DOM/SVG-билдеры, текст, скачивание
│   ├── styles.css        раскладка приложения
│   ├── brand/            brand.css (одна переменная --brand) + 172 SVG + Inter
│   ├── model/            notation · model · geometry · sample
│   ├── io/               umljson (сериализация и миграции) · stereotypes
│   ├── state/            store: состояние, undo/redo, автосохранение
│   └── ui/               render · canvas · panels · toolbar · toolstrip · commands · dialog · icons · theme
├── tests/
│   ├── smoke.mjs         45 проверок интерфейса
│   ├── types.mjs         275 проверок по 14 типам и правилам модели
│   └── inspect.mjs       диагностика одного типа: "model=all&diagram=state"
└── tools/
    ├── make-icons.py     генератор иконок через VectorCraft
    └── icons.vectorcraft редактируемый исходник набора
```

`app/dist/` (сборка, `node build.mjs`) и `__pycache__/` — артефакты, в `.gitignore`.
Снимки-доказательства лежат отдельно, в корневом `shots/`, и хранятся намеренно.

## 8. Проверки перед любой сдачей

```sh
cd app
node build.mjs          # сборка
node tools/verify.mjs   # всё разом: 18 наборов + сверка src↔dist + эталон
node tests/smoke.mjs    # 45 проверок интерфейса
node tests/types.mjs    # 275 проверок по типам
./serve.sh --screenshot /tmp/out.png
```

Тесты поднимают локальный сервер и headless-Chromium по CDP, без зависимостей.
`tests/*.mjs` грузят `index.html`; отдельной тестовой оболочки нет.

**Известный дефект:** `./serve.sh --screenshot` снимает страницу до отрисовки
(ветка `chrome-headless-shell` в `Build/uml-modeler` не передаёт
`--virtual-time-budget`). Порог приёмки — размер файла, а почти пустой PNG его
проходит. Проверка «программа рисует окно» поэтому проходит ложно.
