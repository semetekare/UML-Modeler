# Соединители draw.io: как устроены и что из этого делать нам

Исследование для нашего UML-редактора (vanilla JS + ES-модули + SVG).
**Кода draw.io здесь нет** — только измерения, формулы и выводы, переписанные своими словами.

Пометки: **[факт]** — проверено на файле, на стенде или в коде с указанием места;
**[гипотеза]** — следует из кода/наблюдения, но прямым экспериментом не подтверждено.

Версия документа: 2 (пересобран после повторных замеров). Что изменилось против версии 1:
перетаскивание сегмента **измерено** и оказалось другим, чем считалось (§4.5 — версия 1
ошибалась); добавлены замеры подписей, петель, `jettySize`, 12 конфигураций маршрутизации на
каждую из 7 стратегий, 16 пар фиксированных сторон; меню раскладки и её диалог разобраны
в живом продукте 32.6.10.

## 2. UX-паттерны

### 2.1 Курсоры над линией — измерено в живом продукте

| Наведение | Курсор | Доказательство |
|---|---|---|
| на горизонтальный сегмент ребра | `row-resize` (⇕) | `screenshots/live-01-before.png`, замер `elementFromPoint` → `path`, `cursor=row-resize` |
| на вертикальный сегмент | `col-resize` (⇔) | код: `b.setCursor(e?'col-resize':'row-resize')`, где `e` — «x концов равны» |
| на пустой холст | `default` | замер |

Почему это важно: `row-resize` над горизонтальным сегментом — это обещание «этот сегмент
можно тянуть по вертикали». Так продукт сообщает, что **сегмент — цель перетаскивания**,
а не только точки. И это подтверждается кодом обработчика (§4.5), который для ортогональных
рёбер двигает сегмент целиком.

### 2.2 Состояние → действие → реакция → итог

| # | Начальное состояние | Действие | Реакция | Итог |
|---|---|---|---|---|
| 1 | ребро не выделено | клик по линии (±4.5 px) | линия выделена, появились управляющие точки | `getSelectionCells() = ["e1"]` — **замерено** |
| 2 | ребро выделено | появление «виртуальной» точки на середине каждого сегмента | полупрозрачная точка, курсор `row/col-resize` | код `createVirtualBends` |
| 3 | тянем середину сегмента **ортогонального** ребра | движение | сегмент едет целиком: обе ограничивающие точки смещаются на одну величину, новых точек не появляется | **замерено** (§4.5): вертикальный сегмент +30 по x → обе точки `x=270`; горизонтальный +30 по y → обе `y=430` |
| 4 | тянем середину сегмента **прямого** ребра (`edgeStyle=none`) | движение | в геометрию вставляется **одна** новая точка в месте отпускания | **замерено**: было `points: []`, предпросмотр `[(335,300)]` |
| 5 | тянем существующую точку | движение | двигается только она | обработчик: индекс → одна точка |
| 6 | точка отпущена поверх другой точки | — | лишняя точка удаляется | `getPreviewPoints`, ветка `mxUtils.contains(...)` → `splice` |
| 7 | точка отпущена почти на прямой между соседями + Alt (`straightRemoveEnabled`) | — | точка удаляется, линия выпрямляется | тот же код |
| 8 | тянем конец ребра на фигуру | — | конец прилипает, в стиль пишутся `exitX/exitY/exitDx/exitDy` | модель + §3.1 |

**Ограничение этого исследования, честно:** строки 3, 4, 5 получены вызовом того же
обработчика, который продукт создаёт для ребра (`graph.createHandler(state)` →
`mxEdgeSegmentHandler`/`mxEdgeHandler`), а не движением мыши. Курсор над сегментом измерен
живьём и совпадает с тем, что обещает код. Прямого «до/после» с мышью нет — это записано
открытым вопросом в проекте.

### 2.3 Чего в UX нет

- Нет модального «выберите тип соединения»: тип определяется тем, куда попал курсор.
- Нет отдельного режима «рисовать связи»: связь тянется из точек-портов, которые появляются
  при наведении на фигуру (синие стрелки/крестики на границе) — [факт по скриншотам и по
  `mxConnectionHandler`, поведение портов не измерялось численно].
- Нет предупреждения при раскладке, которая стирает ручные изгибы (§9).

## 3. Геометрическая модель

### 3.1 Концы: доля рамки + смещение (главная находка)

Ребро хранит конец не как точку на границе, а как **долю от рамки фигуры плюс смещение**:

```
d.x = bounds.x + point.x * bounds.width  + dx * view.scale
d.y = bounds.y + point.y * bounds.height + dy * view.scale
if (constraint.perimeter) d = getPerimeterPoint(state, d)   // спроецировать на границу
if (round) d = (round(d.x), round(d.y))                     // ВСЕГДА округление до целых
```

Дословно из `mxClient.js` (20.8.3), `mxGraph.prototype.getConnectionPoint`:

```js
d = new mxPoint(e.x + b.point.x * e.width + b.dx * d,
                e.y + b.point.y * e.height + b.dy * d);
...
if (b.perimeter) d = this.view.getPerimeterPoint(a, d, !1);
```

а флаг `perimeter` берётся так (`mxGraph.prototype.getConnectionConstraint`):

```js
d = mxUtils.getValue(a.style, STYLE_ENTRY_PERIMETER, true)   // по умолчанию TRUE
```

**Что это значит на практике** (замер на стенде, целевая фигура `B = (300,40,100,60)`):

| style | точка на конце `to` | смысл |
|---|---|---|
| `entryX=0.25;entryY=0.5` (без `entryPerimeter`) | `(300, 70)` | доля задаёт **направление** из центра, точка садится на границу |
| `entryX=0.25;entryY=0.5;entryPerimeter=0` | `(325, 70)` | доля задаёт **координату**: 300 + 0.25·100 |
| `entryX=-0.2;entryY=0.5;entryPerimeter=0` | `(280, 70)` | доля может выйти за 0…1 — конец «висит» снаружи фигуры |
| `entryX=0;entryY=0.5;entryDx=0;entryDy=10` | `(300, 80)` | смещение `dy` в пикселях добавляется после доли |

Отсюда три следствия, которых у нас нет:

1. **Конец переживает ресайз.** Доля `0.25` остаётся на четверти ширины при любой ширине.
   У нас конец задан `side + t` (`geometry.js:219`) и тоже переживает ресайз — но только для
   четырёх сторон и без смещения наружу.
2. **`entryPerimeter` — это переключатель «приколоть к рамке» против «положить в координату».**
   Продукт по умолчанию пишет `entryPerimeter=0`, то есть фиксирует точку.
3. **Округление до целых.** В файлах поэтому и лежат «странные» значения `0.904`, `-0.008`,
   `1.001`: это обратный пересчёт из округлённых пикселей. Значит при импорте нельзя ждать
   круглых дробей — надо принимать любые числа и не «исправлять» их.

### 3.2 Точки перегиба

- `<Array as="points"><mxPoint x="…" y="…"/></Array>` — упорядоченный список, **абсолютные**
  координаты (в системе родителя), а не доли. Подтверждается 185 рёбрами корпуса.
- `<mxPoint as="sourcePoint">` и `<mxPoint as="targetPoint">` присутствуют **даже у полностью
  привязанного ребра**. Это не «свободные концы», а кэш последних вычисленных точек.
- `noEdgeStyle=1` в стиле означает «маршрутизатор не трогай, вот эти точки и есть маршрут».
  Именно это дописывает авто-раскладка (§9).
- **Точки относительные или абсолютные?** По умолчанию абсолютные: переносишь фигуру — точки
  остаются на месте. Но есть стиль `followTerminals=1`: тогда при переносе концов точки
  пересчитываются (`Graph.getFollowedEdgePoints`, `app.min.js` 32.6.10, ≈ смещение 1 583 025).
  Для ортогонального ребра работает `getFollowedSegmentPoints` — каждая ломаная «растягивается»
  пропорционально смещению концов по своей оси; для остальных — `getFollowedAxisPoints` —
  точки переносятся по той же оси, что и конец. Если маршрут изменился так, что «тот же путь»
  не сохраняется, точки не трогают. **[факт по коду, мышью не проверял]**

Вывод для нашей модели: `waypoints` у нас уже абсолютные (`geometry.js:298–299`). Разница в
том, что у нас нет кэша `sourcePoint/targetPoint`, нет признака «маршрут фиксирован»
(у нас наличие `waypoints` само выключает автораскладку) и нет режима «точки следуют за
концами» — у нас точки всегда остаются в мире.

`baseDash, block, blockThin, classic, classicThin, diamond, diamondThin, doubleBlock, open,
openThin, oval`.

Меню стрелок продукта 32.6.10 (`Format.addLineMarkerItems`, `app.min.js` ≈ смещение 2 206 097)
перечисляет явно, в таком порядке (заливка и контур — отдельные пункты):

```
залитые:   classic, classicThin, open, openThin, openAsync, block, blockThin, async, oval,
           diamond, diamondThin
контурные: classic, classicThin, block, blockThin, async, oval, diamond, diamondThin, box,

```

Плюс два служебных пункта: **«нет маркера»** (`endArrow=none`) и **«скопировать с другого
конца»**. Итого 25 разных имён в 33 пунктах меню — [факт по коду; выпадающий список мышью
не пересчитывал].

Замеры (ребро `(120,60) → (300,60)`, размер по умолчанию):

| style | что нарисовано |
|---|---|
| `startArrow=none;endArrow=none` | **ни одного маркера**: `M 120 60 L 300 60` — линия без головок возможна |
| `endArrow=classic` | линия укорочена до `293.63`, маркер `M 298.88 60 L 291.88 63.5 L 293.63 60 L 291.88 56.5 Z` |
| `endArrow=block` | `M 298.88 60 L 291.88 63.5 L 291.88 56.5 Z` — простой треугольник |
| `endArrow=open` | маркер **не залит**, рисуется дважды (толстая подложка + штрих), линия до `297.76` |
| `endArrow=diamond` | `M 299.29 60 L 295.79 63.5 L 292.29 60 L 295.79 56.5 Z` — ромб длиной 7 |
| `startArrow=classic;endArrow=diamond` | **два разных маркера одновременно**, линия между ними |
| `endSize=4` / `endSize=16` | длина маркера 5 / 17 px (размер + толщина линии) |
| `endFill=0` | тот же путь, но без заливки (рисуется дважды) |

Насколько маркер «съедает» линию (расстояние от вершины маркера до конца штриха, ребро
`(160,70) → (340,70)`, толщина 1):

| маркер | classic | block | open | oval | diamond | diamondThin | doubleBlock | baseDash |
|---|---|---|---|---|---|---|---|---|
| срез, px | 10.87 | 14.12 | 2.24 | 6.00 | 13.71 | 13.99 | 27.12 | 0 |

Размер растёт линейно: `classic` при `endSize` 4/6/8/12/20 даёт срез 4.87/6.37/7.87/10.87/16.87
(это `0.75·size + 1.87`), и срез зависит от толщины линии: `classic` при `sw` 1/2/4 →
6.37/8.24/11.97.

Маркер всегда поворачивается по **последнему сегменту**: на вертикальном ребре путь
`M 280 158.88 L 276.5 151.88 L 280 153.63 L 283.5 151.88 Z` — вершина вниз.

**Как устроена семантика UML.** В draw.io её нет: `endArrow` — это про «где конец `to`»,
а ромб агрегации — просто ещё один маркер (`diamond`/`diamondThin` + `endFill=0/1`).
Продукт **не знает**, что ромб означает агрегацию; это знание живёт в палитре (пресеты стиля).

Итог по нашему Д1: draw.io здесь устроен ровно так, как нам надо — два независимых слота
(начало/конец), у каждого свой тип, размер и заливка, и ни один не вытесняет другой.
Ограничение ровно одно: **один маркер на конец**. Ромб и стрелка на одном конце одновременно
в draw.io не рисуются — это надо решать нам, своей моделью (см. §7.2).

### 3.4 Скругление: квадратичная дуга с обрезкой по половине сегмента

Алгоритм (из `mxShape.addPoints`, `mxClient.js`):

```
arcSize = getValue(style, 'arcSize', LINE_ARCSIZE=20) / 2      // = 10 px по умолчанию
для каждой внутренней вершины V с соседями P и N:
   t1 = min(arcSize, |V-P| / 2)      // отступить от V назад по PV
   t2 = min(arcSize, |V-N| / 2)      // отступить от V вперёд по VN
   L  V - u1*t1
   Q  V  V + u2*t2                  // контрольная точка — сама вершина
```

То есть: **не круговая дуга, а квадратичная кривая с вершиной в роли контрольной точки**, и
радиус обрезается **отдельно с каждой стороны** половиной прилегающего сегмента. Замеры:

| style | путь | радиус |
|---|---|---|
| `rounded=0` | `M 120 60 L 340 60 L 340 233.63` | — |
| `rounded=1` | `M 120 60 L 330 60 Q 340 60 340 70 L 340 233.63` | 10 |
| `rounded=1;arcSize=6` | `… L 337 60 Q 340 60 340 63 …` | 3 |
| `rounded=1;arcSize=40` | `… L 320 60 Q 340 60 340 80 …` | 20 (arcSize/2) |
| короткий средний сегмент 14 px | `… Q 200 60 200 67 L 200 70.5 Q 200 74 210 74 …` | 7 = половина |
| короткий средний сегмент 6 px | `… Q 200 60 200 63 L 200 64.5 Q 200 66 210 66 …` | 3 = половина |
| короткий средний сегмент 3 px | `… Q 200 60 200 61.5 L 200 62.25 Q 200 63 210 63 …` | 1.5 = половина |

Последние три строки — ответ на «что при коротком сегменте»: угол **не ломается и не
выворачивается**, радиус сжимается до половины короткой ноги, и оба конца короткого сегмента
сжимаются **независимо**. Образец скруглений: `samples/C5-rounded-corners.drawio.svg`.

Сравнение с нашим `pathD` (`geometry.js:332`): у нас радиус фиксирован (`small=6`, `large=16`,
`ROUND_R` в `geometry.js:310`), для углов до 90° рисуется настоящая дуга `A`, при обрезке —
`Q` с контрольной точкой в вершине. То есть **геометрия та же по смыслу**, но радиус не
настраивается числом: при `arcSize=40` draw.io даёт 20, мы максимум 16.

### 3.5 Кривая (`curved=1`)

Код `mxPolyline.paintCurvedLine` + замер:

```
M p0  Q p1 mid(p1,p2)  Q p2 mid(p2,p3) …  Q p[n-2] p[n-1]
```

Замер: `M 120 60 Q 340 60 340 233.63` — прямая связь из двух сегментов превращается в одну
квадратичную кривую, где **угол стал контрольной точкой**, а линия проходит через середины
сегментов. Никакого сглаживания по Катмуллу-Рому и никаких «узлов» — очень дешёвая операция.
Кривая включается и поверх ортогональной маршрутизации, при этом обработчик остаётся
сегментным (§4.5), то есть тянуть сегмент всё равно можно.

### 3.6 Подписи

Замер на стенде (ребро `A(60,60,80,40)` → `B(400,250,80,40)`, путь через две ручные точки):

| случай | путь | где оказалась подпись |
|---|---|---|
| ломаная, 3 сегмента длиной 120.9 / 190 / 140.9 | `(140,75)→(260,60)→(260,250)→(400,265.6)` | `(260, 165.1)` — ровно **половина полной длины пути**, а не середина среднего сегмента |
| неравные колена 440 / 280 / 213 | `(120,60)→(120,500)→(400,500)→(436.5,290)` | `(147, 500)` — снова половина длины (466.6 из 933.2) |
| та же ломаная + `offset = (-20, 15)` | — | `(240, 180.1)` = базовая точка + смещение |
| прямая | — | середина отрезка |
| длинный текст подписи | — | позиция **не зависит** от длины текста |

Плюс факты из модели:

- Подпись ребра — это `value` самой ячейки ребра; смещение — `<mxPoint as="offset" x y>`
  внутри геометрии. В корпусе таких нет: все рёбра без подписей.
- Подпись можно «оторвать»: тогда она становится **дочерней ячейкой ребра**
  (`parent=<id ребра>`), стиль `edgeLabel`, координаты — доля вдоль пути.
- В draw.io подпись **не поворачивается** по сегменту (замерено: `transform` без `rotate`).

У нас `labelPos(pts, ldx, ldy)` (`geometry.js:390`) считает середину **по длине пути** — правило
то же, что у draw.io. И мы дополнительно поворачиваем текст по сегменту; это лучше для UML,
но это наше отличие, а не «как в draw.io».

### 3.7 Петля на одной фигуре и связь с связью

Замеры на стенде (`A = (100,100,120,60)`):

| случай | абсолютные точки |
|---|---|
| петля `source == target`, `orthogonalLoop=1;jettySize=auto` | `(220,120) → (240,120) → (240,140) → (220,140)` |
| петля с фиксированными концами `exitX=0.5,exitY=0` и `entryX=0.25,entryY=0` | `(160,100) → (130,100)` — короткий хвост по верхней грани |

То есть петля — это **квадрат 20×20**, приставленный к грани фигуры и отцентрованный по её
середине (120…140 при центре 130). Размер не зависит от размера фигуры.

Связь с связью: ребро `e2` с `source = e1` (id ребра) допустимо и рисуется — `e2` начинается
**на пути** `e1`: замер `(210,220) → (210,400)` при `e1` из `(120,220)` в `(380,220)`.

Наш аналог петли уже есть для сообщений (`canvas.js:516–519`: квадрат 40×20). Для обычных
связей петля не поддержана.

## 4. Алгоритмы

### 4.1 Ортогональная маршрутизация (замерено)

Стенд: `A = (40,40,80,40)` (центр 80,60), `B = 100×60` в разных позициях, концы свободные.
Полная матрица — `raw/bench2.json`; здесь только то, из чего складываются правила:

| позиция B | `orthogonalEdgeStyle` | `elbowEdgeStyle` | `entityRelation` | `none` (прямая) |
|---|---|---|---|---|
| справа, по центру y | `(120,60) (210,60) (210,70) (300,70)` | то же | `(120,60) (150,60) (270,70) (300,70)` | `(120,61.5) (300,68.2)` |
| справа, y перекрыт | `(120,60) (210,60) (210,80) (300,80)` | то же | `(120,60) (150,60) (270,80) (300,80)` | `(120,63) (300,76.3)` |
| снизу, x перекрыт | `(80,80) (80,190) (110,190) (110,300)` | `(90,80) (90,190) (90,300)` | `(120,60) (170,60) (170,330) (140,330)` | `(82.2,80) (106.7,300)` |
| по диагонали (юго-восток) | `(120,60) (350,60) (350,300)` | `(120,60) (210,60) (210,330) (300,330)` | `(120,60) (150,60) (270,330) (300,330)` | `(100,80) (320,300)` |
| по диагонали (северо-запад) | `(40,60) (-170,60) (-170,-160)` | `(40,60) (-40,60) (-40,-190) (-120,-190)` | `(40,60) (10,60) (-90,-190) (-120,-190)` | `(60,40) (-140,-160)` |
| зазор 10 px по x | `(120,60) (130,60) (130,70) (130,70)` | `(120,60) (125,60) (125,70) (130,70)` | `(120,60) (150,60) (150,65) (100,65) (100,70) (130,70)` | `(120,64) (130,65)` |

Наблюдаемые правила (для своей реализации достаточно этих):

1. Конец без явной привязки садится в точку **пересечения линии центров с границей**
   (на стороне, обращённой к партнёру), на координате центра своей фигуры по второй оси.
2. Если проекции фигур на ось **перекрываются** — маршрут из четырёх точек: выход → перегиб
   ровно на **середине зазора** → сдвиг на координату центра цели → вход.
3. Если не перекрываются — одна точка перегиба на `(центр цели по x, центр источника по y)`
   для горизонтального направления (и симметрично для вертикального): три точки, без полки.
4. `elbowEdgeStyle` в тех же случаях входит в цель с **обращённой** стороны и ставит перегиб
   на середине зазора — то есть даёт на одну точку больше, но «полку» у цели.
5. `entityRelationEdgeStyle` — короткие полки по 30 px у каждой фигуры на координате центра
   и прямая диагональ между ними.
6. `edgeStyle=none` — прямая между центрами, обрезанная по границам.
7. `segmentEdgeStyle` на этих конфигурациях вёл себя как `orthogonalEdgeStyle`.

Проверка на 16 парах фиксированных сторон (`A → B` по диагонали, все комбинации W/E/N/S)
даёт ту же логику: `E→N` = `(120,60) (350,60) (350,260)` (горизонталь до центра цели, затем
вертикаль), `W→E` = обход слева и вход справа с отступом 10 px:
`(40,60) (30,60) (30,170) (410,170) (410,290) (400,290)`. Полная таблица — §11.

**[гипотеза]** Точное правило выбора «середина зазора против центра фигуры» в
`mxEdgeStyle.OrthConnector` зависит от направлений выхода и перекрытия проекций: мои замеры
покрывают 12 позиций × 7 стратегий и 16 пар сторон, но не все «повёрнутые» комбинации.
Для нашей реализации предлагаю не копировать правило, а взять принцип: *перегиб на середине
зазора, если зазор положительный; иначе обход снаружи на величину `STUB`* — это то, что у нас
уже делает `routePoints` (`geometry.js:245`).

### 4.2 Как выбирается точка подключения (свободный конец)

Конец без `exitX/entryX` «плавающий»: `mxCellState.isFloatingTerminalPoint` возвращает `true`,
и точка пересчитывается по линии центров на каждой перерисовке. Как только доля записана в
стиль, конец становится жёстким (`isFloatingTerminalPoint = false`) и больше не двигается сам.

Наш аналог — `side + t` (`geometry.js:219 edgePoint`), причём сторона выбирается по
направлению (`canvas.js:456 anchorTowards`). Разница: у нас дискретные позиции на грани
(t — доля вдоль грани), у draw.io — доля **обеих** осей рамки, то есть любая точка
прямоугольника, включая внутренность и внешность.

### 4.3 Пересечение с фигурами, `jettySize`

- Маршрутизатор **не обходит** фигуры: я поставил прямоугольник `(200,0,60,130)` прямо на путь
  `(120,60) → (420,60)` и прогнал 5 вариантов (`orth`, `orth` с `jettySize=40`, `segment`,
  и два с фиксированными сторонами) — **все пять дали одну и ту же прямую** `(120,60) (420,60)`.
  Значит писать A* «чтобы как в draw.io» не нужно.
- `jettySize` (по умолчанию 10, замерено: обход на 10 px за границу — `(40,60) (30,60) …`,
  `(80,40) (80,30) …`) задаёт **отступ при обходе собственных фигур**, когда конец выходит не
  в ту сторону. В обычном маршруте он не виден (`auto`/`0`/`40` дали одинаковый путь), но
  при зазоре меньше `jetty` перегиб уезжает: при зазоре 10 px `jettySize=0` → перегиб 125,
  по умолчанию → 130, `jettySize=40` → 160.
- Настоящий обход препятствий в продукте есть, но это **отдельная команда**:
  Arrange → Layout → «Orthogonal Routing…» (`LibavoidRouting`, `app.min.js` ≈ 10 500 840).
  То есть даже draw.io считает обход фигур не режимом рисования, а пересчётом по команде.

### 4.4 Hit testing (наш Д2)

Ядро (`mxGraph.getCellAt` + `mxGraph.intersects`): обход детей **в обратном порядке**
(последний нарисованный — первый проверенный), рекурсивно внутрь, и только потом сама ячейка.
Замер на стенде (контейнер `C=(100,100,400,300) swimlane`, дети `CH1`, `CH2`, сосед `OV`
поверх контейнера):

| точка | что вернул `getCellAt` |
|---|---|
| центр дочерней фигуры | `CH1` / `CH2` — **ребёнок побеждает контейнер** |
| пустая область контейнера | `C` |
| заголовок контейнера | `C` |
| сосед, перекрывающий контейнер | `OV` — **верхний по z побеждает** |
| на линии ребра | ребро, допуск **±4.5 px** (невидимая линия 9 px): `dy=4` попадает, `dy=5` уже нет |

То есть **по самому `getCellAt` контейнер не перехватывает** дочернюю фигуру. Наш Д2 — это не
поведение движка, а правило, которое мы сами добавили: `shapeAt` (`canvas.js:473`) берёт первую
фигуру в обратном порядке массива, в чей бокс попала точка, и **вложенность не учитывает** —
если контейнер лежит в массиве позже ребёнка, он и победит.

Дополнительно draw.io разрешает неоднозначность при **протягивании конца связи** своим кодом
(`mxEdgeHandler.createMarker().getCell`, `app.min.js`), и там есть четыре правила:

```js
if (d != null && !this.graph.isCellConnectable(d)) {          // 1. не соединяемая — взять родителя
    e = this.graph.getModel().getParent(d);
    if (this.graph.getModel().isVertex(e) && this.graph.isCellConnectable(e)) d = e;
}
if (this.graph.isSwimlane(d) && this.graph.hitsSwimlaneContent(d, x, y)   // 2. над содержимым дорожки
    || !this.isConnectableCell(d)                                          //    контейнер не цель
    || d == this.state.cell                                                // 3. не в себя
    || (d != null && !this.graph.connectableEdges && e.isEdge(d))          // 4. рёбра — только если разрешено
    || this.graph.isAncestor(this.state.cell, d)) d = null;
```

Для нас это значит: цель — **самая глубокая** соединяемая фигура, а контейнер берётся только
если под курсором нет ничего глубже (или если ребёнок не соединяем). Правило про swimlane
(над содержимым контейнер — не цель) **[гипотеза]** в части «что видит пользователь»: я прочитал
код, но не воспроизвёл сценарий мышью.

### 4.5 Перетаскивание: точки против сегмента (главная правка версии 2)

**Каким обработчиком правится ребро — решает не человек, а стиль.** Замер
`graph.createHandler(state)` для каждого стиля (`raw/bench3.json`):

| style | разрешённая стратегия | обработчик | тянется сегмент? |
|---|---|---|---|
| `edgeStyle=orthogonalEdgeStyle` | `OrthConnector` | `mxEdgeSegmentHandler` | **да** |
| `edgeStyle=segmentEdgeStyle` | `SegmentConnector` | `mxEdgeSegmentHandler` | **да** |
| `edgeStyle=orthogonalEdgeStyle;curved=1` | `OrthConnector` | `mxEdgeSegmentHandler` | **да** |
| `edgeStyle=elbowEdgeStyle` | `ElbowConnector` | `mxElbowEdgeHandler` | нет (свои ручки) |
| `edgeStyle=entityRelationEdgeStyle` | `EntityRelation` | `mxEdgeHandler` | нет |
| без `edgeStyle` (прямая) | — | `mxEdgeHandler` | нет |

Что делает каждый на перетаскивании середины сегмента (**замер вызовом того же обработчика**):

Ребро `A(40,40,80,40) → B(520,260,80,40)`, ручные точки `(240,60) (240,400) (520,400)`,
абсолютные точки `(120,60) (240,60) (240,400) (520,400) (520,300)`:

| жест | результат предпросмотра | что стало с точками |
|---|---|---|
| вертикальный сегмент `(240,60)-(240,400)` тянем на +30 по x | `(270,60) (270,400) (520,400)` | **обе ограничивающие точки** поехали вместе, новых нет |
| горизонтальный сегмент `(240,400)-(520,400)` тянем на +30 по y | `(240,60) (240,430) (520,430)` | то же, обе поехали |

Прямое ребро (`edgeStyle=none`, точек нет), тянем середину единственного сегмента:
`points: []` → предпросмотр `[(335,300)]` — **вставляется одна точка** в месте курсора.

Формула из `mxEdgeSegmentHandler.getPreviewPoints` (по смыслу):

```
pts = абсолютные точки ребра
для отрезка c→f, у которого f — захваченная ручка:
    если отрезок горизонтальный (c.y ≈ f.y):  c.y = cursor.y; f.y = cursor.y
    если отрезок вертикальный (c.x ≈ f.x):    c.x = cursor.x; f.x = cursor.x
остальные точки не меняются
```

То есть сегмент едет **перпендикулярно себе**, обе его точки получают одну координату, число
точек не меняется. Это ровно то поведение, которого не хватает нашему Д3.

Когда сегмента ещё нет (у ребра нет ручных точек), работает `mxEdgeHandler`:
`points.splice(VIRTUAL_HANDLE - index, 0, cursorPoint)` — одна новая точка на сегмент.

Бонусы из того же места: точка, брошенная на другую точку, удаляется; точка, брошенная на
прямую между соседями (с Alt / `straightRemoveEnabled`), тоже удаляется.

**Важно для нас:** вывод версии 1 («draw.io вставляет одну точку, соседние не смещаются»)
верен только для **прямых** рёбер. Для ортогональных, то есть для всех наших UML-связей,
продукт делает наоборот — двигает сегмент целиком. Это меняет рекомендацию §7.4.

## 7. Рекомендации по реализации (vanilla JS + SVG, без смены архитектуры)

Всё ниже — добавления к тому, что уже есть; ни один файл не переписывается целиком.

### 7.1 Концы: доля + смещение (P0)

Добавить в связь необязательное поле:

```js
fromAttach: { fx: 0.25, fy: 0.5, dx: 0, dy: 0, project: false }
toAttach:   { … }
```

`edgePoint(shape, layout, side, t)` остаётся как есть; новый `attachPoint(shape, attach)`
считает:

```
x = shape.x + fx * shape.w + dx
y = shape.y + fy * shape.h + dy
если project: спроецировать на границу по лучу из центра (пересечение с рамкой)
```

Правила: `project` по умолчанию `false` (как в реальных файлах); значения вне 0…1 разрешены;
при импорте не округлять — только при отрисовке. `side/t` остаются для старых файлов и для
UI «прилипло к грани».

### 7.2 Маркеры: два независимых слота (P0, закрывает Д1)

Заменить блок `render.js:1145–1148` на явный порядок «семантика решает, что за маркер; конец
решает, где он»:

```js
const ends = { from: [], to: [] };           // список маркеров на каждом конце
if (aggFrom !== 'none') ends.from.push(diamond(aggFrom));
if (def.tail)           ends.from.push(def.tail);
if (aggTo !== 'none')   ends.to.push(diamond(aggTo));
if (head && head !== 'none') ends.to.push(head);
// рисуем ВСЁ, что накопилось: ромб и стрелка сосуществуют,
// потому что они про разное (агрегация vs направление)
```

Порядок отрисовки внутри конца: сначала дальний от конца маркер (ромб), затем ближний
(стрелка), со сдвигом по последнему сегменту на длину предыдущего маркера. Так «ромб на
семантическом конце» перестаёт зависеть от того, откуда потянули линию:
`aggregationOf(rel,'from'|'to')` уже отвечает на этот вопрос (`model.js:203`).

Это **наше** отличие от draw.io (там на конец один маркер): UML требует одновременно ромб
агрегации и стрелку навигации на одном конце, поэтому слоты должны быть списками.

### 7.3 Скругление и кривая (P1)

- `rounded` оставить перечислением для совместимости, но добавить `arcSize` (число) поверх:
  `r = arcSize ?? ROUND_R[rounded]`, по умолчанию 10 для `small`.
- Обрезку `t = min(r, |сегмент|/2)` у нас уже делает `pathD` — оставить, это ровно правило draw.io.
- `curved`: новая ветка в `pathD`: `M p0` + `Q p[i] mid(p[i],p[i+1])` … + `Q p[n-2] p[n-1]`.
  Пятнадцать строк, никаких зависимостей.

### 7.4 Перетаскивание сегмента (P1, закрывает Д3) — **переписано**

Версия 1 советовала «просто вставлять точку». Замер §4.5 показал, что для ортогональных рёбер
(а у нас все UML-связи ортогональны) draw.io двигает **сегмент целиком**. Правильная модель:

1. при наведении на ребро (не на точку) найти ближайший сегмент и его ориентацию;
2. поставить курсор `row-resize` (горизонтальный сегмент) / `col-resize` (вертикальный) —
   ровно как draw.io;
3. на `pointerdown` по сегменту:
   - если у связи есть `waypoints` — взять две точки, ограничивающие этот сегмент, и двигать
     **обе** на одну величину по перпендикуляру к сегменту (вторая координата не меняется);
   - если `waypoints` нет — создать **две** точки на концах сегмента (по одной на каждой
     границе) и дальше двигать их так же; это даёт «зафиксированный маршрут» с первого жеста;
4. концы, привязанные к фигурам, пересчитываются как обычно (`edgePoint`), внутренние точки
   едут вместе;
5. при отпускании, если точки почти на прямой между соседями, — удалить (у нас это делает Alt;
   можно оставить Alt, чтобы не отбирать жест);
6. один жест = одна запись в undo (у нас уже так для точек, `canvas.js:1072`).

Для прямых связей (`route: 'straight'`) оставить прежнее поведение: жест по сегменту =
`addWaypointAt` в точке нажатия (`canvas.js:583`) — это ровно то, что draw.io делает
`mxEdgeHandler`-ом.

### 7.5 Hit testing при протягивании связи (P0, закрывает Д2)

Правило вместо «первый попавшийся предок» (`shapeAt`, `canvas.js:473`):

```
кандидат = самая глубокая фигура под курсором, у которой connectable
если кандидат — контейнер и под курсором есть ребёнок этого контейнера → взять ребёнка
если кандидат не соединяем → взять его родителя
контейнер берётся только если под курсором нет ни одной дочерней фигуры
```

Это одна функция «`targetAt(point)`», которую вызывают и создание связи, и перетаскивание конца.
Порядок обхода — как `getCellAt`: обратный z, рекурсивно внутрь, потом сам.

### 7.6 Импорт чужих файлов (P2)

`noEdgeStyle=1` → не пересчитывать маршрут; `points` брать как есть.
`sourcePoint/targetPoint` игнорировать. `entryPerimeter` по умолчанию `false`.

### 9.2 Что раскладка делает с ручной геометрией (замер, главное)

Сценарий: 8 фигур, 7 рёбер; у `e2` — 2 ручные точки, у `e3` — 3, у `e5` — 1; у `e4` и `e7`
заданы `entryX/entryY/exitX/exitY`. Запуск `mxHierarchicalLayout(DIRECTION_WEST)` по родителю:

| ребро | точки до | точки после |
|---|---|---|
| `e2` | `[260,220] [420,220]` | `[1312,25] [1388,25]` |
| `e3` | `[150,420] [250,420] [350,420]` | `[112,25] [188,25]` — **три стали двумя** |
| `e4` | нет | `[312,25] [388,25]` |
| `e7` | нет | `[912,25] [988,25]` |

- **Ручные точки не сохраняются: они перезаписываются молча.** Ни сообщения, ни флага,
  ни «оставить как было».
- Привязки концов (`entryX/entryY/exitX/exitY`) **сохраняются** — их раскладка не трогает.
- В стиль ребра дописывается `noEdgeStyle=1;orthogonal=1`: маршрут после раскладки считается
  **фиксированным**, а не автоматическим.
- Маркеры не меняются.
- **Отмена:** `undoDepth = 1`, один `undo()` вернул и точки, и стили **точно** (сравнение
  снимков `layoutUndone == layoutBefore` → `true`). Раскладка — одна операция.

Почему я уверен, что и в продукте 32.6.10 точки теряются так же: `executeLayout` оборачивает
всё в `graph.beginArrange()/endArrange()` (`app.min.js` ≈ 1 578 790), а `beginArrange` только
**запоминает изменённые ячейки** для события `cellsArranged` и открывает одну транзакцию —
никакого сохранения и восстановления `points` там нет. Плюс в бандле 805 ключей ресурсов, и
единственные ключи про точки перегиба — `waypoints` и `clearWaypoints` (панель форматирования
и пункт «Clear Waypoints» в Arrange). Строки-предупреждения не существует.
**[факт по коду; поведение ELK на живом листе мышью не прогонял]**

Отсюда прямое следствие для нашего инварианта: **поведение draw.io нельзя копировать как есть.**
Молчаливая потеря ручных точек — ровно то, чего владелец не хочет. Нам нужно то же действие,
но с явным предупреждением и выбором.

### 9.3 Что предлагается для UML

| Диаграмма | Раскладка | Почему |
|---|---|---|
| Классов | иерархическая (сверху вниз) по обобщениям | иерархия наследования читается слоями |
| Деятельности | иерархическая по потокам | поток управления и есть иерархия |
| Состояний | иерархическая по переходам | то же |
| Вариантов использования | круг вокруг актёров | связей мало, центр важен |
| Последовательности | **не применять** | время задаётся порядком сообщений, а не геометрией |
| Компонентов / размещения | «физика» / компактное дерево | важнее «не наезжать», чем слои |

### 9.4 Готовая формулировка команды

> **«Разложить»** — одна команда меню над текущим листом.
> Применяется к выделению, если оно есть, иначе ко всему листу.
> Результат — новая геометрия вершин и рёбер; **одна отмена** возвращает всё.
> Ручные точки перегиба: **диалог заранее** перечисляет «будет потеряно N ручных изгибов
> на M связях» и предлагает «Оставить изгибы / Разложить без них / Отмена».
> Точки подключения (`fromAttach/toAttach`) не меняются.
> **Не применяется сама** — ни при открытии файла, ни после импорта, ни фоном, ни «для красоты».
> Пока команда не вызвана, геометрия листа не меняется ни на пиксель.

Параметры диалога — по образцу draw.io, но без «молчаливых» опций: направление, расстояние
между уровнями и узлами, стиль соединителя (ортогональный / ломаная), углы
(как есть / прямые / скруглённые), «не менять размеры фигур».

Что именно проверять в реализации: раскладка пишет `waypoints`; после неё маршрут должен быть
помечен как ручной (у нас это «есть `waypoints`»), иначе наш `routePoints` пересчитает его и
раскладка «отменится» сама.

   пересчитан глазами в UI.
5. **Точные правила `OrthConnector`** на всех комбинациях направлений: замерено 12 позиций ×
   7 стратегий + 16 пар сторон; «повёрнутые» комбинации (выход влево, вход вверх и т.п.)
   покрыты не все.
6. **`followTerminals`** — правило пересчёта точек при переносе концов прочитано в коде,
   но не проверено движением фигуры.

Четыре из них закрыты в этой итерации и сняты с проекта: перетаскивание сегмента (п. 1 — измерено,
осталось только отсутствие мышиного прогона), меню и диалог раскладки (п. 2 в части «что предлагает
продукт»), список маркеров (п. 4), правило подписи (было отдельным вопросом, теперь §3.6).
Открытыми в проекте остаются четыре: прогон ELK-раскладки на живом листе, правило swimlane над
содержимым, полный перебор «повёрнутых» комбинаций `OrthConnector` и поведение `followTerminals`
при переносе фигуры.
