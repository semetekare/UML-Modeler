# Канонический профиль стереотипов: 428 записей → 304 стереотипа

Профиль Visual Paradigm (`material/stereotypes.xml`) — это 428 записей
`<Stereotype>`, в которых одно и то же понятие встречается по два раза, а три
понятия записаны ещё и разными буквами. Пока файл читается как есть, приложение
не может ответить на вопрос «какое определение имеется в виду»: `pictogramFor`
берёт первую запись с нужным именем, а у записи `usecase` рисунка нет — значит
`pictogramFor(profile, "usecase")` возвращает `null`, хотя у `UseCase` рисунок
есть. Разбор явления — [`STEREOTYPES.md`](stereotypes.md); этот документ — про
то, что получилось после канонизации, какими числами это доказано и что из
этого следует для `app/`.

Канонизация — данные, а не код приложения. `app/` в этой партии не менялся.

| Артефакт | Что это |
|---|---|
| [`material/profile-canonical/build.py`](../../material/profile-canonical/build.py) | сборка: XML + карта рисунков + нотация → `profile.json`, `reachability.json` |
| [`material/profile-canonical/profile.json`](../../material/profile-canonical/profile.json) | один канонический профиль: **304 стереотипа**, **407 расширений**, 428 исходных записей в `sources` |
| [`material/profile-canonical/reachability.json`](../../material/profile-canonical/reachability.json) | что приложение сможет показать, а что нет и почему |
| [`material/profile-canonical/check.mjs`](../../material/profile-canonical/check.mjs) | проверка полноты и чисел; код 1, если что-то разошлось |

---

## 1. Как воспроизвести

```sh
python3 material/profile-canonical/build.py
node material/profile-canonical/check.mjs
```

`build.py` — только stdlib Python (`xml.etree.ElementTree`, `json`, `re`,
`hashlib`, `pathlib`); `check.mjs` — только Node без зависимостей. Ничего не
устанавливается. `build.py` читает `material/stereotypes.xml`,
`material/stereotype-icons.json`, `app/notation/uml.json` и
`app/src/io/stereotypes.js` (последние два — только чтение) и пишет два файла
рядом с собой.

**Детерминированность.** В выводе нет ни времени, ни абсолютных путей; порядок
везде — порядок исходного файла. Повторный прогон даёт побайтово тот же
`profile.json` и `reachability.json` (проверено `sha256sum` двух прогонов).

**Коды возврата.** `build.py` возвращает 1, если измеренное разошлось с
`EXPECTED` в начале файла. `check.mjs` возвращает 1, если не сошлась хоть одна
из шести проверок раздела 3. Это то же правило, что у
[`audit.py`](../../material/stereotype-audit/audit.py): числа в документации не
могут тихо разъехаться с данными.

## 2. Правила канонизации

### 2.1 Словарь

| Слово | Значение | Сколько |
|---|---|---|
| **запись** | один `<Stereotype>` из `ApplicationStereotypes` или `ProjectStereotypes`, в порядке файла | 428 |
| **определение** | пара (каноническое имя, `baseType`) — одно расширение одного стереотипа | 407 |
| **стереотип** | одно имя и список `baseTypes[]`; по UML 2.5.1 §12.3.3.4 расширений может быть несколько | 304 |

Правило «одно имя — один стереотип» — то, ради чего всё делалось: в списке
инспектора `entity` один пункт с пятью расширениями, а не пять пунктов с
одним именем.

### 2.2 Дедупликация: `(нормализованное имя, baseType)`

Записи группируются по паре (нормализованное имя, `baseType`); в группе
остаётся **прикладная** запись, потому что она первая в файле и означает
«общая для всех проектов». Проектная не выбрасывается: её `id` попадает в
`sources` канонического стереотипа, а `check.mjs` доказывает, что каждая из
428 записей находится ровно в одном `sources`.

Нормализация — нижний регистр, пробелы, `_` и `-` выброшены. Это ключ
сведения, а не сравнения имён: `Default` и `default` схлопываются как одно
понятие, но их `baseType` остаются разными расширениями.

| Шаг | Правило | Результат |
|---|---|---|
| 1 | 428 записей по ключу `(имя, baseType)` | 410 определений, 18 записей — дубли |
| 2 | те же 410 по ключу `(нормализованное имя, baseType)` | 407 определений, ещё 3 записи — варианты написания |
| 3 | 407 определений по каноническому имени | 304 стереотипа |

Снятые 21 запись: **18 настоящих дублей** (прикладная + проектная копия) и
**3 дефекта написания**. Ни одна не потеряна — все 428 `id` есть в `sources`.

### 2.3 Написание: детерминированный выбор

Каноническое написание выбирается так, без вкусовщины:

1. написание, которое уже пишет нотация (`app/notation/uml.json`, поля
   `stereotype` / `keyword`), — чтобы элементы, созданные нашими инструментами,
   совпадали с профилем;
2. иначе — написание **первой прикладной** записи в файле;
3. иначе — первой проектной.

Остальные написания не выбрасываются: они лежат в `aliases` и по ним
разрешается модель, где записано другое написание (правило §4.2
`STEREOTYPES.md`). Всего псевдонимов — 9.

Семь групп, где написание разошлось:

| Нормализованное | Написания | Каноническое | Почему | Дефект? |
|---|---|---|---|---|
| `executionenvironment` | `execution environment`, `executionEnvironment` | `executionEnvironment` | нотация | **да** |
| `usecase` | `usecase`, `UseCase` | `usecase` | первая прикладная | **да** |
| `usecaserealization` | `usecase realization`, `use case realization` | `usecase realization` | первая прикладная | **да** |
| `default` | `Default`, `default` | `Default` | первая прикладная | нет |
| `interface` | `Interface`, `interface` | `interface` | нотация | нет |
| `participant` | `participant`, `Participant` | `participant` | первая прикладная | нет |
| `service` | `Service`, `service` | `Service` | первая прикладная | нет |

Первые три — дефекты: совпали и область, и `baseType`, то есть один стереотип
записан дважды. Четыре остальных — **не дефекты**: совпало написание, а
`baseType` разные, по §7.4.3.2 это различимые члены. Их записи не удалены:
они стали расширениями одного стереотипа (`Default` — `State2`,
`ActivityAction`, `Transition2`, `Operation`), а прежнее написание осталось
псевдонимом. В отчёте такие группы помечены `defect: false` и
`collapsedDefinitions: 0`.

Отдельно — два имени, которых в профиле **нет в каноническом написании**, потому
что нотация пишет их иначе:

| Профиль | Нотация | Каноническое | Псевдоним |
|---|---|---|---|
| `Include` (проектный) | `include` (ключевое слово) | `include` | `Include` |
| `Extend` (проектный) | `extend` (ключевое слово) | `extend` | `Extend` |

Это то же решение, что описано в `STEREOTYPES.md` §4.6, шаг 6 и вопрос 10:
одно понятие — одно написание; на листе остаётся `«include»`.

### 2.4 Один стереотип — много `baseTypes`

`baseTypes[]` — объединение `baseType` всех схлопнутых записей, в порядке
первого появления. Так 7 записей `process` становятся одним стереотипом с
семью расширениями, а `entity` — с пятью (`Component`, `Class`, `Object`,
`InteractionLifeLine`, `AssociationClass`). Всего 407 расширений у 304
стереотипов: **103 определения слились в `baseTypes[]`**.

Слияние не теряет содержимое. Если tagged-определения у разных `baseType`
различаются, они сохраняются в `taggedValuesByBaseType`, а не выбираются
молча:

| Стереотип | Что различается | Что сохранено |
|---|---|---|
| `XSDschema` | у `Package` два определения (`Namespace`, `NamespacePrefix`), у `Class` — ни одного | `taggedValuesByBaseType: {Package: […], Class: []}` |
| `usecase` | у `UseCase` смысловой порядок перечислений, у `Class` — алфавитный | `taggedValuesByBaseType` + `taggedValuesVariants` |

`taggedValuesVariants` хранит и различие **внутри одного `baseType`**: у
`usecase` × `UseCase` есть прикладная запись со смысловым порядком
(`Summary → User → Subfunction`) и запись `UseCase` с алфавитным. Обе остаются
в профиле с источниками, поэтому «порядок значений перечислений» — уже не
потеря, а выбор приложения.

### 2.5 Рисунок: `iconPath` не теряется

`iconPath` — указатель VP на файл в его архиве. В каноническом профиле он не
переносится как путь для рисования, но **сохраняется как доказательство**:
`pictogram.iconPaths` перечисляет все непустые пути схлопнутых записей, а
`pictogram` выбирает рисунок по первому.

| Величина | До | После |
|---|---|---|
| записей с непустым `iconPath` | 29 | — |
| определений (имя × `baseType`) с рисунком | — | **24** |
| стереотипов с рисунком | — | **15** |
| различных `iconPath` | 23 | **23** (все в `iconPaths`) |
| различных рисунков (`glyph`) | 15 | **15** |

Рисунок один на стереотип, но **разный по `baseType`**: `pictogramByBaseType`
хранит рисунок для каждого расширения. Это важно для Б11: у `usecase` овал
принадлежит записи на `Class`, а у расширения `UseCase` рисунка нет, поэтому
`pictogramFor` обязан учитывать `baseType` элемента, а не только имя
(`STEREOTYPES.md` §2.8).

### 2.6 Остальные поля

| Поле | Правило |
|---|---|
| `id` | `st-` + слаг канонического имени (`st-entity`, `st-usecase-realization`), устойчив между прогонами |
| `scope` | `application`, если хоть одна схлопнутая запись прикладная, иначе `project`; точная область каждой записи видна по префиксу `A:` / `P:` в `sources` |
| `documentation` | первая непустая по файлу; в данных нет группы, где документации противоречат |
| `sources` | все `id` схлопнутых записей в порядке файла, `A:` — прикладная, `P:` — проектная |
| `rules` | текстом в самом `profile.json`: какое правило к чему применено |

**Что сознательно не переносится: `<Formats>`.** Это оформление VP (заливка,
шрифт), а не смысл UML; таких записей 8. В приложении своя палитра, и хранить
чужой `Fill color1="Cr:…"` в профиле стереотипов незачем. Это единственная
осознанная потеря, и она не про смысл — в отличие от «порядка перечислений»,
который сохранён.

### Что проверяет `check.mjs`

| # | Проверка | Как доказано |
|---|---|---|
| 1 | ни одна запись не потеряна и не посчитана дважды | все 428 `id` из XML найдены в `sources`; `sources` покрывают 428/428; повтор `id` — ошибка |
| 2 | 428 → 407 (−21) | 410 точных пар − 3 сведения написаний; 18 = 428 − 410 |
| 3 | все 23 `iconPath` сохранены | множество путей в `pictogram.iconPaths` равно множеству непустых путей XML; каждый есть в карте рисунков |
| 4 | `baseTypes` — объединение схлопнутых | для каждого стереотипа множество `baseType` его `sources` равно `baseTypes` |

| 6 | числа не разъехались | `EXPECTED` (428, 407, 23, 304) и производные (410, 18, 3, 21, 15) |

Проверка падает и на испорченном `profile.json`: удалённый `sources`,
выдуманный `baseType` и потерянный рисунок дают три разных сообщения (это
проверено прогоном на копии).

## 4. Что достанется приложению

### 4.1 Достижимость

Приложение привязывает `baseType` профиля к видам элементов и связей в
`APPLICABILITY` (`app/src/io/stereotypes.js`): 64 вида, 56 `baseType`. Сверка с
профилем даёт:

| Величина | Значение |
|---|---|
| `baseType` в профиле | 97 |
| из них упомянуты в `APPLICABILITY` | **52** |
| записей, достижимых | **277 из 428** (64,7 %) |
| записей, недостижимых | **151** |
| стереотипов, которые можно показать хоть где-то | **173 из 304** |
| стереотипов, недостижимых целиком | **131** |
| стереотипов, достижимых частично (часть расширений — нет) | **9** |

173 = 304 − 131; девять частично достижимых входят в 173. Пример частичного —
`Default`: `State2`, `ActivityAction`, `Transition2` достижимы, `Operation` нет;
`bind` достижим на `Realization` и нет на `BindingDependency`.

### 4.2 Две причины недостижимости, и их нельзя смешивать

| Семейство | Записей | Это чужая нотация или наш пробел |
|---|---|---|
| `Attribute` (38) + `Operation` (6) | **44** | **по делу**: у нас атрибут и операция — строки членов, а не элементы; стереотип на них не надеть |
| `BMMRelationship` (37) | **37** | **чужая нотация**: Business Motivation Model |
| `ArchiMate*` (27 значений) | **48** | **чужая нотация**: ArchiMate, вне границ проекта |
| `SysML*` (9 недостижимых значений) | **11** | **чужая нотация**: SysML, вне границ проекта |
| `Requirement` (2), `Reception` (1), `ValuePin` (3), `ExpansionNode` (3) | **9** | **наш пробел**: метаклассы UML, вида элемента нет |
| `BindingDependency` (1), `CollaborationOccurrence` (1) | **2** | **наш пробел**: метаклассы UML, вида связи нет |

Итого **151**: по делу недостижимы **140** (96 записей чужих нотаций + 44
члена-строки), из-за пробела нотации — **11**. Пробел — это шесть метаклассов
UML: `Requirement`, `Reception`, `ValuePin`, `ExpansionNode`,
`BindingDependency`, `CollaborationOccurrence`; их и надо решать в Б14.

Отдельно: чужих записей **104**, а не 96, — `BMM` 37 + `ArchiMate` 48 +
`SysML` 19. Восемь из них достижимы, потому что `APPLICABILITY` принимает
`SysMLBlock`, `SysMLValueType` и `SysMLParticipantProperty`. «104» — это объём
чужой нотации в профиле; «96» — сколько из неё недостижимо.

### 4.3 Обратное направление: пробел в профиле

`APPLICABILITY` ссылается на четыре `baseType`, которых в профиле нет вовсе:

| `baseType` | Виды приложения | Что это значит |
|---|---|---|
| `DeploymentSpecification` | `deploymentSpec` | частично закрыт `Artifact` |
| `Interaction` | `interaction`, `interactionUse` | **у этих двух видов не остаётся ни одного стереотипа** |
| `Message` | `message`, `reply`, `createMessage`, `destroyMessage` | частично закрыт `SequenceMessage` и др. |
| `Property` | `part` | частично закрыт `Collaboration2` и `SysMLParticipantProperty`; сам стереотип `Property` есть, но на `Attribute` |

То есть недостижимость бывает двух направлений: **профиль обещает то, чего нет
в нотации** (151 запись) и **нотация ждёт то, чего нет в профиле** (4
`baseType`). Второе — не 151 запись, а дырка в списке «Подходящие»; у
`interaction` и `interactionUse` она полная, у остальных частичная.

### 4.4 Что с этим делать в Б14

1. **11 записей пробела** — либо добавить шесть метаклассов в нотацию, либо
   честно записать их в «неприменимо» (решение человека, вопрос 6 в
   `STEREOTYPES.md`).
2. **4 отсутствующих `baseType`** — не записи профиля, а строки
   `APPLICABILITY`: либо убрать их из списков (и сказать, что стереотипов для
   `interaction` нет), либо завести виды `Interaction`/`Message`.
3. **140 записей «по делу»** — не показывать в «Подходящих». Скрыть совсем или
   показать серыми в разделе «неприменимо» — вопрос 6, к числам он не
   относится.

`app/` в этой партии закрыт: ниже — оценка, не код.

значит держать вторую копию правил из раздела 2 и риск, что она разойдётся с
`check.mjs`.

### 5.2 Старые файлы моделей

В файле стереотип записан строкой: `element.stereotype = "UseCase"`. После
канонизации каноническое имя — `usecase`, поэтому:

| Что | Что произойдёт |
|---|---|
| сам файл | **не меняется**: `serialize` пишет ту же строку, побайтовое пересохранение `old-v3.json` сохраняется (правило 1 из §4.1) |
| подпись на листе | остаётся `«UseCase»`: рисуется то, что лежит в модели |
| разрешение имени | точное совпадение больше не находит запись; находит **нормализованное** (`UseCase` → `usecase`), но только если приложение делает второй шаг из §4.2 `STEREOTYPES.md` |
| tagged values и рисунок | находятся **только** через этот второй шаг; без него старое `«UseCase»` потеряет и то, и другое — это единственная видимая регрессия, если Б11 не сделать |
| `Include` / `Extend` | старые значения разрешаются в `include`/`extend` по нормализации; подпись остаётся `«Include»`/`«Extend»`, если её не нормализовать при показе |
| `default` | разрешается в `Default`; у `Operation` tagged-определений нет, так что видимой разницы нет |
| `use` | в профиле есть `use` только на `BMMRelationship`; это ключевое слово нотации, а не применённый стереотип — поведение не меняется, потому что точное совпадение и сегодня находит ту же запись |

Вывод: **строку в файле трогать не нужно и нельзя**; нужен резолвер
`точное имя → нормализованное имя → null` и `pictogramFor` с `baseType`. Оба
пункта — работа Б11, и без них канонизация ухудшит вид старых моделей, а не
улучшит.

## 6. Открытые вопросы

1. **`usecase` строчными.** Правило «первая прикладная запись» даёт `usecase`,
   хотя в VP на диаграммах видно `«UseCase»`, и старые файлы пишут `UseCase`.
   Оставить вычисленное правило (и лечить псевдонимом) или зафиксировать
   `UseCase` вручную? Это самый спорный выбор канонизации: он единственный, где
   правило и привычная подпись расходятся. Так же спорны `usecase realization`
   (против `use case realization`) и `include`/`extend`, которые стали
   ключевыми словами.
2. **Слияние четырёх «недефектных» групп.** `Default`/`default`,
   `Interface`/`interface`, `Participant`/`participant`, `Service`/`service`
   теперь один стереотип с несколькими `baseTypes[]`. Формально §7.4.3.2
   позволяет считать их разными; мы выбрали «одно понятие — одно имя». Если
   нужна раздельность, это одна строка в правиле, но список снова вырастет.
3. **`taggedValuesByBaseType`.** UML говорит, что у стереотипа один набор
   свойств; VP хранит разные наборы для разных `baseType` (`XSDschema`,
   `usecase`). Профиль сохраняет оба. Должен ли инспектор показывать их
   по-разному для `Class` и `Package`, или это ошибка данных, которую надо
   отвергнуть?
4. **Порядок перечислений `usecase`.** Смысловой порядок сохранён в
   `taggedValuesVariants`, но какой из двух вариантов считать основным —
   вопрос человека (вопрос 2 в `STEREOTYPES.md`).
5. **131 стереотип недостижим целиком.** Скрыть из списка или показывать
   серыми? На числа не влияет, на доверие человеку — влияет.
6. **Четыре проектных ключевых слова** (`include`, `extend`, `import`,
   `substitute`). В профиле они остались стереотипами проекта; стандарт
   §12.4.9.6 `name_not_clash` не велит их импортировать. Показывать их в
   списке как в VP или считать ключевыми словами нотации?
7. **Восемь достижимых записей SysML.** `SysMLBlock`, `SysMLValueType`,
   `SysMLParticipantProperty` приложение принимает, хотя SysML вне границ
   проекта. Оставить как есть или убрать из `APPLICABILITY`, чтобы «чужая
   нотация» была честно недостижима?
8. **`<Formats>`.** Восемь записей VP несут заливку и шрифт; в профиль они не
   перенесены. Нужны ли они для сверки с оригиналом, или это лишний вес?
