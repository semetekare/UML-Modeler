## 2. Порядок применения

Порядок не произвольный: каждый шаг опирается на предыдущий, и обратный ход стоит
дороже прямого. Он совпадает со сводным порядком [`docs/README.md`](../docs/README.md),
но разложен по тому, **что можно сделать, не дожидаясь формата**.

### Шаг 0 — видимое, без формата (0.5–1 день)

Делается на текущем `uml-class-diagram/1`, ничего не закрепляет.

1. **Одна полоса инструментов над листом** вместо тулбара и вкладки «Палитра»
   (`ui-audit-design.md` §3.1, `density-spec.md` §5). Дерево получает всю левую панель.
2. **Дерево вкладкой по умолчанию**; палитры-вкладки нет.
3. **Меню масштаба в статусбаре**: 50 / 75 / 100 / 125 / 150 / «вписать», `Ctrl+0`,
   `Ctrl+=`, `Ctrl+-` (`ui-audit-design.md` §3.2).
4. **favicon** — `app/src/brand/icons/favicon.svg` вместо data-URI в `index.html`.
5. **`aria-label`** на 35 кнопок без него.

**Критерий:** ни одного действия в двух местах; ноль ошибок в консоли; левая панель
при открытии показывает дерево.

### Шаг 1 — токены бренда (0.5 дня)

Создать `app/src/brand/brand.css`; `ui-kit` не править, только переопределять.

```css
:root { --brand: #fa5d00; }
[data-brand="moss"] { --brand: #4f6b21; }
[data-brand="teal"] { --brand: #0e7490; }
[data-brand="violet"] { --brand: #6b3fd4; }
[data-brand="plum"] { --brand: #9a1f6e; }
[data-brand="graphite"] { --brand: #3f3f42; }

:root {
  --brand-ink:    color-mix(in oklab, var(--brand) 78%, #000);
  --brand-strong: color-mix(in oklab, var(--brand) 62%, #000);
  --brand-soft:   color-mix(in oklab, var(--brand) 12%, var(--surface-paper));
  --surface-paper:  #ffffff;
  --surface-panel:  #fbf7f2;
  --surface-desk:   #f4efe9;
  --surface-sunken: #f7f2ec;
}
```

Плюс `--sc-accent`, `--sc-accent-rgb`, `--sc-glow`, `--sc-glow-rgb` ← `--brand`, и
`--sc-app` ← `--brand` (сейчас там фиолетовый `#5b6ee1`, `adapters/uml.css:17`).
Выбор пресета — `localStorage['brand']`, читать **до первой отрисовки**.

**Критерий:** после внедрения пересчитать контраст `--brand-ink` на трёх поверхностях;
отклонение от таблицы `DESIGN-BRIEF.md` §5.3 не больше 0.15, порог 4.5 не пробит.

### Шаг 2 — формат `uml-model/2` (1–2 дня)

Без него шаги 3–5 закрепят однодиаграммность. Схема — `model-view-ui.md` §2.1:
`elements` + `packages` + `diagrams` + `shapes` (с `elementId`) + `connections`
(с концами-элементами) + `connectors` (с `connectionId`).
Миграция старого файла на чтении — `uml-class-diagram/1` → элементы из `shapes`,
одна диаграмма.

**Критерий:** старый файл открывается; переименование класса на одной диаграмме видно
на второй; `uml-component` стал видом, а не схемой.

### Шаг 3 — модель и вид в интерфейсе (2 дня)

По `model-view-ui.md` §2–§6: три состояния элемента (`●` здесь / `○` в модели /
`◌` нигде), две команды удаления, связи в дереве, «показать связанные»,
вложенные диаграммы.

**Критерий:** `Del` на листе маскирует; `Shift+Del` удаляет из модели с честным
подтверждением; элемент остаётся в дереве после снятия с листа; `Ctrl+Z` возвращает
удаление из модели.

### Шаг 4 — таблица членов класса (1 день)

`ui-audit-design.md` §3.3. Колонки видимость / имя / тип / значение / флаги
(`ID`, `/` derived, статический). Сигнатура операции — поля, не строка мини-языка.

**Критерий:** `updateStudent(st:Student):boolean` задаётся полями; флаги — свойства
модели, а не символы в тексте.

### Шаг 5 — иконки в коде (0.5 дня)

Сейчас **0 из 36 файлов импортируются кодом**: палитра рисуется функциями в
`app/src/ui/icons.js` на третьей сетке `viewBox="0 0 32 20"`, значки видимости —
инлайном в `render.js:123`, favicon — data-URI. Подключение — по
`icon-inventory.md` §3.1.

**Критерий:** цвет иконки наследуется (`currentColor`), в файлах нет `#000000`;
палитра и лист используют один набор.

### Шаг 6 — остальное по `docs/README.md`

Семантика класса, семантика связи, пакеты, затем типы диаграмм. Здесь дизайн уже
ничего не добавляет: `model-view-ui.md` §7–§8 описывает инспектор, а порядок задан
источником.

## 3. Противоречия между файлами и как они сняты

Файлы писались независимо, по одному источнику. Расхождения есть, и они сняты
здесь, а не замолчаны.

### 3.1 Где живут инструменты: командная полоса 32 px или полоса с подписями

`density-spec.md` §5 предлагает убрать палитру и положить девять инструментов в
командную полосу иконками (24 px). `ui-audit-design.md` §3.1 предлагает отдельную
горизонтальную полосу над листом с подписями.

Оба правы в разном. Аргумент за подписи настоящий: в UML класс, интерфейс и
перечисление на иконке 16 px неразличимы, а `UX-OPERATIONS` §3.1 перечисляет
инструменты **именами**. Аргумент за 24 px тоже настоящий: арифметика
`density-spec` §4 показывает запас 205 px при 820.

**Решение: полоса инструментов над листом, значок 24 + подпись 11 px под ним.**
Это не 84 px референса и не 32 px командной полосы. Высота: 24 + 4 + 16 + 2×6 = **56 px**.
Подписи появляются только там, где полоса физически влезает — посчитано:

| Ширина окна | Лист | Нужно с подписями | Нужно иконками | Форма | Запас |
|---|---|---|---|---|---|
| 1440 | 854 | **765.1** | 356.0 | подписи, 56 px | +72.9 |
| 1366 | 780 | 765.1 + 16 = **781.1** | 356.0 | иконки, 32 px | перебор **1.1** |
| 1280 | 694 | 781.1 | 356.0 | иконки, 32 px | — |
| 1024 | 486 | 781.1 | 356.0 | иконки, 32 px | — |
| 820 | 602 | 781.1 | 356.0 | иконки, 32 px | — |

Ширины подписей — Inter 11/400, `fontTools` `[ИЗМ]`: «Перечисление» 79.0,
«Зависимость» 71.1, «Примечание» 68.2, «Ассоциация» 65.2, «Реализация» 63.2,
«Обобщение» 63.1, «Интерфейс» 59.8, «Выбор» 35.2, «Класс» 32.5, «Пакет» 31.9.
Ячейка = подпись + 16 (паддинг 8×2), зазор 4, полевой отступ 16.

**Порог: подписи при ширине окна ≥ 1370 px.** При 1366 не хватает **1.1 px** — это
тот случай, когда «почти влезает» нельзя выдавать за «влезает»: 1366 идёт в форму
с иконками. Полоса с подписями стоит над листом и занимает только его ширину, а не
ширину окна — поэтому её и не складывают с хлебными крошками и «Справкой» из
командной полосы `density-spec.md` §4.1.

При иконках подписи не теряются: они есть в палитре команд `Ctrl+K` и в `title`
каждой кнопки.

### 3.2 Интерлиньяж: 1.21 от метрик или явные 16 px

`DESIGN-BRIEF.md` §6.3 считает высоты как «13.3 + 2×5 → 24», беря интерлиньяж
1.21 из `hhea` Inter (1984/−494/0, `fontTools`). `density-spec.md` §2.1 показывает,
что это даёт **дробный** паддинг: (24 − 13.31)/2 = 5.345 px, и базовая линия
попадает между пикселями.

**Принято исправление `density-spec`, и бриф уже исправлен:** интерлиньяж задаётся
явно — **16 px** для кеглей 11 и 12.5 (`DESIGN-BRIEF.md` §7.1). Тогда любая строка =
16 + 2·k·4, паддинги целые, высоты остаются те же (24 / 28 / 32 / 44). Заодно
уточнено обоснование минимума: при 11 px x-height Inter = **6.005 px** и cap =
**8.003 px** — целые; при 10.5 px 5.73 и 7.64, то есть дробные и «мыльные» на 1×.

### 3.3 Ширина инспектора: 296 или 320

`DESIGN-BRIEF.md` §6.6 даёт 296 для всех ширин ≥ 1200. `density-spec.md` §4.3 даёт
**320 докнутым** и 296 при 1024, с порогом «докнутый инспектор при холсте ≥ 462 px».
462 — ширина холста в кадре `1001.png` (x 252…716 = 465 минус рамка) `[ИЗМ]`, то есть
та ширина, в которой нарисованы все 12 диаграмм классов учебника.

**Принято `density-spec`, и бриф уже исправлен:** 320 / 296 / накладной
(`DESIGN-BRIEF.md` §6.6), потому что порог обоснован измерением, а 296 — круглое
число без источника. 320 выбрано не «покрупнее»: при нём колонка имени получает
104 px, чего хватает на `CourseOffering` (80.5) и `updateStudent` (78), но **не**
хватает на `hasScheduleForSemester` (133.8) и `getCourseOfferingList` (115.6) —
два имени из двадцати обрезаются, и это названо ценой. Панель 350 убрала бы обрезку,
но при 1024 холст упал бы до 432 < 462 и нарушила бы порог докнутого инспектора.

### 3.4 Ширина левой панели: 264 или 236

`DESIGN-BRIEF.md` §6.6 и `density-spec.md` §4.3 — 264/240/216.
`model-view-ui.md` §2.3 рисует схему с подписью «дерево · 236 px».

**Принято 264/240/216** (`DESIGN-BRIEF.md` §6.6). 236 в схеме — перенос числа из
`mechanics.json`, которое
`MEASUREMENTS-AUDIT.md` §4.2 опровергает (в оригинале 202 и 328 на двух кадрах;
величина тянется сплиттером). Схема `model-view-ui` — иллюстрация расположения,
не спецификация ширины.

### 3.5 Граница поля: bone или driftwood

`DESIGN-BRIEF.md` §4.1 (первая редакция) отдавал границу поля цвету `bone #c0bbb6`
по прямому маппингу Harvest → `--sc-line-strong`. `density-spec.md` §2.6 посчитал
контраст: **1.81:1** на креме.

**Принято исправление, бриф уже исправлен** (`DESIGN-BRIEF.md` §4.4). WCAG 1.4.11
требует 3:1 для границы элемента управления; bone не проходит ни на одной из наших
поверхностей (1.67–1.90). Границу рисует `driftwood #8e8b87` (3.05–3.39), hover и
рамку выбранного — `ash #777571` (4.02–4.60). Это единственное место, где brand-слой
Harvest пришлось поправить, а не перенести: значение взято из референса, проверено и
не прошло проверку.

### 3.6 Палитра: «нет в раскладке» или «полоса 84 px»

`density-spec.md` §5 говорит «палитры как постоянной полосы — 0 px».
`ui-audit-design.md` §3.1 говорит «горизонтальная полоса над листом, 84 px».

Расхождения нет по существу: оба убирают палитру из **левой панели**. Разница — в
высоте полосы: 84 у референса, 56 у нас (§3.1). 84 не берём: в референсе значок
30 px и подпись под ним (`MEASUREMENTS-AUDIT.md` §4.1: значки `y 61…92` = 31 px,
подписи `y 96…109`), у нас значок 24 — разница 28 px уходит листу.

Полоса 84 px остаётся в силе как **источник** числа: она измерена в кадре и
подтверждает, что палитра в оригинале горизонтальная, а не боковая. Это единственный
вывод, который из неё берётся; высоту мы задаём свою.
